# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## Monorepo

This is a **pnpm + Turborepo** monorepo. Run repo-wide tasks from the root; run app-specific commands through the workspace filters.

```
apps/api                @fitme/api     — Hono REST API (Node)
apps/coach              @fitme/coach   — the Coach: an EVE agent (Vercel's durable agent framework, ai@7)
apps/exercises          @fitme/exercises — Exercise Library API: Hono + zod-openapi, serving a baked-in library.json bundle (Node)
apps/mobile             @fitme/mobile  — Expo / React Native app
apps/web                @fitme/web     — Next.js (App Router) web app
apps/site               @fitme/site    — Next.js marketing site (Vercel project fitme-site; fitmeproject.com isn't served from it yet, see apps/site)
apps/webhooks           @fitme/webhooks — Hono app receiving third-party webhooks (Node)
packages/core           @fitme/core    — domain models, labels, formatters, pure helpers
packages/exercise-library @fitme/exercise-library — the Exercise Library API client shared by the Coach, MCP and mobile, plus its in-memory fake
packages/design-tokens  @fitme/design-tokens — the design tokens and HIG text style utilities: one Tailwind v4 CSS file (mobile, web and site import it)
packages/supabase       @fitme/supabase — Supabase project + generated DB types
packages/db             @fitme/db      — asUser / withService: the only way backend apps reach Postgres
packages/observability  @fitme/observability — errors and traces: the shared privacy, propagation, environment and sampling rules, and the Node setup (Sentry behind it)
packages/services       @fitme/services — business logic run inside an asUser / withService transaction
packages/typescript-config              — shared tsconfig presets
```

## Architecture

### apps/mobile — Expo app

React Native / Expo app using **file-based routing** via `expo-router`:

- `app/` — Expo Router routes (file-based navigation)
  - `_layout.tsx` — Root layout: initializes fonts, Sentry and RevenueCat, and default-exports the layout through `Sentry.wrap` (render crashes, touch breadcrumbs, app start). Sentry (`@sentry/react-native`, the `fitme-mobile` project) is off in `__DEV__` builds (`enabled: !__DEV__`), takes `scrubEvent` (`beforeSend` / `beforeSendTransaction`) and `tracePropagationTargets` from `@fitme/observability`'s root export (trace headers to our services only, never Clerk, RevenueCat, Supabase or Segment), `sendDefaultPii: false`, traces at 0.1 and profiles at 0.5 of traced sessions. Release builds upload source maps and dSYMs through the `@sentry/react-native/expo` plugin (`SENTRY_AUTH_TOKEN` in the EAS `production` environment)
  - `(tabs)/` — Bottom tab navigator (Home, History, Coach, Library, Profile). Native tabs only show routes declared in `_layout.tsx` (SDK 58), so Home is the `(home)` group: its `index.tsx` is the app's `/` route, with no redirect route in between
  - `auth/` — Login/Register screens and the shared emailed-code screen (presented as fullscreen modal)
  - `onboarding/` — Post-registration onboarding flow (fullscreen modal)
  - `planner/` — AI plan generation flow (modal)
  - `plans/[planId]/` — Plan detail and workout views
  - `exercises/[exerciseSlug]/` — Exercise detail view and its guide (a form sheet), keyed by Exercise slug and read from the Exercise Library API
- `components/` — Reusable UI components
  - `ui/` — Primitive UI components (Button, Input, Dialog, etc.) built on `@rn-primitives`
  - `providers.tsx` — Wraps app with ClerkProvider (secure-store token cache), QueryClientProvider, ThemeProvider, KeyboardProvider; renders `auth-sync.tsx`, which identifies the Clerk User to Sentry (`{ id }`, the Clerk id only: no email or name; cleared on sign-out)/RevenueCat/Segment and clears the query cache on sign-out
  - `authenticated.tsx` — Auth guard component: waits for Clerk to load, redirects to `/auth/register` when signed out
- `hooks/` — Data layer
  - `queries/` — Read queries using `react-query-kit`'s `createQuery`; `exercise-library.ts` holds the Exercise Library hooks (see Key Patterns)
  - `mutations/` — Write mutations using `react-query-kit`'s `createMutation`
  - `revenueCat.ts` — RevenueCat subscription queries
  - `coach-model.ts` — `useSelectedCoachModel`: the served model list, the picked model and its setter, for the Coach header and model picker
- `lib/` — App-specific utilities
  - `supabase.ts` — Supabase client whose access token is the Clerk session token (no Supabase Auth session)
  - `clerk.ts` — Clerk publishable key, `getClerk()` for code outside React, `getCurrentUserId()`, `getClerkErrorMessage()`
  - `mmkv.ts` — MMKV storage instance (`createMMKV()`, react-native-mmkv 4 on Nitro Modules; same default instance and directory as v3, so saved data carries over), plus `devToolsStorage`, the same instance with `delete` for the devtools sync. Under Jest MMKV swaps in its own in-memory instance; `package.json` maps `react-native-nitro-modules` to `test-utils/nitro-modules.ts` so the import resolves
  - `coach-chat.ts` — Coach screen helpers: `COACH_URL`, per-turn model context, error → paywall mapping, the saved Conversation (see Key Patterns)
  - `exercise-library.ts` — the `@fitme/exercise-library` client, at `EXPO_PUBLIC_EXERCISES_URL` with the User's Clerk session token resolved per request; `exercise-cache.ts` keeps the Exercises it resolved in MMKV (see Key Patterns)
  - `coach-model.ts` — the Coach model list's schema and MMKV cache (`coach.models`), and the picker's choice (`coach.model`) resolved against it (see Key Patterns)
  - `utils.ts` — `cn()` class merger (tailwind-merge with the HIG font scale)
  - `segment.ts` — the Segment client, created at import. Segment generates ids through `crypto.getRandomValues`, so `react-native-get-random-values` is a direct dependency even though no app code imports it: only a direct dependency gets its native module (`RNGetRandomValues`) autolinked, and without it the client throws at import and the app never renders. Don't remove it as unused.
  - `constants.ts`
- `plugins/` — local Expo config plugin for Xcode 27 compatibility: `with-ios-min-deployment-target.js` (raises pod targets below iOS 15.1, including resource bundles; still needed on SDK 58, since pods such as `react-native-keyboard-controller`, `react-native-safe-area-context`, `@sentry/react-native` and Segment still declare older minimums). RevenueCat needs no patch: `react-native-purchases` 10 pins purchases-ios 5.95.0, which builds under Xcode 27 / Swift 6.4. The app itself targets iOS 16.4 (SDK 58's default). UIScene adoption needs no flag on SDK 58: prebuild generates `SceneDelegate.swift`, so there is no `expo-build-properties` plugin.

### apps/web — Next.js app

- `app/` — App Router routes. `(app)/` is the authenticated area (dashboard; account menu is Clerk's `<UserButton>`); `sign-in/[[...sign-in]]` is Clerk's prebuilt `<SignIn>` page. `ClerkProvider` in the root layout sets the sign-in URL and sends signed-out Users to `/`.
- `proxy.ts` — Next 16 request proxy running `clerkMiddleware`: every route except `/` and `/sign-in` calls `auth.protect()`, which redirects signed-out requests to sign-in with a `redirect_url` back. Route paths live in `lib/routes.ts`.
- `lib/supabase/server.ts` (`createClient()`, Server Components) and `lib/supabase/client.ts` (`useSupabase()` hook, Client Components) — `supabase-js` clients typed with `Database` from `@fitme/supabase` whose `accessToken` is the User's Clerk session token, so RLS reads their Clerk id from `sub`. There is no Supabase Auth session in the web app.
- `components/ui/` — shadcn-style primitives (Tailwind v4 + cva). `components.json` is set up for the shadcn CLI.
- Styling: Tailwind v4 via `@tailwindcss/postcss`; `app/globals.css` imports `@fitme/design-tokens` and only maps the font roles to the `next/font` variables (`--next-font-*`). Dark only (`color-scheme: dark`), whatever the OS setting.
- `lib/clerk-appearance.ts` — Clerk's `appearance.variables` as `var(--color-…)` / `var(--radius-…)` / `var(--font-…)` strings, passed once to `ClerkProvider`, so `<SignIn>` and `<UserButton>` follow the tokens.
- Errors and traces: `@sentry/nextjs`, reporting to the `fitme-web` Sentry project (`NEXT_PUBLIC_SENTRY_DSN`, browser and server alike; unset → nothing sent), every option from `lib/observability.ts`'s `sentryOptions()`: the root export's `sdkOptions` for that DSN, the same options `@fitme/observability/node` starts with. `instrumentation.ts` starts it on the server (Node and edge) and exports `onRequestError`, so errors from Server Components, route handlers, server actions and `proxy.ts` are reported; `instrumentation-client.ts` starts it in the browser with `browserTracingIntegration` (page loads, navigations, `fetch` spans; trace headers to the propagation targets only) and no Session Replay or web vitals (an empty integration named `WebVitals` keeps browser tracing from adding the real one; Vercel Speed Insights covers vitals). `app/global-error.tsx` reports root render errors. The Sentry user is the Clerk id only: `components/sentry-user.tsx` (rendered by `Providers`) sets `{ id }` in the browser and clears it on sign-out, and `proxy.ts` and `(app)/layout.tsx` set it for the request's server events. `next.config.ts` exposes `VERCEL_ENV` / `VERCEL_GIT_COMMIT_SHA` as `NEXT_PUBLIC_VERCEL_ENV` / `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` for the browser and wraps the config in `withSentryConfig`: with `SENTRY_AUTH_TOKEN` the build uploads its source maps to `SENTRY_ORG` / `SENTRY_PROJECT` for the release `VERCEL_GIT_COMMIT_SHA` and deletes them from the output; without it the upload is skipped and the build still succeeds. `apps/web/turbo.json` hashes `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` into the build, since both are inlined.

### apps/site — Next.js marketing site

The public marketing site, meant for fitmeproject.com (which doesn't serve it yet: see Hosting below). No auth, no Supabase. Tailwind v4 via `@tailwindcss/postcss` (CSS-first config in `app/globals.css`, typography plugin loaded with `@plugin`) with shadcn-style `components/ui/` primitives. Dark only, on `@fitme/design-tokens`: `app/globals.css` imports the tokens and adds only the site's `display-1` / `display-2` sizes (hero and page headings), the Nunito Sans font roles mapped to the `next/font` variable, and `prose-fitme` (the typography plugin's colors from the tokens; `components/prose.tsx` for long-form copy).

- `app/` — landing page, `blog/`, `support/`, `privacy-policy/`, `terms/`, plus `sitemap.ts`, `robots.txt` and OG/Twitter images.
- `blog/*.mdx` — posts with `title`, `summary`, `publishedAt` frontmatter, parsed by `app/blog/utils.ts` and rendered with `next-mdx-remote-client`. Cover image: `public/blog/<publishedAt>.png`.
- `public/.well-known/apple-app-site-association` — universal links for the iOS app (served as JSON via `next.config.ts` headers).
- Analytics: PostHog (proxied through `/ingest` rewrites), Google Tag Manager, Vercel Analytics and Speed Insights. Client init lives in `instrumentation-client.ts`.
- Hosting: the `fitme-site` Vercel project builds it, but it has no domain. fitmeproject.com (DNS on Vercel, checked 2026-10-21) points at superapp (`domains.superapp.now`), which serves a separate Vite-built site from DigitalOcean App Platform, not this app: nothing in this repo deploys there. Until the domain moves to `fitme-site`, this app's Sentry setup only reports from `fitme-site` deployments (previews and its `*.vercel.app` production URL).
- Errors and page loads: `@sentry/nextjs`, browser only, reporting to the `fitme-site` Sentry project. `instrumentation-client.ts` initialises it after PostHog from `@fitme/observability`'s root export (`resolveObservabilityConfig` with `NEXT_PUBLIC_SENTRY_DSN`, so no DSN → no init, nothing sent; `scrubEvent` as `beforeSend` / `beforeSendTransaction`), with `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` inlined by `next.config.ts` as `NEXT_PUBLIC_VERCEL_ENV` / `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` (hashed into the build by `apps/site/turbo.json`). Page loads and navigations are traced at the shared rates (`traceLifecycle: "static"`, so the scrubber sees each transaction); no trace headers on any request (the site calls no backend of ours), no Session Replay, and no web vitals (Speed Insights has them): `browserTracingIntegration` ignores CLS, LCP and INP, and `beforeSendTransaction` drops every transaction's `measurements` (TTFB, FCP and the rest too). `dataCollection` is locked down like the Node setup's: no cookies, headers, bodies, URL query strings or user info. `app/global-error.tsx` reports root render errors, then renders Next's own error page. There is no `instrumentation.ts`: no server SDK, so nothing server-side is reported or traced. `next.config.ts` wraps the config in `withSentryConfig` (from `@sentry/nextjs/config` in SDK 11): with `SENTRY_AUTH_TOKEN` (`SENTRY_ORG` / `SENTRY_PROJECT`) it uploads the browser source maps for the release `VERCEL_GIT_COMMIT_SHA` and deletes them from the output; without it the upload is skipped, and a failed upload is only logged. The site imports `@sentry/nextjs` itself (the Next SDK has to hook the build and the client entry), but takes every rule from `@fitme/observability`.

### apps/api — REST API

Hono app served with `@hono/node-server`, bundled with tsdown. Reads domain data from `@fitme/core`. Reports to the `fitme-api` Sentry project through `@fitme/observability`, with the same entry, build setup and `turbo.json` as `apps/webhooks`.

- `src/index.ts` — Node entrypoint, `PORT` env (default 3003).
- `src/app.ts` — the Vercel entry (`dist/app.js`): imports `hono`, calls `initObservability({ service: "api" })`, then loads `create-app` with a dynamic `import()` and default-exports `createApp()` (see `apps/webhooks`).
- `src/create-app.ts` — `createApp({ reportError })` (no argument = `@fitme/observability/node`'s `reportError`): `observeHono(app)` first (request spans), logger, CORS, `/health`, `/v1`, JSON `notFound`/`onError` handlers returning `{ error: { code, message } }`; `onError` reports every unhandled error before the 500, an `HTTPException` (and any 4xx a route answers itself) goes out unreported.
- `src/routes/v1.ts` — versioned router; each resource lives in its own file under `src/routes/` and is mounted here. Input validation uses `@hono/zod-validator`.
- `src/routes/client-config.ts` — public, unauthenticated `GET /v1/client-config`: `{ data: { minimumVersion: { ios, android } } }`, the oldest supported mobile app version per platform from `MIN_APP_VERSION_IOS` / `MIN_APP_VERSION_ANDROID` (`x.y.z`; unset or malformed → `null`, no minimum). Cached for 5 minutes (`Cache-Control: public, max-age=300, s-maxage=300`).
- `src/routes/coach-models.ts` — public, unauthenticated `GET /v1/coach/models`: `{ data: { models: [{ id, label, description }], defaultId } }`, straight from `coachModels` and `defaultCoachModelId` in `@fitme/core` (list order; no other fields per model), so it always matches what the Coach accepts. No auth: the list isn't secret, the Coach channel does the gating. Cached for 5 minutes like `client-config`.
- Tests (`src/__tests__/`, vitest) drive `createApp` through `app.request`, with a fake `reportError` where what gets reported matters (`app.test.ts`), so they need no Sentry.
- `tsdown.config.ts` — source maps for the Vercel build, uploaded for the release `VERCEL_GIT_COMMIT_SHA` with `SENTRY_AUTH_TOKEN` and skipped without it, exactly as in `apps/webhooks`; `apps/api/turbo.json` hashes `VERCEL_GIT_COMMIT_SHA` into the build.
- Deployed to Vercel (project `fitme-api`, region `cle1` in `vercel.json`) at https://api.fitmeproject.com.

### apps/webhooks — webhooks app

Hono app served with `@hono/node-server`, bundled with tsdown (same setup as `apps/api`), that receives every third-party webhook. It reaches Postgres only through `withService` from `@fitme/db` and runs business logic from `@fitme/services`.

- `src/app.ts` — the Vercel entry (`dist/app.js`): imports `hono` (Vercel's Hono preset requires it), calls `initObservability({ service: "webhooks" })`, then loads `create-app` with a dynamic `import()` so `pg` and the rest load after observability has started and get instrumented (see `packages/observability`), and default-exports `createApp()`.
- `src/create-app.ts` — `createApp({ clerk, reportError })` (no argument = the real dependencies): `observeHono(app)` first (request spans), logger, public `/health`, one route per sender, and the same JSON `notFound`/`onError` handlers as `apps/api` (`{ error: { code, message } }`); `onError` reports every unhandled error before the 500, an `HTTPException` answers its status unreported. `reportError` is `@fitme/observability/node`'s, shared by the routes and `onError`.
- `src/routes/clerk.ts` — `POST /clerk`, `clerkRoutes({ deleteCoachConversations, deleteUserData, reportError, signingSecret })`: verifies the Svix signature with `verifyWebhook` from `@clerk/backend` on the raw request before anything reads the body (401 otherwise; an unset `CLERK_WEBHOOK_SIGNING_SECRET` answers a reported 500 so Clerk retries). `user.deleted` runs `deleteUserData` through `withService`, then (once that has committed) `deleteCoachConversations`; a failure of either is reported and answers 500 so Clerk retries. Other events answer 200. No `svix-id` dedupe: both steps are idempotent; a webhook that isn't must dedupe on `svix-id`.
- `src/coach.ts` — `deleteCoachConversations({ listSessionIds, resetSession })`: lists the User's recorded Coach session ids (`listCoachSessionIds` in `withService`: the id is retired by then) and resets each (five at a time); any failed reset fails the call (an `AggregateError`, first failure as its `cause`). The `coach_sessions` rows stay as tombstones (see `packages/services`). No recorded sessions → no Coach call at all. `coachSessionResetter({ coachUrl, secret })` posts `COACH_URL/eve/v1/session/:id/reset` with `Bearer COACH_RESET_SECRET`; eve answers `reset`, or `no_active_session` for one already reset, expired or unknown, so a retry is harmless; anything else (or unset `COACH_URL` / `COACH_RESET_SECRET`) throws.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3004).
- Tests (`src/__tests__/`, vitest) drive `createApp` through `app.request` with payloads signed by a test secret (`standardwebhooks`), a fake `reportError` and fake dependencies, so they need no database or Sentry.
- `tsdown.config.ts` — the Vercel build (`dist/app.js`) emits source maps and runs `sentryRollupPlugin` from `@sentry/node/rollup`: with `SENTRY_AUTH_TOKEN` it uploads them to `SENTRY_ORG` / `SENTRY_PROJECT` for the release `VERCEL_GIT_COMMIT_SHA` and deletes the `.map` files; without it (local, CI) it injects debug ids, keeps the maps and skips the upload, and the build still succeeds. A failed upload is logged and never fails the build. `apps/webhooks/turbo.json` hashes `VERCEL_GIT_COMMIT_SHA` into the build, so a commit never replays another commit's `dist/` (and skips its upload).
- Deployed to Vercel as its own Pro project, region `cle1` (`vercel.json`), reporting to the `fitme-webhooks` Sentry project. `FITME_DATABASE_URL` carries `application_name=webhooks`. Its `/clerk` endpoint is registered for `user.deleted` on both Clerk instances, each with its own signing secret in the matching Vercel environment.

### apps/exercises — Exercise Library API

Hono app built on `@hono/zod-openapi` (zod 4), served with `@hono/node-server` and bundled with tsdown (same setup as `apps/webhooks`), that serves the Exercise Library (ADR 0007, ADR 0008; the spec is the Linear project "Exercise Library service"). The content lives in the private `kprovorov/fitme-exercises` repo, which publishes it as a `library.json` bundle; the build bakes the bundle in, so nothing is read from disk, a database or the network at runtime: the deployment is the data. The monorepo is going public: never commit real Exercise content here, only the made-up fixture.

- `src/app.ts` — the Vercel entry (`dist/app.js`), the `apps/webhooks` pattern: imports `"hono"` (Vercel's Hono preset requires it), calls `initObservability({ service: "exercises" })`, then loads `create-app`, the generated library and the rate limiter with dynamic `import()`s so they load after observability has started, and default-exports `createApp` with the real env, the generated library and `@fitme/observability/node`'s `identifyUser` and `reportError`.
- `src/create-app.ts` — `createApp({ auth, identifyUser, library, rateLimiter, reportError })`: `observeHono(app)` first (request spans), logger, CORS (`origin: "*"`, before auth, so preflights answer without a token and every response is readable cross-origin; ADR 0007), public `/health`, then `requireCaller` on every other route (unknown ones included), `identifyUser(sub)` for a User (the Sentry user is the Clerk id only; a server caller sets none), `rateLimitUsers`, `deviceCache` on `/exercises/*`, the routes, and the same JSON `notFound`/`onError` handlers as `apps/api` (`{ error: { code, message } }`).
- `src/routes/exercises.ts` — `GET /exercises`: alphabetical by name (ties by slug), `search` (case-insensitive substring of the name, trimmed, `%`/`_` literal, at most 100 characters), `muscle_group`, `limit` (1–50, default 20), `offset` (default 0) → `{ data: ExerciseSummary[], total, hasMore }` (an offset past the end is an empty page). With `slugs=a,b,c` (at most 40, repeats answered once; not combined with the list parameters) it's a batch lookup → `{ data, missing }` in asked order, no 404. `GET /exercises/:slug` → one `Exercise`, or 404 `not_found`. Invalid query → 400 `invalid_request`.
- `src/schemas.ts` — every response from one field definition (`summaryFields`): `ExerciseSummary` (`slug`, `name`, `muscle_groups`, `thumbnail_url`, `video_url`) and `Exercise` (plus `description`, `instructions`, markdown). Add a field there. `MuscleGroup` is `z.enum(muscleGroups)` from `@fitme/core` (core stays zod-free), the only list in the app.
- `src/auth.ts` — `requireCaller`: `Authorization: Bearer` is first compared (as sha256 digests, constant time) with `EXERCISES_COACH_SECRET` and `EXERCISES_MCP_SECRET` (unset or under 32 characters accepts nothing) → a server caller; otherwise it must be a Clerk session token (with a `sid`) verified networkless against `CLERK_JWT_KEY_PRODUCTION` or `CLERK_JWT_KEY_DEVELOPMENT`, either one → the User (`sub`). Anything else → 401 `unauthorized`. No Pro gate: the Exercise Library is free content.
- `src/rate-limit.ts` — `rateLimitUsers`, after `requireCaller` on every route: each User (Clerk `sub`) gets 120 requests per minute (a fixed window), server callers aren't counted. Over the limit → 429 `rate_limited` with `Retry-After` (seconds), before anything is served (a 304 counts too). The `RateLimiter` comes through `createApp`: `rateLimiterFromEnv` picks Upstash Redis (`UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`; no client retries, each call aborted after 1 s so a request served uncounted stays uncounted, and Upstash's Rate Limit Analytics on, its write left to `waitUntil`), outside production without it the in-memory `memoryRateLimiter` (per process), and in production without it throws, so the deployment fails at startup. A limiter that throws or takes over 1 s serves the request uncounted (fail open) and is reported. The per-IP backstop is a Vercel Firewall rule, configured by hand.
- Errors and traces go through `@fitme/observability` (no Sentry code of its own): `reportError` is injected through `createApp`, like `apps/webhooks`'; `onError` reports every unhandled error, then answers the JSON 500, and `rateLimitUsers` reports a failing limiter. Reporting to the `fitme-exercises` Sentry project (`SENTRY_DSN`; unset → logs only, nothing sent).
- `tsdown.config.ts` — the Vercel build (`dist/app.js`) emits source maps and runs `sentryRollupPlugin` from `@sentry/node/rollup`, as `apps/webhooks`' does: with `SENTRY_AUTH_TOKEN` it uploads them for the release `VERCEL_GIT_COMMIT_SHA` and deletes the `.map` files; without it it skips the upload and the build still succeeds; a failed upload is only logged. The `build` is uncached anyway (see `src/generate.ts`), so it needs no `VERCEL_GIT_COMMIT_SHA` in its turbo hash.
- `src/cache.ts` — `deviceCache`: a 200 under `/exercises/*` gets `Cache-Control: private, max-age=3600` and the library hash as its `ETag`; a matching `If-None-Match` (weak comparison, or `*`) answers 304 with no body. Runs after auth, so a 304 only goes to a caller; errors stay uncacheable.
- `src/bundle.ts` — the zod schema of `library.json` version 1, the contract with `fitme-exercises`: `{ version: 1, exercises: [{ slug, muscle_groups, locales: { en: { name, description, instructions } }, thumbnail: { oid, extension }, video: { oid, extension } }] }`. Strict: an unknown field, a wrong `version`, an invalid or repeated slug, an unknown or repeated muscle group, a bad oid (sha256 hex) or an extension other than `jpg`/`png`/`webp` (thumbnail) or `mp4` (video) fails the build. No URLs: a media object's path is `<slug>/<oid>.<ext>` on both sides. A new muscle group goes into `muscleGroups` in `@fitme/core` first, then into the content.
- `src/served-library.ts` — `serveLibrary(bundle, supabaseUrl)`: every Exercise as its response object, sorted by name, media resolved on the `exercise-media` bucket (`thumbnail_url` through the image transformation `render` endpoint, so clients append `width`/`height`; `video_url` the public object URL), the lowercased name index search runs on, and the sha256 of it all (the `ETag`).
- `src/generate.ts` (`pnpm generate`) — gets the bundle, validates it (`src/build/library-module.ts`; every problem names the bundle and the field, and exits 1) and writes the git-ignored `src/generated/library.ts`. Which bundle: a production build (`VERCEL_ENV=production`) fetches `library.json` from the private Vercel Blob store (`get("library.json", { access: "private", useCache: false })` from `@vercel/blob`, uncached so it gets the version just published), authenticated through Vercel OIDC (`VERCEL_OIDC_TOKEN` plus `BLOB_STORE_ID`, both set by Vercel once the store is connected; no Blob token on the project). If OIDC isn't available during the build, the fallback is a `BLOB_READ_WRITE_TOKEN` on the project (Production, Sensitive), which the SDK picks up by itself. A missing store, a missing blob, a failed fetch or an invalid bundle fails the build: production never falls back to the fixture. Every other build reads the bundle at `LIBRARY_BUNDLE` (absolute or relative to `apps/exercises`; default the committed fixture `fixtures/library.json`, made-up Exercises only) and never calls Blob (a preview build would too, but no previews deploy). The build log names the bundle, its Exercise count and the library hash (the `ETag`), so a deployment's content can be identified from it. `SUPABASE_URL` must be the project's https origin; it's required on Vercel (`VERCEL` set), and unset anywhere else the media URLs point at a placeholder project. `build`, `dev`, `typecheck` and `test` all run `generate` first (in their scripts, so with or without turbo). Its turbo `build` is never cached and passes the Blob variables through (`apps/exercises/turbo.json`): turbo would hash the `LIBRARY_BUNDLE` path, not the bundle, and can't see Blob at all, so it would replay a stale library.
- `src/openapi.ts` (`pnpm openapi`) — writes the committed `openapi.json` from the route definitions (not served). No version prefix, so changes are additive only. The Exercise Library API workflow (`.github/workflows/exercises-api.yml`, pull requests touching `apps/exercises`, `packages/core` or `.github/oasdiff`) fails when `openapi.json` is stale, runs `scripts/check-api-breaking.sh` (oasdiff against the base branch: every removal fails, errors and warnings alike, `.github/oasdiff/severity-levels.txt` raising the info-level ones; the one allowed response enum addition is a new muscle group in `muscle_groups`), builds the app and checks `dist/app.js` imports `hono`. **Deliberate removal:** only after the minimum version gate has cut off every build that reads the field; in the removal PR copy each line the check prints (without the `[check id]`) into `.github/oasdiff/allowed-breaking-changes.txt`, say which minimum app version made it safe, and empty the file again once the removal is on `main`. Never loosen the check another way.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3006). `dev` and `generate` load `apps/exercises/.env` if it exists.
- Tests (`src/app.test.ts`, `src/build/library-module.test.ts`, vitest) drive `createApp` through `app.request` with fixture Exercises, Clerk tokens signed by test RSA keys (`src/test/clerk.ts`), test secrets, a fake reporter and fake limiters (the in-memory one on a fake clock), and the bundle validation on fixture bundles (valid, the committed fixture, unknown muscle group, wrong `version`, invalid slug, …).
- `vercel.json` — region `cle1`, `outputDirectory: dist`, `git.deploymentEnabled` `{ "**": false, "main": true }` (Vercel deploys a branch when any matching rule is true, and `**` also matches branch names with `/`), so only `main` deploys and there are no previews. No `ignoreCommand`: see CI/CD. The Vercel project, domain (`exercises.fitmeproject.com`) and media bucket are FIT-179.

### apps/coach — the Coach (EVE)

The Coach as an [EVE](https://www.npmjs.com/package/eve) agent (ADR 0005) whose model calls go through Vercel AI Gateway (ADR 0006), which replaced the `ai-agent` edge function (since removed). EVE is in preview: it is pinned to an exact version; read its changelog on every bump. Its docs ship in the package (`node_modules/eve/docs/`, start at `README.md`; the `eve` agent skill points there). EVE is filesystem-first: every file under `agent/` is discovered by its path, so put helpers in `agent/lib/` and tests in `test/`. Needs Node 24: `engines.node` is `24.x`, so Vercel never moves it to a new major on its own.

- `agent/agent.ts` — `defaultTools: false` (no shell, file or web tools; `eve info --json` lists what the model gets), Conversations end 30 days after they start (`limits.sessionTimeoutMs`; an ended run's data is kept for the plan's default period through `experimental.workflow.retention: "default"`: without it, eve 0.80+ deletes a private or unknown-audience session's run data as soon as its run ends outside development, and account deletion relies on a reset session's stream outliving the reset), and the model is resolved on every `step.started` by `coachModelSelection` (`agent/lib/models.ts`): the client sends `clientContext: { model }` per turn, eve hands it to the resolver as a `context.instruction` user message (`Client context:` + JSON), and the id must be in `coachModels` from `@fitme/core`, the only list (none → `defaultCoachModelId`; anything else, pre-Gateway ids like `gpt-5.5` included, fails the turn). Coach model ids are the Gateway's own (`openai/gpt-5.5`, `anthropic/claude-haiku-4.5`), so the selection returns the id and eve routes the call through AI Gateway (credits; Vercel OIDC deployed, `AI_GATEWAY_API_KEY` locally), with `providerOptions.gateway.order` listing the hosts of that same model (OpenAI → Azure → Bedrock, Anthropic → Bedrock → Vertex) so a failed call moves to another host, never another model. No `promptCacheKey` (OpenAI caches automatically); eve sets the Gateway `sessionId` per Conversation itself.
- `agent/instructions.md` — the system prompt, carried over from `ai-agent`.
- `agent/channels/eve.ts` — the eve HTTP channel (`/eve/v1/session…`) behind `accountDeletionReset()` (`agent/lib/reset-auth.ts`) then `clerkSession()` (`agent/lib/clerk-auth.ts`), then `evalRunner()` (`agent/lib/eval-runner.ts`), which admits only on the dev server a local `eve eval` boots (`EVE_EVALUATION` and `EVE_DEV` set, never on Vercel): eve's `local-dev` principal with `allowToolStubs`, never a Clerk User, so tools refuse to act for it, and `admitTurn` lets its turns run without recording the session. `accountDeletionReset` accepts `Bearer COACH_RESET_SECRET` (compared in constant time; unset or under 32 characters accepts nothing) as the `service` principal `account-deletion` on `POST /eve/v1/session/:id/reset` only, and answers 403 for it anywhere else; any other bearer moves on to `clerkSession`: a Clerk session token verified networkless against `CLERK_JWT_KEY`; its `sub` becomes the session principal (`authenticator: "clerk"`). Missing or bad token → 401; missing key → 500. Then the Pro check (every route, before the session claim): `createProCheck` (`agent/lib/pro-access.ts`) asks RevenueCat's v1 REST API (`GET /v1/subscribers/:id` with `REVENUECAT_SECRET_KEY`) whether the caller's Clerk id (the id `auth-sync` identifies to RevenueCat) has the active `proEntitlement` ("Fitme Pro", from `@fitme/core`) (lifetime or within its billing grace period counts), caching each answer per User for 5 minutes in the instance (a Pro answer no longer than the entitlement lasts; failures aren't cached). Not Pro → 403 `{ ok: false, code: "coach_pro_required" }` (the app's paywall); RevenueCat failing or taking over 5 s, an unreadable answer or a missing key → reported 503 `coach_pro_check_unavailable`, never let through. Both codes are `coachErrorCodes` in `@fitme/core`, for the app to match on. EVE's route auth has no session ownership, so any route addressing a session (`/eve/v1/session/:id…`: messages, stream, cancel, clear, compact, reset) claims it through `claimSession` (`agent/lib/claim-session.ts`: `recordCoachSession` as the caller in `asUser`, a no-op if it's recorded already, then `getCoachSessionOwner` in `withService`) and answers 403 unless it is recorded for the caller. EVE gives the channel no session id at creation, so the creator's first request addressing it records it; a failed recording fails the request, never lets anyone in. No `localDev()`, so local requests need a token too. Clerk tokens never go past the channel. `/eve/v1/health` is public.
- `agent/lib/owner.ts` — the Conversation owner is the session's `auth.initiator` (the verified caller who started it): the only User id tools act as. Route auth doesn't check session ownership, so `agent/hooks/conversation.ts` cancels a `turn.started` whose caller isn't the owner, and claims the session for the owner (the same `claimSession`, every turn) before the model runs; a session recorded for someone else, or a failed recording, is reported and cancels the turn (account deletion needs every session id to reset it).
- `agent/hooks/turn-limits.ts` — caps per turn (`agent/lib/turn-limits.ts`): 20 model steps and $1.00 of model cost (the `costUsd` AI Gateway reports on each `step.completed`, summed per turn; ADR 0006). The `step.started` past either cap cancels the turn; the last call can overshoot the budget by its own cost, and EVE's retries of a step (up to 4, same `stepIndex`, state restored) aren't counted. A finished step that reports no cost fails closed: it is reported to Sentry and the next `step.started` cancels the turn. eve's own `limits.max*PerSession` (`maxTokenCostUsdPerSession` included) are per session and prompt the user to continue, so they aren't used.
- `agent/hooks/failures.ts` — `step.failed`, `turn.failed` and `session.failed` are reported with their session and turn ids. Every report in the Coach (those, a missing step cost, the owner and session-claim guards, the Pro check) goes through `reportError` from `@fitme/observability/node` to the `fitme-coach` Sentry project, with `environment` and the commit as `release`; `agent/instrumentation/sentry.ts` starts it once at server startup (eve's provider `setup`) with `tracing: false`, so the Sentry SDK neither traces nor sends trace headers. `SENTRY_DSN` unset → logs only.
- Traces (`agent/instrumentation/`): eve's own OpenTelemetry. `otel.ts` sets `deployment.environment` from `VERCEL_ENV` and the process-wide `coachTracePolicy` (`agent/lib/trace-export.ts`): no Conversation content (prompts, tool arguments, answers, tool results) in any span outside local development, whatever the audience, so Vercel Agent Runs gets metadata only too. `sentry-traces.ts` is the Sentry destination: `otelIntegration()` with `OTLPHttpProtoTraceExporter` (`@vercel/otel`) to `SENTRY_OTLP_TRACES_URL`, authenticated with the DSN's public key (`x-sentry-auth`); without that URL or `SENTRY_DSN` (local dev, evals, tests) it is `disableInstrumentation()` and nothing is exported. Its `sentryExportPolicy` redacts every span's inputs and outputs, then keeps only an allowlist of metadata attributes (turn and step structure, model ids, `*.usage.*` tokens and cost, tool names, timings, `error.type`): an attribute a later eve or AI SDK adds stays out until it's listed there.
- Source maps: `nitro.config.ts` (`sourcemap: true`, read by the nitro build `eve build` runs) makes the server bundle emit them, and `scripts/upload-source-maps.ts` (run by `build` after `eve build`) injects debug ids and uploads them with `sentry-cli` for the release `VERCEL_GIT_COMMIT_SHA` (`SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT`), then deletes them; without the token it skips, and a failed upload is logged, never fails the build. Authored code maps to eve's compiled module map (readable, unminified JS), not to the `.ts` files: eve compiles it without source maps.
- `agent/tools/` — one file per tool, the filename is the tool name, ported 1:1 from `ai-agent` (names, inputs, descriptions). Each is a thin wrapper: `asUser(owner, (tx) => service(tx, owner, …))` with `owner` from `requireConversationOwner(ctx.session.auth)`; tool inputs never carry a User id (their zod schemas strip unknown keys). So far: `get_user_profile` → `getProfile`, `activate_plan` → `activatePlan`, `update_user_profile` → `updateProfile`, `get_active_plan` → `getActivePlan` (`{ error: "No active plan found" }` without one), `get_plans` → `listPlans`, `get_workouts_history` → `listWorkoutHistory` (`limit` 1–20, default 10), `search_exercises` → the Exercise Library API's `list` (no database; first 8 matches as `{ exercise_slug, name, muscle_groups }`; `muscle_group` one of `muscleGroups`), the Plan edits `add_exercise_to_workout`, `remove_exercise_from_workout`, `replace_exercise_in_workout`, `add_set_to_exercise`, `remove_set_from_exercise` and `update_set_recommendations` → the matching `@fitme/services/workout-edits` function (row ids are uuids, Exercises are `exercise_slug` / `new_exercise_slug`; set targets and set counts have MCP's plan bounds, reps and weight from `@fitme/core/limits`, the rest in `agent/lib/workout-edits.ts`; an Exercise already at its set limit or a missing row is an `{ error }` result; a remove that finds nothing says it may already have been removed, since a re-run step repeats it; the two appends pass `requestKey(ctx, input)` from `agent/lib/request-key.ts`: a hash of the session, turn, the step's message count, the tool, its input and the call's position among identical calls of the same step execution (told apart by the `ctx.messages` array, which the AI SDK shares across one execution's tool calls and a re-run rebuilds), so a re-run step, which repeats the model call under new `callId`s, finds the rows the first run added, while two identical calls in one step still add two rows), and `display_workout_plan` (returns its input; the app renders every successful result as the plan card, so its schema is the app's contract and a refusal is a thrown tool error, never an `{ error }` result; writes nothing). Exercises (FIT-239; project "Exercises off Postgres", ADR 0010): tools refer to them by Exercise slug only, through the `@fitme/exercise-library` client (`agent/lib/exercise-library.ts`: `EXERCISES_URL` with `EXERCISES_COACH_SECRET`; tests swap in the fake). `agent/lib/exercises.ts` holds the two rules: `checkExerciseSlugs` runs one `lookup` before any `asUser` in every tool taking a slug (`add_exercise_to_workout`, `replace_exercise_in_workout`, `display_workout_plan`): an unknown slug, or a uuid-shaped one from an older Conversation, is an `{ error }` sending the model to `search_exercises`, and a library failure an `{ error }` asking to retry (reported); nothing is written either way. `withExerciseDetails` names the Exercises of `get_active_plan` and `get_workouts_history` (`name`, `muscle_groups` next to `exercise_slug`; the services' legacy joined `exercise` is dropped) through one `lookup` after the transaction; a slug the library doesn't know, or every slug when it fails (reported), gets a name made from the slug and no muscle groups, so reads always answer. Until the contract step `display_workout_plan` also returns each Exercise's legacy `exercise_id` (or `null`), looked up by slug in the `exercises` table (`legacyExerciseIdsBySlug` in `asUser`; a slug it doesn't know is reported): the plan card in installed v2.0.0 apps reads it and sends it to `create_plan`. Delete both at the contract step.
- `evals/` — `eve eval` evals (`*.eval.ts`, `evals.config.ts`): the common asks (show my plan, last week's sessions, find a chest exercise, propose a plan, a general question) against a real model, every read tool and `display_workout_plan` stubbed from `evals/fixtures.ts` per session (`t.session({ stubs: readToolStubs })`; Exercises by slug, as the tools show them). Local only: a remote `--url` target has no eval authenticator.
- `agent/sandbox.ts` — just-bash (in-process, nothing to build or pay for): eve prepares a sandbox even though no tool uses one.
- `eve build` bundles the source-only `@fitme/*` packages into `.output/` itself. `FITME_DATABASE_URL` carries `application_name=coach`.
- Tests (`test/`, vitest) call the pure functions and the tools' `execute` directly: channel auth through `routeAuth` with tokens signed by a test RSA key (Pro check faked), the Pro check with RevenueCat faked through an injected `fetch` and clock (cache window and timeout included), the eval runner's env gate, model selection, turn limits, the trace export policy (metadata kept, content dropped) and the Sentry OTLP config, the owner/turn guard, and each tool with `@fitme/db` and its service mocked (`test/tool-context.ts` fakes a session owned by a Clerk User).

### apps/mcp — MCP server

Stateless [Streamable HTTP](https://modelcontextprotocol.io) MCP server built on Hono + `@modelcontextprotocol/sdk`, served with `@hono/node-server`.

- `src/server.ts` — composition root: `createMcpServer({ context })` (`context` = the request's `ToolContext`, built by the HTTP layer from a verified Clerk User) registers the tool groups from `src/tools/` (`registerTool` with zod input schemas, `title`, and read-only/destructive/idempotent `annotations`).
- `src/tools/` — `catalog.ts` (catalog tools from `@fitme/core`: ping, muscle groups, plan options; they still need a token like every other tool), and user tools in `exercises.ts`, `plans.ts` (+ `plan-schemas.ts`), `sessions.ts`, `profile.ts`; page bounds in `limits.ts` (set bounds from `@fitme/core/limits`). `helpers.ts` holds `asJson`, `requireFound`, `withToolErrors` and `withServices` (`withToolErrors` plus the caller's services; a failure becomes an `isError` result: a `ToolError` (not found, not configured) shows its message unreported, anything else (a Postgres error, an unknown exception) goes to the context's `reportError` first (as is: `@fitme/observability/node`'s `reportError` strips a query failure's SQL, parameters and Postgres message) and shows the Postgres message, never the SQL, or a generic one). Invalid input is rejected by the SDK before the handler runs, so it's never reported either. Every write reads its result back in its own transaction, so no tool returns a `warning`. `exercise-library.ts` is how tools reach the Exercise Library (ADR 0010): `fromLibrary` (searches, `get_exercise`, write checks: a library failure is reported, then the `ToolError` "Exercise Library unavailable, try again."), `requireKnownSlugs` (one `lookup` before the services' transaction; unknown slugs are a `ToolError` naming them, unreported, and nothing is written) and `lookupForRead` / `namedPlan` / `namedSession` (after the transaction, the legacy joined `exercise` swapped for the slug's `name` and `muscle_groups`; an unknown slug, or the library failing (reported) or unconfigured, gets `exerciseNameFromSlug`'s name and no muscle groups, and the read still answers).
- `src/context.ts` — `createToolContext({ user, reportError, createServices?, createExerciseLibrary? })`: per-request `ToolContext` for a verified Clerk User, carrying the app's `reportError` for `withServices` and `getExerciseLibrary()`, the `@fitme/exercise-library` client (`src/exercise-library.ts`: `EXERCISES_URL` with `EXERCISES_MCP_SECRET` as the bearer; either unset is the "not configured" tool error, unreported). `getServices()` returns the `UserServices` (`src/services.ts`) built for `user.userId`, each method running one `@fitme/services` function inside `asUser(user.userId, …)`; every user tool runs on them via `withServices` and never passes a User id, and a missing `FITME_DATABASE_URL` is the "not configured" tool error.
- `src/auth.ts` — MCP authorization (OAuth 2.1) with Clerk as the authorization server: protected-resource metadata naming the Clerk instance (`protectedResourceHandlerClerk` from `@clerk/mcp-tools/hono`) and the middleware chain for `/`: `requireConfig` (500 when `CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY` or `FITME_DATABASE_URL` is missing; never serve without auth), `requireBearerToken` (`401` + `WWW-Authenticate: Bearer resource_metadata=…`), `@clerk/hono`'s `clerkMiddleware`, then `requireClerkUser` (`getAuth(c, { acceptsToken: "oauth_token" })`; a rejected token gets `401` `error="invalid_token"`). No audience check (Clerk OAuth tokens have no `aud`), no custom scopes, no dynamic client registration.
- `src/app.ts` — the Vercel entry (`dist/app.js`), as in `apps/webhooks`: imports `hono`, calls `initObservability({ service: "mcp" })`, then loads `create-app` with a dynamic `import()` (so `pg` gets instrumented) and default-exports `createDefaultApp()` (`createApp` with `@fitme/observability/node`'s `reportError`). `tsdown.config.ts` and `turbo.json` upload source maps the same way too (only with `SENTRY_AUTH_TOKEN`; a failed upload never fails the build).
- `src/create-app.ts` — `createApp({ reportError, createServices?, createExerciseLibrary?, identifyUser? })` builds the Hono app: `observeHono(app)` first (request spans); the MCP endpoint is the root `/` (all methods, initialize and `tools/list` included), behind the `auth.ts` chain, creating a fresh server per request through `streamableHttpHandler` (`@clerk/mcp-tools/hono`); only `/.well-known/oauth-protected-resource` (OAuth discovery) and `/health` (liveness) are public. After `requireClerkUser`, `identifyUser` (default: `@fitme/observability/node`'s) sets the request's Sentry user to the verified Clerk id only. A JSON `onError` (`{ error: { code, message } }`) reports every unhandled error before the 500; an `HTTPException` and the auth chain's 401s and config 500 answer unreported. Deployed at https://mcp.fitmeproject.com.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3002).
- Tests (`src/__tests__/`, vitest) drive `createMcpServer` through the SDK's `InMemoryTransport` + `Client` (`harness.ts`, `contextFor(services, reportError?, library?)` builds the `ToolContext`, the library defaulting to the in-memory fake over `BENCH` and `SQUAT`; `recordingReporter()` records what a tool reports), and the Hono app via `app.request` (`app.test.ts`, with `@clerk/hono` mocked so `getAuth` answers per test, and a recording `reportError` and `identifyUser`). Tools run on fake services (`connectWithServices` / `fakeServices`: an unfaked method fails the call) and the fake Exercise Library (`fakeLibrary`, `failWith` for an outage), never the network. `integration/` (separate vitest config, `test:integration`) runs the same tools against a real local stack as made-up Clerk-style `user_…` ids through `asUser` on the stack's pooler (the config reads its URL from `supabase status`, like `packages/services`; `FITME_DATABASE_URL` overrides), including a cross-user isolation suite that also calls the RPCs and table writes directly as the intruder, with the fake Exercise Library over `INTEGRATION_EXERCISES` (seeded slugs: until the contract step a slug write needs its slug in the legacy `exercises` table). `integration/clerk-oauth.test.ts` (helpers in `integration/clerk.ts`) runs the real OAuth flow headlessly against the Clerk development instance (Backend API test Users and a public OAuth application, sign-in token on a dev browser, consent POSTed to the Frontend API, PKCE through the MCP SDK's OAuth client, then user tools over HTTP) and is skipped without `CLERK_DEV_SECRET_KEY`. CI runs both in `.github/workflows/integration-tests.yml`.
- Exercises are Exercise slugs everywhere, in tool inputs (`exercise_slug` in the plan schemas, `exerciseSlug` for `get_exercise` / `get_exercise_history`) and outputs; no tool takes or shows an `exercise_id` (MCP clients fetch tool schemas every session, so it switched in one step). `list_exercises` and `get_exercise` read the Exercise Library API (`list`, `get`); a `list_exercises` page over the API's 50 is read in two requests.
- Plan writes go through `createPlan` / `updatePlan` from `@fitme/services/plans`, each one transaction. `update_plan` with `workouts` recreates every workout (new ids); a metadata-only update keeps them. Unknown Exercise slugs are rejected (`requireKnownSlugs`) before anything is written. `start_workout_session` and `finish_workout_session` run `startWorkoutSession` / `finishWorkoutSession` from `@fitme/services` (see there), each returning the session read in the same transaction.

### packages/core — `@fitme/core`

Platform-agnostic code shared by both apps: `models.ts` (Profile, Plan, Workout, Exercise, etc. plus enum arrays like `goals`, `muscleGroups`), `labels.ts`, `formatters.ts`, `names.ts` (`splitName`), `limits.ts` (`MAX_REPS`, `MAX_WEIGHT`, `MAX_WEIGHT_DECIMALS`: a set's bounds, shared by the mobile set inputs, MCP and the Coach), `types.ts` (pagination), `utils.ts` (`range`, `muscleGroupToName`, `handleSupabaseError`). ### packages/design-tokens — `@fitme/design-tokens`

The design tokens (ADR 0009): the only place a token value is defined. Source-only, like the other `@fitme/*` packages.

- `src/tokens.css` (export `@fitme/design-tokens/tokens.css`) — one Tailwind v4 `@theme` block and the text style `@utility`s, no `@import`s of its own: the 19 `--color-*` tokens (hex, 8-digit where there's alpha), the 11 HIG `--text-*` sizes with their `--line-height`s, `--spacing-xs/sm/md/lg`, Tailwind's default `--radius-*` scale plus `--radius-card` and `--radius-full` (9999px, so `rounded-full` resolves through it), the `--size-button-pill-*` / `--size-button-circle-*` Button heights measured from native iOS (FIT-204), and the font roles (`--font-nunito-sans-regular/semibold/bold`, `--font-ibm-plex-mono`, `--font-ibm-plex-mono-semibold`) with generic fallback families. Dark only: one value per token, no theme variants, no light values anywhere. After the block, the text styles (ADR 0009, FIT-200): `text-<style>` and `text-<style>-emphasized` for the 11 HIG styles, and `text-mono-<style>` / `text-mono-<style>-semibold` at `title-2`, `body`, `subhead`, `footnote` and `caption-1`, each one `@utility` setting the font role, weight, size, line height and letter spacing 0 (Tailwind also generates a size-only `text-<style>` from each `--text-*` token; the `@utility` adds the rest). The final tables are in `docs/agents/ui.md`.
- How apps use it: `apps/mobile/global.css` `@import`s it after `tailwindcss` and `uniwind`, then maps each font role to the bundled font files in its own small `@theme`; it defines no other token itself. uniwind follows the `@import` through Tailwind's compiler under Metro, in dev and release builds. The site and `apps/web/app/globals.css` import it the same way, mapping the font roles to their `next/font` fonts. Code that reads a token at runtime reads the `--color-*` variable (`useCSSVariable("--color-foreground")`); there are no bare `--background`-style variables.
- `src/index.ts` — the reader: `parseTokens(css)` turns the `@theme` block into a typed `Token[]` (`kind`, `name`, `value`, `variable`; an unknown prefix throws), `parseUtilities(css)` the `@utility` blocks into `Utility[]` (`name`, `declarations`), `readTokens()` / `readUtilities()` parse the package's own file. Used by its tests and the literal check.
- `src/literal-check.ts` (`pnpm literal-check`, run by Node's own type stripping, hence `allowImportingTsExtensions`) — the literal check (FIT-202): reads every `.tsx` under `apps/mobile`, `apps/web` and `apps/site` (not `__tests__/`, `*.test.tsx`, native projects or build output), parses it with TypeScript and fails on a hex color, `rgb()` / `rgba()` / `hsl()` / `hsla()`, or an arbitrary `text-[…]`, `leading-[…]`, `rounded-[…]` or spacing (`p-[…]`, `m-[…]`, `gap-[…]`, `space-x/y-[…]`) value in a string literal, printing `file:line:column  literal  hint` (the hint names the matching token when there is one, through `readTokens()`). Comments and JSX text never count; URL fragments and `href` / `id` / `testID` / `nativeID` values aren't colors; a CSS-variable reference with no fallback (`h-(--size-button-pill-default)`, `[var(--x)]`) isn't an arbitrary value. `ALLOWLIST` (a path and a reason each; empty so far) exempts a file, and an entry whose file has no literal left fails the check. CI runs it in the `checks` job of `.github/workflows/unit-tests.yml`. The rule and the allowlist policy are in `docs/agents/ui.md`.
- Tests (`src/__tests__/`, vitest) check the literal check on inline `.tsx` fixtures (`literal-check.test.ts`), and what a consumer sees: the 19 colors present and valid hex, the WCAG contrast floors (`input` and `ring` at least 3:1 on `background` and `card`, `ring` at least 3:1 against `input`, `destructive-foreground` on `destructive` and `destructive` on both surfaces at least 4.5:1), every HIG style's size and line height, the spacing, radius, size and font tokens, and the 32 text style utilities against the HIG table (font role, weight, size, line height, letter spacing), compiled through Tailwind (`tailwindcss` devDependency) as an app would.
- A PR that changes a value here also updates the matching Figma variable through the Figma MCP (`docs/agents/ui.md`).

### packages/observability — `@fitme/observability`

Errors and traces for every app (Sentry today; the vendor-neutral name leaves room for Axiom). Source-only, like `@fitme/db`. An app on it never imports `@sentry/*` for errors or traces: it goes through this package, which keeps the rules in one place. The one exception is a platform SDK that has to hook the app's build and entry points (`@sentry/react-native` in `apps/mobile`, `@sentry/nextjs` in `apps/site` and `apps/web`): the app calls it directly, with every rule it can take from the root export. So far `apps/webhooks`, `apps/api`, `apps/exercises`, `apps/mcp` and `apps/coach` (errors only: `initObservability({ service, tracing: false })` for an app tracing through its own OpenTelemetry pipeline) are on it, and `apps/mobile`, `apps/site` and `apps/web` read its root export (`apps/mobile` the scrubber and propagation targets; `apps/site` the config and scrubber; `apps/web` `sdkOptions`, every shared option).

- `.` (`src/index.ts`) — pure, no SDK import, safe for Node, React Native and Next: `scrubEvent` (`beforeSend` / `beforeSendTransaction`: drops `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers, cookies and request bodies, and reduces the user to `{ id }`, the Clerk id; a user without an id is dropped; a backstop for errors captured around `reportError`, such as Sentry's own handlers or console breadcrumbs: an event with an exception value mentioning `Failed query:` has every exception value replaced (the rest are its cause chain), and such a breadcrumb loses its message and data), `sanitizeError(error)` (a Drizzle `DrizzleQueryError` anywhere in the cause chain → a fresh `DatabaseQueryError`: only the SQLSTATE, also as the `sqlstate` tag, the original stack frames and no cause, so no SQL, parameter or Postgres message, which can echo input; anything else as is) with `isQueryError` (recognised by shape, `query` and `params` own properties, since the package can't depend on drizzle-orm), `tracePropagationTargets` (regexes: our services `api`, `app`, `coach`, `exercises`, `mcp`, `webhooks` on `fitmeproject.com`, localhost / 127.0.0.1, and same-origin relative paths; never a wildcard over `*.fitmeproject.com`, since Clerk answers on `clerk.fitmeproject.com`), `resolveObservabilityConfig({ dsn, env })` (`environment` = `VERCEL_ENV`, `development` without it; `release` = `VERCEL_GIT_COMMIT_SHA`; traces at 0.2 in production and 1.0 otherwise; no DSN → `enabled: false`, nothing sent). Each platform passes its own DSN variable. `sdkOptions(config)` turns the resolved config into the SDK options every platform starts with: the scrubber as `beforeSend` / `beforeSendTransaction`, the propagation targets, `traceLifecycle: "static"` (SDK 11 streams spans by default, which skips `beforeSendTransaction`) and `dataCollection` locked down (SDK 11's replacement for `sendDefaultPii: false`: no user info, cookies, bodies, credential headers, response headers, DB query data, gen-AI inputs/outputs or stack-frame variables).
- `./node` (`src/node.ts`) — `initObservability({ service, tracing? })`: called once at process startup, before the app is built; without `SENTRY_DSN` it does nothing (local runs, tests, CI). Otherwise it starts `@sentry/node` with `sdkOptions` and a `service` tag; `tracing: false` drops its spans and trace headers (for an app tracing through its own OpenTelemetry pipeline, the Coach). `reportError(error, tags?)` runs `sanitizeError` first, then logs, captures (tags merged with the `sqlstate` one) and flushes (2 s) before the response, since a serverless instance may freeze afterwards; before init it only logs. `identifyUser(userId)` sets the request's Sentry user to `{ id }` (a Clerk id from a verified token only; each request has its own scope). `observeHono(app)` (Sentry's `honoMiddleware`, registered first with `app.use`) gives a Hono app its request spans whatever order Hono was loaded in. On Vercel the SDK also keeps the function alive until each request's spans are flushed.
- `@sentry/node` is a runtime dependency here and must also be in each consuming app's own `dependencies` (the tsdown apps keep it external).
- **Bundling finding (FIT-217):** the SDK instruments libraries through module hooks it registers at `initObservability`, so it only sees modules loaded after that. A tsdown bundle hoists every external `import` to the top of the entry, so a statically imported `pg` loads before init and gets no spans (`[instrumentation:pg, pg-pool] not injected yet`). The Vercel entry (`src/app.ts`) therefore imports `hono`, calls `initObservability`, and only then `await import("./create-app.js")`; with that, `pg` / `pg-pool` spans appear under the request span. Request spans don't depend on load order (`observeHono`), and outgoing `fetch` spans (`http.client`, with trace headers to the propagation targets) come from Node's own diagnostics channels, so bundling doesn't affect them. A tsdown app moving onto the package copies the `apps/webhooks` entry, build setup and `turbo.json`.
- Tests (`src/__tests__/`, vitest) cover the root export: the scrubber (its `Failed query:` backstop included), `sanitizeError` on Drizzle-shaped errors, the SDK options, the propagation list (our services and localhost match; Clerk, RevenueCat, Supabase and look-alike hosts don't) and the config resolution (production, preview, no DSN, outside Vercel); `report-error.test.ts` checks what `reportError` hands a mocked `@sentry/node` and the console for a query failure.

### packages/exercise-library — `@fitme/exercise-library`

The one client for the Exercise Library API (`apps/exercises`), shared by the Coach, MCP and the mobile app (project "Exercises off Postgres"), plus an in-memory fake for their tests. Source-only, like the other `@fitme/*` packages, and `fetch`-only: nothing Node-specific, so it runs in Node and React Native (the query string is built by hand, since React Native's `URLSearchParams` is partial). No zod; its only dependency is `@fitme/core` (muscle groups), so a tsdown app needs nothing extra in its `dependencies`.

- `src/client.ts` — `createExerciseLibrary({ url, token, fetch?, timeoutMs? })`. `token` is an async getter asked once per request: a server secret (`EXERCISES_COACH_SECRET`, `EXERCISES_MCP_SECRET`) for the Coach and MCP, the User's Clerk session token for mobile; `null` / empty fails unauthorized without a request. `get(slug)` → one `Exercise` in full (`GET /exercises/:slug`), or `null` for a 404 or an empty slug (no request). `lookup(slugs)` → `{ data, missing }`: drops repeated slugs, splits the rest into requests of at most 40 (`MAX_LOOKUP_SLUGS`, the API's `?slugs=` limit), sent in parallel, and answers in asked order with every slug no Exercise has in `missing` (an empty slug or one with a comma is never sent, only answered missing); one failed chunk fails the lookup. `list({ search, muscleGroup, limit, offset })` → `{ data, total, hasMore }`, sending only the parameters given so the API's defaults apply.
- `src/errors.ts` — every failure is an `ExerciseLibraryError` with a `code` (match on it or the subclass): `ExerciseLibraryUnauthorizedError` (401, or no token), `ExerciseLibraryRateLimitedError` (429, `retryAfterSeconds` from `Retry-After`, 60 when unreadable), `ExerciseLibraryUnavailableError` (network failure, a throwing token getter, the 10 s timeout (`timeoutMs`), any other status, an unreadable or malformed answer (each answer is checked field by field, muscle groups only as strings so a new one never breaks an old client); `cause` kept) and `ExerciseLibraryInvalidRequestError` (400, the API's message).
- `src/types.ts` — `ExerciseSummary`, `Exercise`, `ExercisePage`, `ExerciseBatch` mirror `apps/exercises`' `src/schemas.ts` by hand (muscle groups typed from `@fitme/core`): a field added there is added here too. `ExerciseLibrary` is the interface both the client and the fake implement.
- `src/name.ts` — `exerciseNameFromSlug(slug)`: the readable name (`barbell-back-squat` → `Barbell back squat`) a consumer shows for an Exercise it can't resolve.
- `src/fake.ts` (export `@fitme/exercise-library/fake`) — `createFakeExerciseLibrary(exercises)`: the API's answers over those Exercises in memory (alphabetical by name, ties by slug; trimmed case-insensitive substring search, `%`/`_` literal; muscle group filter; paging with its defaults and bounds, an out-of-bounds parameter failing invalid request; lookup with `missing`, summaries only; `get` answers the Exercise in full, empty description and instructions for one given as a summary), and `failWith(error)` fails every call until `failWith(null)`. Consumers' tests use it, never the network.
- Tests (`src/__tests__/`, vitest) drive the client through a stubbed `fetch` answering like `apps/exercises` (`stub-api.ts`): chunking at 40, order, dedupe and `missing`, the bearer on every request, the error mapping; `fake.test.ts` checks the fake answers exactly what the client does over the same Exercises, and fails on demand.

### packages/db — `@fitme/db`

The only way backend apps reach Postgres (ADR 0003): Drizzle on node-postgres (`pg`, not postgres.js) through the Supavisor transaction pooler, as the shared `fitme` login. Source-only, like the other workspace packages.

- `src/schema.ts` + `src/relations.ts` — generated Drizzle schema (the `public` tables plus `private.retired_user_ids` as `retiredUserIdsInPrivate`); `src/index.ts` re-exports the tables, and the relations only feed the client so `tx.query` works. `schema:generate` runs `drizzle-kit pull` (`drizzle.config.ts`, direct superuser URL from `supabase status`) against the running local stack, renames the `private` schema object to `privateSchema`, sorts declarations by name and formats with Biome, so reruns against the same migrations are byte-identical. Never edit them by hand, and never run `drizzle-kit generate`/`migrate`/`push`: the Supabase SQL migrations own the schema (ADR 0004). After a migration, regenerate and commit both files with `database.types.ts`.
- `src/index.ts` — the two doors and the `Transaction` type (typed with the generated schema, so `tx.select().from(plans)` and `tx.query.plans.findMany(…)` are checked). `asUser(userId, fn)` opens a transaction, runs `SET LOCAL ROLE authenticated` and `set_config('request.jwt.claims', {sub, role: authenticated}, true)`, then `fn(tx)`, so RLS and `current_user_id()` apply; `userId` only ever comes from a verified token. `withService(fn)` does the same as `service_role` (bypasses RLS; only where that is the point, such as webhooks). Both also set `application_name` locally.
- `src/client.ts` — internal: the lazily created `pg.Pool` (small `max`, registered with `@vercel/functions`' `attachDatabasePool`) and Drizzle client, from `FITME_DATABASE_URL`, which must carry `?application_name=<app>`. Never export the raw client or pool, and never import this module from outside the package.
- A new runtime dependency here (or in `@fitme/services`) must also go in the `dependencies` of `apps/mcp` and `apps/webhooks`, or their tsdown build fails (see "Workspace packages are source-only").
- Never use a session-level `SET ROLE` or `set_config(…, false)` anywhere: the transaction pooler doesn't reset connections, so session state leaks to other requests.
- A transaction is one connection: await its queries one at a time, never `Promise.all` over the same `tx` (pg deprecates queueing on a busy client and pg@9 rejects it). The db, services and MCP integration suites run with `--throw-deprecation`, so such a query fails them.
- `fitme` (migration `20261014130000_fitme_login.sql`) is `LOGIN NOINHERIT` with no grants of its own, a member of `authenticated` and `service_role` only, so a query outside both doors fails with "permission denied". Its credential is service-role strength: server environments only. Local stacks set its development password in `supabase/roles.sql` (run by the CLI before the migrations, never pushed); hosted projects set theirs by hand. The pooler user is `fitme.pooler-dev` locally and `fitme.<project-ref>` on hosted projects.
- `integration/` (`test:integration`) runs the doors against the local stack's pooler (its port comes from `supabase status --output-format json`; `FITME_DATABASE_URL` overrides): identity and RLS, concurrent transactions with rollbacks never seeing another User's id, clean reused connections, and the login denied outside the doors. CI runs it in the integration-tests workflow.

### packages/services — `@fitme/services`

Business logic shared by the backend apps (ADR 0004), replacing the Postgres RPCs one by one. Source-only; each service is its own export (`@fitme/services/<name>`), no barrel.

- The rule: a service takes the `Transaction` from `asUser` or `withService` as its first argument and never opens its own connection. Any User id it acts on comes from a verified source (a verified token, or a signed webhook), never from request or tool input.
- Exercise slugs, expand step (FIT-238; project "Exercises off Postgres"): every Workout Exercise in `getPlan` / `getActivePlan` / `createPlan` / `updatePlan` and every Workout Session Exercise in `getWorkoutSession` / `listWorkoutHistory` / start and finish carries `exercise_slug` next to the joined `exercise` object. Writes take an Exercise as `exercise_slug` or `exercise_id` (`createPlan` / `updatePlan`), `exerciseSlug` or `exerciseId` (`addExerciseToWorkout`), `newExerciseSlug` or `newExerciseId` (`replaceExerciseInWorkout`), and send only that column: the `sync_exercise_slug` trigger fills in the other (see `packages/supabase`). `startWorkoutSession` copies both, like the RPC. Only uuids are checked (`UnknownExercisesError`); a slug isn't (ADR 0010: the tool layer checks it), and one the legacy `exercises` table doesn't know fails the write on NOT NULL (`replaceExerciseInWorkout` sends the looked-up uuid with the slug, since the trigger would keep the old uuid on an UPDATE). A replacement already in place is compared by slug. The contract step drops the uuid inputs, the checks and the joined `exercise`.
- `profile.ts` — `getProfile(tx, userId)`, run inside `asUser`: the User's Profile (gender, age, height, weight as numbers, `measurement_system`) plus its `units` (metric = cm/kg, us/uk = in/lbs; an unknown system counts as metric), or `null` without a Profile. Used by MCP's `get_profile` and the Coach's `get_user_profile`. `updateProfile(tx, userId, changes)` (the Coach's `update_user_profile`): changes only the given fields and returns `getProfile`'s result, or `null` with nothing changed without a Profile. A new `measurement_system` first converts every stored height and weight of the User as the `convert_measurement_system` RPC does (same factors and rounding, same rows: sessions are reached through their Workout), which the mobile app still calls, so change both together; the given height and weight are then written in the new system's units. It row-locks the Profile with a no-op UPDATE first, so a repeat or concurrent run sees the new system and never converts twice.
- `coach-sessions.ts` — `recordCoachSession(tx, userId, sessionId)` / `listCoachSessionIds(tx, userId)`, run inside `asUser`: the Coach's EVE session ids per User in `coach_sessions` (migration `20261014160000_coach_sessions.sql`; RLS: a User reads and inserts only their own rows, `service_role` may delete). Recording is idempotent (`on conflict do nothing`), and an id already recorded for another User stays theirs. `getCoachSessionOwner(tx, sessionId)` runs in `withService` (the channel's ownership check). `deleteUserData` locks this table but keeps the rows, and so does the Clerk webhook after resetting the sessions: each is the ACL for an EVE session whose stream outlives the reset (a missing row lets the first caller claim it), and the id in it is already retired, so it fails closed. The webhook lists them with `listCoachSessionIds` in `withService`, since the retired id no longer matches RLS.
- `exercises.ts` — run inside `asUser`: `listExercises(tx, { limit, offset, search?, muscleGroup? })` (alphabetical page plus `total`/`hasMore`; `search` is a case-insensitive substring with `%`/`_` literal; an offset past the end is an empty page), `getExercise(tx, exerciseId)` (every column, or `null`), `legacyExerciseIdsBySlug(tx, slugs)` (each known slug's legacy uuid, for the Coach's plan card until the contract step) and `getExerciseHistory(tx, userId, { exerciseSlug, limit })` (or `{ exerciseId, limit }`, which nothing calls any more; the User's Workout Session entries for the Exercise, newest first, only sets with a logged weight). Timestamps go through `jsonTimestamp` (`json-timestamp.ts`, `to_json`) so they keep PostgREST's ISO format. `getExerciseHistory` is MCP's `get_exercise_history` and `legacyExerciseIdsBySlug` the Coach's `display_workout_plan`; nothing calls `listExercises` or `getExercise` any more (MCP and the Coach search the Exercise Library API).
- `plans.ts` — run inside `asUser`, each filtering on the User id as well as RLS: `listPlans(tx, userId)` (live Plans newest first, each with Workout summaries in rotation order and Exercise counts; no pagination), `getPlan(tx, userId, planId)` (a live Plan with Workouts, Exercises and sets, each in `order`; `null` when missing, soft-deleted or foreign), `getActivePlan(tx, userId)` (the same for the User's active Plan, or `null` with none), `deletePlan(tx, userId, planId)` (soft delete: sets `deleted_at`, and the `deactivate_deleted_plan` trigger clears `is_active`; an already deleted Plan answers `alreadyDeleted: true`, a missing one `null`) and `activatePlan(tx, userId, planId)` (the `activate_plan` RPC in TypeScript, which stays for the mobile app, so change both together: the live Plan becomes active and every other Plan of the User inactive, so at most one is active; its summary, or `null` with nothing changed for a missing, soft-deleted or foreign Plan. Concurrent activations serialize on row locks and the last one wins), `createPlan(tx, userId, plan)` (the `create_plan` RPC: a Plan with its Workouts, Exercises and sets, each `order` from its array position, made the active Plan through `activatePlan`; the Plan in full) and `updatePlan(tx, userId, planId, changes)` (the `update_plan` RPC: only the given metadata fields change; with `workouts` every Workout is deleted and recreated, new ids, otherwise they and their ids stay; the Plan in full, or `null` with nothing changed for a missing, soft-deleted or foreign Plan; it locks the Plan row by its UPDATE before touching Workouts, like the RPC). Both throw `UnknownExercisesError` for unknown Exercise uuids before anything commits, and the RPCs stay for the mobile app, so change both together. Each read is one relational query (one statement, so one snapshot under READ COMMITTED: a concurrent `update_plan` never mixes old metadata with new Workouts). Output matches what PostgREST returned: snake_case keys, timestamps through `jsonTimestamp`, numeric weights as numbers. Used by MCP's `list_plans`, `get_plan`, `create_plan`, `update_plan`, `delete_plan` and `activate_plan`, and by the Coach's `activate_plan` (`activatePlan`), `get_plans` (`listPlans`) and `get_active_plan` (`getActivePlan`).
- `workout-edits.ts` — the Coach's Plan edits, run inside `asUser`, each filtering on the User id as well as RLS (another User's row is `null` / `false`, never edited): `addExerciseToWorkout(tx, userId, { workoutId, exerciseSlug | exerciseId, sets, requestKey? })` and `addSetToExercise(tx, userId, { workoutExerciseId, set, requestKey? })` append after the last row; `removeExerciseFromWorkout(tx, userId, workoutExerciseId)` and `removeSetFromExercise(tx, userId, setId)` renumber the remaining siblings from 1; `replaceExerciseInWorkout(tx, userId, { workoutExerciseId, newExerciseSlug | newExerciseId, sets })` keeps the row and its place and replaces its sets (when that Exercise with exactly those sets is already in place, it rewrites nothing, so set ids stay valid); `updateSetRecommendations(tx, userId, setId, changes)` changes only the given targets. Adding and replacing throw `UnknownExercisesError` for an unknown uuid before writing, and `addSetToExercise` throws `TooManySetsError` for a Workout Exercise already at `MAX_SETS_PER_EXERCISE` (20) sets. A replacement already in place is detected by comparing weights as Postgres rounds them to numeric(8,2). Each append, remove or replace first takes ROW EXCLUSIVE on `workouts`, `workout_exercises`, `workout_exercise_sets` (`deleteUserData`'s order, so it queues behind an account deletion instead of deadlocking with its cascade), then row-locks (`FOR NO KEY UPDATE`) the parent it appends to or renumbers (the Workout, or the Workout Exercise) and nothing above it, so concurrent edits keep `order` contiguous and can't deadlock with `updatePlan` / `finishWorkoutSession`. A Workout of a soft-deleted Plan is still edited, as `ai-agent` did. Retries: removing, replacing and updating are safe to repeat (a repeated remove answers not found); an append stores its `requestKey` in the row's `request_key` column (migration `20261015120000_plan_edit_request_keys.sql`, partial unique index), and a repeated call with the same key returns that row.
- `workout-sessions.ts` — run inside `asUser` (RLS scopes every query to the User): `listWorkoutSessions(tx, { limit, offset, status })` (newest first, with exercise/set/logged-set counts and `total`, counted in the page's own statement; an offset past the end is an empty page), `getWorkoutSession(tx, id)` (exercises and sets in order, or `null`; one statement, so a concurrent delete never yields a half-read session), `listWorkoutHistory(tx, { limit })` (the last `limit` finished sessions, last finished first, each in full like `getWorkoutSession`, in one statement; the Coach's `get_workouts_history`), `logSet(tx, { setId, repsCompleted, weightCompleted })` (`logged` / `not_found` / `session_finished`; one guarded UPDATE that only matches a set of an open session, so it takes no row lock that could deadlock with `deleteUserData`) `deleteWorkoutSession(tx, id)` (false when nothing matched), `startWorkoutSession(tx, workoutId)` and `finishWorkoutSession(tx, id)` (`started` / `finished` with the session, or `not_found`). Timestamps are rendered as PostgREST did (`to_json`), numerics as numbers, weights in the User's unit. Used by every MCP Workout Session tool.
- Start and finish reimplement the `start_workout_session` / `finish_workout_session` RPCs, which the mobile app still calls: until the RPCs are dropped, a behaviour change goes into both. Start returns the User's open session for the Workout (`resumed`) or inserts one `ON CONFLICT DO NOTHING` against the one-open-per-Workout index and copies the Workout's exercises and sets; a lost race resumes the winner's session, and a Workout of a soft-deleted Plan, another User's, or one whose open session belongs to another id is `not_found`. Finish keeps the RPC's lock order (`workout_sessions` `ROW EXCLUSIVE`, then the Plan row, then the session), claims only an open session, and moves its Workout to the end of the Plan, renumbering from 1 (`rotated`); a session whose Workout is gone is only finished (`rotated: false`), an already finished one is left alone (`alreadyFinished`).
- `workout_session_plan_changes(session_id, apply default false)` (migration `20261021120000_workout_session_plan_changes.sql`, which also indexes `workout_exercises.workout_id`, `workout_exercise_sets.workout_exercise_id` and `workout_session_exercise_sets.workout_session_exercise_id`; pgTAP `workout_session_plan_changes.test.sql`) has no services mirror on purpose (an ADR 0004 exception until the plan and workout-session RPCs move to `apps/api`; MCP and the Coach don't use it). For a finished Workout Session it works out the structural changes to its Workout, matching session Exercises to Workout Exercises by `order`: `replace_exercise`, `add_exercise`, `remove_exercise` and `add_sets` (sets created during the session: no `reps_recommended`, or past the Plan's set count, since replacing an Exercise in the app zeroes every set's targets), targets from the logged sets, nothing that was never logged, at most 20 sets per Workout Exercise. It returns `{ plan, workout, changes }` (each change with its Exercise(s) and the sets it saves as `{ reps, weight }`); `apply = true` also writes them in one transaction (replacements and added sets, then removals renumbering from 1, then added Exercises appended) and stamps `workout_sessions.plan_changes_applied_at`, after which both modes return no changes. An open session, a NULL `workout_id`, a soft-deleted Plan, a repeated `order` on either side (the app never writes one, but RLS allows it, and the slot join would grow with the product of the duplicates) or more than 50 Exercises (or an Exercise with more than 100 sets) on either side has none; another User's session is not found. Locks: ROW EXCLUSIVE on `workout_sessions`, `workouts`, `workout_exercises`, `workout_exercise_sets` (`deleteUserData`'s order), then the Plan row, the Workout row, its Workout Exercise rows (the Coach's set edits lock only those) and the session row (`finish_workout_session`'s order), in preview too, so concurrent applies serialize and the second is a no-op. Granted to `authenticated` only, for the mobile finish flow (FIT-232).
- `delete-user-data.ts` — `deleteUserData(tx, userId)`, run inside `withService` (it replaced the dropped `delete_user_data` SQL function): rejects an empty id, locks the User-owned tables and their children `IN SHARE ROW EXCLUSIVE MODE` (roots, children, then `coach_sessions`), throws `UserRekeyedError` (`code` `55000`) for an id the Clerk migration rekeyed away (a `private.retired_user_ids` row with `rekeyed_to`), retires the id in `private.retired_user_ids` (on conflict do nothing) and deletes the root rows (Workout Sessions, Plans, Profile), whose children cascade; Coach session ids stay (the webhook resets those sessions and keeps the rows as their ACL). A second run is a no-op. Its table list must track the schema. `service_role`'s grants for it come from migration `20261014140000_service_role_deletes_user_data.sql`.
- `integration/` (`test:integration`) runs the services against the local stack's pooler like `packages/db` (the URL helper is `@fitme/db/local-database-url`), as made-up Clerk-style `user_…` ids; CI runs it in the integration-tests workflow.

### packages/supabase — `@fitme/supabase`

- `supabase/` — Supabase CLI project: `config.toml`, `migrations/`, `seed.ts`, `sync.ts`. There are no Edge Functions: backend code lives in the Node apps (`apps/api`, `apps/coach`, `apps/mcp`, `apps/webhooks`).
- Account deletion: the app deletes the User in Clerk (`user.delete()`, needs Clerk's "allow users to delete their accounts") and signs out; Clerk then sends `user.deleted` to `apps/webhooks`' `POST /clerk` (registered on both Clerk instances), the only cleanup path, which runs `deleteUserData` from `@fitme/services` inside `withService`, then wipes the User's Coach Conversations: it resets every EVE session recorded for them through the Coach's reset route (`apps/webhooks/src/coach.ts`), so none can be resumed (a send answers `session_not_active`). EVE still keeps a reset session's stream for its retention period, so the `coach_sessions` rows stay as tombstones: owned by the retired id, they keep the channel answering 403 to everyone. A session whose first recording failed has no row, so deletion can't find it; the first Clerk caller who addresses it claims it (nobody but its creator has the id). A failed cleanup answers 500 so Clerk retries (about a day) and is reported to Sentry.
- Exercise slugs, expand step (migration `20261022120000_exercise_slugs_expand.sql`, FIT-235; project "Exercises off Postgres"): `workout_exercises` and `workout_session_exercises` carry `exercise_slug` (NOT NULL, no foreign key or format check, ADR 0010) beside `exercise_id`. The `sync_exercise_slug` trigger fills whichever one a write didn't send from `exercises` (an unknown one is rejected by NOT NULL); `exercise_slug`'s default `''` means "not sent" and `exercise_id`'s evaluates to NULL, so both are optional in the generated insert types. `create_plan` / `update_plan` take each Exercise as `exercise_id` or `exercise_slug`, and `start_workout_session` and `workout_session_plan_changes` copy both (the latter matches by slug). The contract step drops the trigger, the defaults and `exercise_id`.
- `data/` — exercise CSV + markdown descriptions/instructions used by the sync script. Legacy: the Exercise Library's content is moving to the private `fitme-exercises` repo, served by the Exercise Library API (to be `apps/exercises` in this monorepo, ADR 0008), keyed by Exercise slug, and the `exercises` table is to be dropped (ADR 0007)
- `src/database.types.ts` — generated Supabase types; `src/index.ts` exports `Database`, `Tables<>`, `TablesInsert<>`, `TablesUpdate<>`, `Enums<>`
- Run the Supabase CLI from this directory (or via `pnpm db <script>`).
- Auth: Supabase Auth itself is unused: no users, every sign-up off in `config.toml` (its `[auth]` section only keeps the signing keys and the Clerk trust), no email templates, local mail server off. Supabase trusts Clerk session tokens through third-party auth (`[auth.third_party.clerk]` in `config.toml` points local stacks at the Clerk development instance; the E2E workflow adds it to its preview branch through the Management API; production trusts the production instance via the dashboard, and `config.toml` has no `[remotes]` block so it is never deployed there). `scripts/check-clerk-trust.ts` (`clerk:check`) verifies it; CI runs it against the local stack (integration-tests workflow) and the E2E preview branch (e2e workflow) when the `CLERK_DEV_SECRET_KEY` secret is set.
- Local signing keys: `config.toml` sets `[auth] signing_keys_path` to `supabase/local-only-signing-keys.json` (committed, development only), holding the local stack's own ES256 signer. Never trust it on a hosted project.
- Identity (ADR 0001): every `user_id` column is `text` with no foreign key to `auth.users`. RLS policies and RPCs read the caller through `public.current_user_id()` (the JWT `sub` claim, only when the token's `role` claim is `authenticated`; NULL for role-less tokens such as Clerk OAuth access tokens, `anon` and any other role, and for ids in `private.retired_user_ids`); never use `auth.uid()`. Nothing cascades from Supabase Auth, so account deletion runs `deleteUserData` (`packages/services`), which retires the id so a still-valid token can't write it back (`current_user_id()` is NULL for it, and `reject_retired_user_id` triggers stop writes that bypass RLS). The one-shot Clerk migration (FIT-73) rekeyed every legacy UUID to its Clerk id and retired the UUID with a pointer (`rekeyed_to`); those rows stay, and `deleteUserData` refuses such an id (`UserRekeyedError`, SQLSTATE 55000). The migration script and its `rekey_user` function were removed after the 30-day rollback window (FIT-77, migration `20261018120000_drop_rekey_user.sql`).
- `supabase/tests/` — pgTAP suite (`pnpm db test:db`). `fitme_login.test.sql` checks the `fitme` login's attributes and memberships and fails when any `public` table has RLS disabled; every new table needs RLS. Table grants on `public` are explicit in the migrations (`20261016120000_explicit_table_grants.sql`, matching the hosted project), never left to Supabase's default privileges: `supabase/roles.sql` drops the default table grants on local stacks and CI, so a new table grants `anon` / `authenticated` / `service_role` what it needs in its own migration (or fails with "permission denied"), and `table_grants.test.sql`, which lists every `public` table, gets a line for it. Functions and sequences keep the defaults. Impersonate a User with `set local role authenticated` plus `request.jwt.claims` carrying a Clerk-style text `sub` and `"role": "authenticated"`; don't insert into `auth.users`.

## Key Patterns

**Data fetching (mobile)**: All queries/mutations use `react-query-kit` wrappers (`createQuery`, `createMutation`) around the Supabase JS client. Import from `~/hooks/queries/<entity>` or `~/hooks/mutations/<entity>`.

**Exercises (mobile)**: Plans, Workouts and Workout Sessions refer to Exercises by Exercise slug (`exercise_slug`; ADR 0007, project "Exercises off Postgres"): the Supabase reads select it and join no Exercise, and the writes (the plan and session RPCs, Workout Session Exercise inserts and replacements) send only `exercise_slug`, unchecked (ADR 0010; the `sync_exercise_slug` trigger fills the legacy `exercise_id`). Details come from the Exercise Library API through `hooks/queries/exercise-library.ts`: `useExercises(slugs)` (and `useExercise(slug)`) answer every slug as a `ShownExercise` at once, one react-query query per slug (`["exercise-summary", slug]`, stale after an hour, the API's `Cache-Control`), the slugs asked for in the same tick sharing one `lookup` (the client splits it into requests of 40); `useExerciseDetailQuery(slug)` reads one in full (`get`) for the detail screen and the guide. Each resolved Exercise is kept in MMKV (`exercises.summary.<slug>`, `exercises.exercise.<slug>`, the same for every User, with when it was saved) and read as the query's `initialData`, so it shows offline and right after a restart and is refetched once stale; one the library no longer has is forgotten. A slug never resolved (offline first run, a failing library, or unknown to it) shows `exerciseNameFromSlug`'s name, no muscle groups and no thumbnail, and isn't a link to a detail screen or guide; screens never wait on the library. Thumbnails are the render endpoint's `thumbnail_url` with the shown size appended (`sizedThumbnailUrl` in `lib/exercise-media.ts`, device pixels). Exercise history queries `workout_session_exercises` by `exercise_slug`. The Coach's plan card links and saves by each Exercise's `exercise_slug` (a card from before slugs can't be saved). Not yet moved (FIT-242): the Library tab and the Exercise picker list the legacy `exercises` table (`useExercisesQuery`), but write and link by its `slug`. The "Update your plan?" sheet still shows the names `workout_session_plan_changes` answers (its response carries no slugs). Each slug's query retries once (never on a 429, 401 or 400), and the detail query writes what it read into the slug's row query, so an Exercise that left the library stops linking at once.

**Data fetching (web)**: Server Components query Supabase directly through `createClient()` from `~/lib/supabase/server`. Client components use `useSupabase()` from `~/lib/supabase/client` and TanStack Query (provider in `components/providers.tsx`).

**Shared types**: Import domain types from `@fitme/core`, never from an app's `lib/`. Import row types from `@fitme/supabase` (`Tables<"plans">`).

**Authentication (mobile)**: Clerk (`@clerk/expo`, hooks-based custom flows on the existing screens). Identity (id, email, name) comes from Clerk's `useUser`; the Profile from `useProfileQuery`. Never call Supabase Auth APIs. `@clerk/expo` is excluded from Expo autolinking in `package.json` (its native module needs iOS 17 and is only used by Clerk's prebuilt native views); the JS SDK treats it as optional. The `<Authenticated>` component wraps protected screens and redirects signed-out users. Registration and password reset both go through the shared code screen `app/auth/verify-code.tsx` (`?purpose=sign-up`, `?purpose=reset-password`, or `?purpose=sign-in` when Device Trust wants a code after a reset; each purpose maps to its Clerk flow in `components/views/verify-code-view.tsx`): forgot-password starts a sign-in and emails the reset code, the code screen moves on to reset-password, which submits the new password and signs the User in. There is no web reset page or universal link. The register and reset-password forms mirror Clerk's minimum password length (`PASSWORD_MIN_LENGTH` in `lib/constants.ts`, 15 on both instances). E2E flows register a fresh `+clerk_test` User per run on the Clerk development instance (test mode: no email sent, fixed code 424242) through `e2e/subflows/register.yaml`, and sign in through `e2e/subflows/sign-in.yaml` (`EMAIL`/`PASSWORD` runFlow env).

**Styling (mobile)**: uniwind (Tailwind CSS for React Native). The tokens come from `@fitme/design-tokens`, which `apps/mobile/global.css` imports; the stylesheet itself only maps the font roles to the bundled font files and adds `border-hairline`. One dark theme, no light variant. Custom spacing tokens: `xs`, `sm`, `md`, `lg`. Text uses the HIG text styles (`text-body`, `text-body-emphasized`, `text-mono-footnote`, …), never a separate font, weight, leading or tracking class; `cn()` (`lib/utils.ts`) knows them.

**UI Components (mobile)**: Built on `@rn-primitives` (shadcn/ui-compatible for React Native). Use components from `apps/mobile/components/ui/`.

**UI quality**: read `docs/agents/ui.md` before building or changing any screen (mobile, web or site): the design rules (tokens, type scale, layout, Primitives, the four states every Screen has) and the screenshot-and-review loop every UI change goes through before it's done.

**Minimum version gate (mobile)**: `components/minimum-version-gate.tsx` wraps the root `Stack` in `app/_layout.tsx`. On launch and on every return to the foreground it fetches `GET /v1/client-config` from `EXPO_PUBLIC_API_URL` (`useClientConfigQuery`) and compares the build's version (`Constants.expoConfig.version`, stamped from the release tag) with the platform's minimum through `isBelowMinimumVersion` (`lib/app-version.ts`; numeric `x.y.z` comparison, the `0.0.0` dev placeholder and unreadable versions never block). Below the minimum the whole app is replaced by `UpdateRequiredView`, whose button opens the App Store (`ios.appStoreUrl` in `app.json`) or Play Store listing. A failed request, an error response or an unset `EXPO_PUBLIC_API_URL` never blocks (a failed foreground recheck keeps the last answer the app got). The app renders normally while the launch check is in flight. To cut off old builds, set `MIN_APP_VERSION_IOS` / `MIN_APP_VERSION_ANDROID` on the `fitme-api` Vercel project (production) and redeploy the API so it picks up the env; no app release is needed. Lowering or removing it unblocks Users the next time they foreground the app (after the 5-minute cache). Only raise it once most installs run a build that has the gate.

**Coach screen (mobile)**: `app/(tabs)/coach/index.tsx` talks to `apps/coach` through `useEveAgentRuntime` from `@assistant-ui/eve` (ADR 0005), pointed at `EXPO_PUBLIC_COACH_URL`, with the Clerk session token as the bearer, resolved per request (reconnects included). The global `fetch` is `expo/fetch`, installed by Expo's runtime (since SDK 57), so eve's NDJSON stream streams; don't set `EXPO_PUBLIC_USE_RN_FETCH`. The custom chat components (`components/chat/`) read the runtime's state (`useAuiState`) as assistant-ui `ThreadMessage`s; the plan card renders from a `display_workout_plan` tool call's result. `lib/coach-chat.ts` holds the pure parts (unit-tested): each send carries `runConfig: { custom: { model } }` (`coachRunConfig`), which eve sends as the turn's client context, with the model-picker's choice read at send time (no model → no client context, so the Coach uses its default); `coachErrorAction` maps the channel's `coach_pro_required` refusal to the paywall, an ended session (`session_not_active`, `session_expired`, `session_stranded`) to a new Conversation, and anything else to the existing error state; a refused or failed send's text goes back into the composer and its failed bubble is hidden (`isRefusedSend`); and the User's current Conversation (eve session cursor plus the event log from the last finished turn) is saved in MMKV per Clerk User id (`coach.conversation.<userId>.session`, rewritten on every streamed event, and `….events`, once per finished turn), so reopening the screen resumes it, an answer still streaming included. "+" in the header resets the eve session and forgets the saved one. The model picker (`app/(tabs)/coach/model-picker.tsx`) lists the models served by `apps/api`'s `GET /v1/coach/models` (`useCoachModelsQuery`, ADR 0006), never a bundled list: the last successful response is kept in the global MMKV key `coach.models` (not per User), read as the query's `initialData` (offline too) and rewritten on every successful fetch; an unreadable or malformed value counts as no list. `lib/coach-model.ts` resolves the saved pick (`coach.model`) against the list: kept while it's in it, otherwise (removed, or an old pre-Gateway id; never migrated) the list's `defaultId`. With no list at all (nothing cached and the fetch failed, or `EXPO_PUBLIC_API_URL` unset) the picker shows a loading or unavailable state and sends carry no `model`; chat never waits on the list.

**Finishing a Workout Session (mobile)**: every way of finishing (the session header's Finish button, the finish suggestion, the Workout card on Home) goes through `useFinishWorkoutSession` (`hooks/finish-workout-session.ts`): the "Finish workout?" confirmation when planned sets are unlogged (not for the suggestion), the finish RPC, then the plan update step: `workout_session_plan_changes(session_id, apply = false)` (`fetchPlanChanges` in `hooks/queries/workout-sessions.ts`). With changes (and a live Plan and Workout) it reads the Profile for the weights' unit, then asks "Update your plan?" (`components/workout-sessions/plan-update-sheet.tsx`, one line per change from the pure formatter in `lib/plan-changes.ts`; the RPC's types, `PlanChanges` and `PlanChange`, live in `@fitme/core`) and opens the Summary once the User answers; without changes it opens the Summary at once, and a failed fetch (of the changes or the Profile) is reported to Sentry and opens the Summary too, so finishing never fails because of it. The sheet is a native `Dialog` that can't be swiped away, shown by `PlanUpdateSheetHost` in the root layout (`app/_layout.tsx`) through the small store in `hooks/plan-update-prompt.ts`, not by the screen that finished: the Workout card that finished it is gone once Home's Plan refetches. "Update plan" applies (`useApplyPlanChangesMutation`, `apply = true`, idempotent server-side, so a Retry never applies twice), invalidates the Plan queries and opens the Summary; a failed apply shows an inline error with Retry, and "Keep plan as is" always opens the Summary unapplied. Segment gets `Plan Update Suggested` (a count per change kind), `Plan Update Accepted` and `Plan Update Declined`. Free: no Pro check.

**Subscriptions**: RevenueCat manages IAP. `useIsProQuery` (queryKey `["rc-is-pro"]`) checks the "Fitme Pro" entitlement. Customer info updates are listened to in `_layout.tsx`.

**Module aliases**: Inside each app, `~/` and `@/` resolve to that app's root. Cross-workspace imports always go through the package name (`@fitme/core`, `@fitme/supabase`).

**Workspace packages are source-only**: no build step. Metro resolves them through the hoisted `node_modules`; Next compiles them via `transpilePackages`. CSS (`@fitme/design-tokens/tokens.css`) is `@import`ed by package name and resolved by Tailwind's compiler (uniwind's, under Metro). The tsdown apps (`apps/api`, `apps/exercises`, `apps/mcp`, `apps/webhooks`) inline `@fitme/*` and no package from `node_modules` (`deps.onlyBundle: []`): a workspace package's runtime dependency (`pg`, `drizzle-orm`, `@vercel/functions` for `@fitme/db`) must also be in the app's `dependencies`, or its build fails; it stays external and Vercel traces it into the function. Their build emits the Vercel entry as `dist/app.js` and the standalone Node server (`pnpm start`) as `dist/node/index.js`, out of Vercel's entrypoint lookup. pnpm uses `nodeLinker: hoisted` (see `pnpm-workspace.yaml`) because React Native autolinking needs a flat `node_modules`. Its `overrides` pin `react` / `react-dom` to the version Expo's React Native expects, so the workspace has one copy (`expo-doctor` flags a second); move it with the Expo SDK, together with each app's own pin. Its `patchedDependencies` patch uniwind (`patches/`): uniwind's Metro resolver swaps `react-native` for its own export list, which lacks RN 0.88's `AssetRegistry`, so expo-asset can't load assets, `useFonts` fails without a LogBox error and the splash never hides. Drop the patch once a uniwind release exports it (FIT-170).

## Git

The default branch is `main` (there is no `master`); branch from it and open pull requests against it. A clone whose `origin/HEAD` still points at `origin/master` is stale; repair it with `git remote set-head origin --auto && git remote prune origin`.

## Code Review Rules

Before reviewing a pull request's diff, gather its intent:

1. Read the PR description in full. It states what the change does, why, and what was deliberately left out.
2. Read the linked Linear issue. The issue key (`FIT-<n>`) is in the PR title, branch name or description. Read its description and comments, including acceptance criteria and blocking relations.
3. If the issue belongs to a Linear project, also read the project description. The project description is the spec, and it holds the decisions and constraints that apply across all of the project's issues.

Then review the diff against that intent: flag code that misses an acceptance criterion, goes beyond the issue's scope, or contradicts a decision in the spec, the ADRs (`docs/adr/`) or this file. Don't flag things the description or spec explicitly defers to a later issue. If a PR names no issue, or you can't read Linear, say so in the review and review against the PR description alone; never guess what an issue says.

## CI/CD

GitHub Actions use pnpm (`pnpm/action-setup`), `pnpm install --frozen-lockfile` and Node 24, the repo's minimum (root `engines`; EVE in `apps/coach` needs it). Linux jobs run on a pinned `ubuntu-24.04` (never `ubuntu-latest`), actions stay on majors that run on Node 24, and every workflow runs the lockfile's Supabase CLI (the `@fitme/supabase` devDependency) through `pnpm exec`, never `supabase/setup-cli`. Unit tests run through `pnpm turbo run test`; the `checks` job runs `pnpm check`, the literal check (`pnpm literal-check`) and `pnpm typecheck`; the pgTAP suite and the MCP, `packages/db` and `packages/services` integration tests run separately against a local Supabase stack (Supabase CLI, Supavisor in transaction mode) in `.github/workflows/integration-tests.yml`. The release workflow (`.github/workflows/release.yml`) never commits to `main` (it's protected): it derives the next version from the commits since the last `v*` tag following conventional commits (`feat:` → minor, `fix:` → patch, `BREAKING CHANGE:` or `type!:` → major), creates the tag with the GitHub release and the Linear release, then calls `.github/workflows/build-mobile.yml`. That workflow (also runnable by hand with a tag, to rebuild) stamps the tag's version into `apps/mobile/app.json` (whose committed `version` is a `0.0.0` placeholder) and starts the iOS production EAS build with auto-submit (every EAS profile extends `base` in `eas.json`, which pins the build's Node 24 version) (both jobs run in the `production` GitHub environment, which holds the `EXPO_TOKEN` and `LINEAR_ACCESS_KEY` secrets). The tag is the source of truth for the app version. The exercise sync workflow runs `pnpm --filter @fitme/supabase exercises:sync` on pushes to `main` that touch the exercise data (legacy, retired with the `exercises` table; ADR 0007). The Database Types workflow (`.github/workflows/database-types.yml`) starts a local database, runs `pnpm db types:generate` (which also normalizes the output with Biome) and fails if `packages/supabase/src/database.types.ts` is stale; against the same database it then runs `pnpm --filter @fitme/db schema:generate` and fails if `packages/db/src/schema.ts` or `src/relations.ts` is stale. Every Vercel project (`apps/api`, `apps/coach`, `apps/mcp`, `apps/site`, `apps/web`, `apps/webhooks`) sets `ignoreCommand` to `npx turbo-ignore@<version> --fallback=HEAD^1` in its `vercel.json`. A deployment is then skipped ("Canceled by Ignored Build Step") unless, since the branch's last deployment (the parent commit, through `--fallback`, on a branch's first one, so a new branch whose last commit leaves an app alone gets no preview of it), the app's workspace, a workspace package it depends on, a `globalDependencies` file (`turbo.json`'s, root `package.json` and `pnpm-workspace.yaml` included) or the app's own resolved lockfile entries changed; a lockfile change that only touches another app skips it, and turbo-ignore builds when it can't compare. A new Vercel app gets the same `vercel.json` line; keep the pin in step with the root `turbo` version. The one exception is `apps/exercises`: its Vercel project builds `main` only (`git.deploymentEnabled`) and has no `ignoreCommand`, so every push to `main` and every deploy hook builds it. A content release in `fitme-exercises` redeploys it through a deploy hook without a monorepo commit, and `turbo-ignore` would cancel that build whenever no commit since the last deployment touched the app (FIT-187). The Exercise Library API workflow (`.github/workflows/exercises-api.yml`) checks its API contract on pull requests; see `apps/exercises`. The PR Risk workflow (`.github/workflows/pr-risk.yml`) gives every pull request to `main` exactly one of `risk:high` / `risk:medium` / `risk:low`, by the highest tier of Risk Path (`.github/risk-paths.yml`) its changed files match; see `docs/agents/pr-risk.md`.

Issues live in Linear, team Fitme (`FIT-<n>`), via the Linear MCP tools. # Ultracite Code Standards

This project uses **Ultracite**, a zero-config preset that enforces strict code quality standards through automated formatting and linting.

## Quick Reference

- **Format code**: `npm exec -- ultracite fix`
- **Check for issues**: `npm exec -- ultracite check`
- **Diagnose setup**: `npm exec -- ultracite doctor`

Biome (the underlying engine) provides robust linting and formatting. Most issues are automatically fixable.

---

## Core Principles

Write code that is **accessible, performant, type-safe, and maintainable**. Focus on clarity and explicit intent over brevity.

### Type Safety & Explicitness

- Use explicit types for function parameters and return values when they enhance clarity
- Prefer `unknown` over `any` when the type is genuinely unknown
- Use const assertions (`as const`) for immutable values and literal types
- Leverage TypeScript's type narrowing instead of type assertions
- Use meaningful variable names instead of magic numbers - extract constants with descriptive names

### Modern JavaScript/TypeScript

- Use arrow functions for callbacks and short functions
- Prefer `for...of` loops over `.forEach()` and indexed `for` loops
- Use optional chaining (`?.`) and nullish coalescing (`??`) for safer property access
- Prefer template literals over string concatenation
- Use destructuring for object and array assignments
- Use `const` by default, `let` only when reassignment is needed, never `var`

### Async & Promises

- Always `await` promises in async functions - don't forget to use the return value
- Use `async/await` syntax instead of promise chains for better readability
- Handle errors appropriately in async code with try-catch blocks
- Don't use async functions as Promise executors

### React & JSX

- Use function components over class components
- Call hooks at the top level only, never conditionally
- Specify all dependencies in hook dependency arrays correctly
- Use the `key` prop for elements in iterables (prefer unique IDs over array indices)
- Nest children between opening and closing tags instead of passing as props
- Don't define components inside other components
- Use semantic HTML and ARIA attributes for accessibility:
  - Provide meaningful alt text for images
  - Use proper heading hierarchy
  - Add labels for form inputs
  - Include keyboard event handlers alongside mouse events
  - Use semantic elements (`<button>`, `<nav>`, etc.) instead of divs with roles

### Error Handling & Debugging

- Remove `console.log`, `debugger`, and `alert` statements from production code
- Throw `Error` objects with descriptive messages, not strings or other values
- Use `try-catch` blocks meaningfully - don't catch errors just to rethrow them
- Prefer early returns over nested conditionals for error cases

### Code Organization

- Keep functions focused and under reasonable cognitive complexity limits
- Extract complex conditions into well-named boolean variables
- Use early returns to reduce nesting
- Prefer simple conditionals over nested ternary operators
- Group related code together and separate concerns

### Security

- Add `rel="noopener"` when using `target="_blank"` on links
- Avoid `dangerouslySetInnerHTML` unless absolutely necessary
- Don't use `eval()` or assign directly to `document.cookie`
- Validate and sanitize user input

### Performance

- Avoid spread syntax in accumulators within loops
- Use top-level regex literals instead of creating them in loops
- Prefer specific imports over namespace imports
- Avoid barrel files (index files that re-export everything)
- Use proper image components (e.g., Next.js `<Image>`) over `<img>` tags

### Framework-Specific Guidance

**Next.js:**
- Use Next.js `<Image>` component for images
- Use `next/head` or App Router metadata API for head elements
- Use Server Components for async data fetching instead of async Client Components

**React 19+:**
- Use ref as a prop instead of `React.forwardRef`

**Solid/Svelte/Vue/Qwik:**
- Use `class` and `for` attributes (not `className` or `htmlFor`)

## Testing

- Write assertions inside `it()` or `test()` blocks
- Avoid done callbacks in async tests - use async/await instead
- Don't use `.only` or `.skip` in committed code
- Keep test suites reasonably flat - avoid excessive `describe` nesting

## When Biome Can't Help

Biome's linter will catch most issues automatically. Focus your attention on:

1. **Business logic correctness** - Biome can't validate your algorithms
2. **Meaningful naming** - Use descriptive names for functions, variables, and types
3. **Architecture decisions** - Component structure, data flow, and API design
4. **Edge cases** - Handle boundary conditions and error states
5. **User experience** - Accessibility, performance, and usability considerations
6. **Documentation** - Add comments for complex logic, but prefer self-documenting code
