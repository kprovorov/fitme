# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## Monorepo

This is a **pnpm + Turborepo** monorepo. Run repo-wide tasks from the root; run app-specific commands through the workspace filters.

```
apps/api                @fitme/api     — the Public API (ADR 0011): Hono + zod-openapi (Node)
apps/arnold             @fitme/arnold  — Arnold, Fitme's AI: an EVE agent (Vercel's durable agent framework, ai@7)
apps/mcp                @fitme/mcp     — MCP server (Streamable HTTP, Clerk OAuth) over the user tools
apps/library            @fitme/library — Library API: Hono + zod-openapi, serving a baked-in library.json bundle (Node)
apps/mobile             @fitme/mobile  — Expo / React Native app
apps/web                @fitme/web     — Next.js (App Router) web app
apps/site               @fitme/site    — Next.js marketing site (Vercel project fitme-site; fitmeproject.com isn't served from it yet, see apps/site)
apps/webhooks           @fitme/webhooks — Hono app receiving third-party webhooks (Node)
packages/core           @fitme/core    — domain models, labels, formatters, pure helpers
packages/library-sdk @fitme/library-sdk — the Library API client shared by Arnold, MCP and mobile, plus its in-memory fake
packages/design-tokens  @fitme/design-tokens — the design tokens and HIG text style utilities: one Tailwind v4 CSS file (mobile, web and site import it)
packages/i18n           @fitme/i18n    — the translations: one i18next catalog per App language, the i18next setup and the translation check
packages/supabase       @fitme/supabase — Supabase project + generated DB types
packages/db             @fitme/db      — asUser / withService: the only way backend apps reach Postgres
packages/observability  @fitme/observability — errors and traces: the shared privacy, propagation, environment and sampling rules, and the Node setup (Sentry behind it)
packages/rate-limit     @fitme/rate-limit — the per-caller rate limiter: Upstash Redis or in memory, chosen from the environment, failing open
packages/services       @fitme/services — business logic run inside an asUser / withService transaction
packages/typescript-config              — shared tsconfig presets
```

## Commands

```bash
pnpm install

# Root (Turborepo)
pnpm dev                 # turbo run dev (all apps)
pnpm dev:mobile          # expo start
pnpm dev:web             # next dev on :3000
pnpm dev:site            # next dev on :3001
pnpm dev:mcp             # tsx watch MCP server on :3002 (MCP endpoint at /)
pnpm dev:api             # tsx watch REST API on :3003
pnpm dev:webhooks        # tsx watch webhooks app on :3004 (needs FITME_DATABASE_URL, CLERK_WEBHOOK_SIGNING_SECRET)
pnpm dev:arnold          # eve dev (no TUI) on :3005 against the local stack (apps/arnold/.env.local: CLERK_JWT_KEY, FITME_DATABASE_URL, AI_GATEWAY_API_KEY)

pnpm build               # turbo run build

pnpm text-check          # no hardcoded visible text in the mobile app's .ts / .tsx: it comes from the catalogs (alias for pnpm --filter @fitme/i18n text-check)
pnpm knip                # unused files, exports, dependencies and binaries across the workspace (knip.jsonc: every ignore names its reason; not in CI)

# Per workspace

pnpm site build          # next build (marketing site)
pnpm mcp build           # tsdown bundle → apps/mcp/dist
pnpm mcp test            # vitest (in-memory MCP client)
pnpm mcp test:integration # vitest against the local Supabase stack through its pooler (CLERK_DEV_SECRET_KEY adds the Clerk OAuth suite)
pnpm api build           # tsdown bundle → apps/api/dist

pnpm webhooks test       # vitest (Hono app via app.request, signed payloads, fake services)
pnpm library generate    # write apps/library/src/generated/library.ts from LIBRARY_BUNDLE (default: the fixture bundle; production builds: Vercel Blob)
pnpm library build       # generate + tsdown bundle → apps/library/dist
pnpm library test        # generate + vitest (Hono app via app.request, test-signed Clerk tokens; bundle validation on fixture bundles)
pnpm library openapi     # regenerate apps/library/openapi.json (commit it; CI fails when it's stale)
pnpm arnold build        # eve build → apps/arnold/.output
pnpm arnold test         # vitest (channel auth, Pro check, model selection, turn limits, tool wiring; no database or model)
pnpm arnold eval         # eve eval: model-behaviour evals with stubbed tools (apps/arnold/evals; needs AI_GATEWAY_API_KEY in apps/arnold/.env.local, no database or Clerk token); run by hand before prompt or model changes, not in CI. `pnpm arnold eval show-my-plan` runs one
pnpm --filter @fitme/db test:integration # vitest through the local Supavisor pooler as the fitme login (needs a local stack)
pnpm --filter @fitme/services test:integration # services inside withService/asUser through the local pooler (needs a local stack)
pnpm db start            # supabase start     (alias for pnpm --filter @fitme/supabase start)
pnpm db types:generate   # regenerate packages/supabase/src/database.types.ts
pnpm --filter @fitme/db schema:generate # regenerate packages/db's Drizzle schema (src/schema.ts, src/relations.ts) from the local stack
pnpm db clerk:check      # prove a Supabase stack accepts Clerk dev session tokens (CLERK_SECRET_KEY sk_test_…, SUPABASE_URL, SUPABASE_ANON_KEY)
pnpm --silent db clerk:jwt-key [domain] # print a Clerk instance's JWT public key (CLERK_JWT_KEY); defaults to the dev instance

# Single test file
pnpm --filter @fitme/core exec vitest run src/__tests__/formatters.test.ts
pnpm --filter @fitme/library-sdk exec vitest run src/__tests__/client.test.ts
pnpm --filter @fitme/mobile exec jest --runTestsByPath <path from apps/mobile> # not --testPathPatterns: it matches the absolute path, so a worktree named after the issue can match every file
```

A jest "worker process has failed to exit" or "asynchronous operations that weren't stopped" means a test leaves a handle open. Run each changed test file alone (`pnpm --filter @fitme/mobile exec jest --runInBand --detectOpenHandles --runTestsByPath <file>`) before calling it pre-existing: a whole-suite rerun that exits cleanly proves nothing.

## Architecture

### apps/mobile — Expo app

The App Store listing is public text in `apps/mobile/store.config.json` (`en-US`
and `uk`), referenced by `submit.production.ios.metadataPath` in `eas.json`.
Change it through PRs; update both locales' release notes for each release.
Release CI waits for EAS auto-submit before pushing metadata to the tag's draft
version, using the existing EAS App Store Connect submission key. Never push
metadata from PRs. `eas metadata:pull` also exports private review details and
assets: retain only public listing text before staging. See README's App Store
listing section for commands, credentials and draft verification.

React Native / Expo app using **file-based routing** via `expo-router`:

- `app/` — Expo Router routes (file-based navigation)
  - `_layout.tsx` — Root layout: initializes fonts, Sentry and RevenueCat, and default-exports the layout through `Sentry.wrap` (render crashes, touch breadcrumbs, app start). Sentry (`@sentry/react-native`, the `fitme-mobile` project) is off in `__DEV__` builds (`enabled: !__DEV__`), takes `scrubEvent` (`beforeSend` / `beforeSendTransaction`) and `tracePropagationTargets` from `@fitme/observability`'s root export (trace headers to our services only, never Clerk, RevenueCat, Supabase or Segment), `sendDefaultPii: false`, traces at 0.1 and profiles at 0.5 of traced sessions. Release builds upload source maps and dSYMs through the `@sentry/react-native/expo` plugin (`SENTRY_AUTH_TOKEN` in the EAS `production` environment)
  - `(tabs)/` — Bottom tab navigator: Workout (`dumbbell.fill`), History (`book.pages`), Arnold AI (`sparkles.2`), Library (`book`), each with Figma's one symbol for both states; the first tab (Home in code, `(home)`) is titled Workout (`tabs.workout`), in the tab bar and the back buttons over the tabs (`getTabTitle`). Profile is no tab: `app/profile.tsx` is a stack screen pushed over the tabs from the Home header's `person.fill` button (spoken label `profile.title`), with a back button to the tab; `__tests__/profile-header-button.test.tsx` covers it. Native tabs only show routes declared in `_layout.tsx` (SDK 58), so Home is the `(home)` group: its `index.tsx` is the app's `/` route, with no redirect route in between
  - `auth/` — Login/Register screens and the shared emailed-code screen (presented as fullscreen modal)
  - `onboarding/` — Post-registration onboarding flow (fullscreen modal)
  - `planner/` — AI plan generation flow (modal)
  - `plans/[planId]/` — Plan detail and workout views
  - `exercises/[exerciseSlug]/` — Exercise detail view and its guide (a form sheet), keyed by Exercise slug and read from the Library API
- `components/` — Reusable UI components
  - `ui/` — Primitive UI components (Button, Input, Dialog, etc.) built on `@rn-primitives`
  - `providers.tsx` — Wraps app with ClerkProvider (secure-store token cache), QueryClientProvider, ThemeProvider, KeyboardProvider; renders `auth-sync.tsx`, which identifies the Clerk User to Sentry (`{ id }`, the Clerk id only: no email or name; cleared on sign-out)/RevenueCat/Segment and clears the query cache on sign-out
  - `authenticated.tsx` — Auth guard component: waits for Clerk to load, redirects to `/auth/register` when signed out
- `hooks/` — Data layer
  - `queries/` — Read queries using `react-query-kit`'s `createQuery`; `library.ts` holds the Library hooks (see Key Patterns)
  - `mutations/` — Write mutations using `react-query-kit`'s `createMutation`
  - `revenueCat.ts` — RevenueCat subscription queries
  - `arnold-model.ts` — `useSelectedArnoldModel`: the served model list, the picked model and its setter, for the Arnold header and model picker
  - `muscle-choice.ts` — each Library screen's Muscle group choice, in memory per screen key (never MMKV), shared with the Muscles sheet (see Exercises (mobile))
- `lib/` — App-specific utilities
  - `supabase.ts` — Supabase client whose access token is the Clerk session token (no Supabase Auth session)
  - `clerk.ts` — Clerk publishable key, `getClerk()` for code outside React, `getCurrentUserId()`, `getClerkErrorMessage()`
  - `mmkv.ts` — MMKV storage instance (`createMMKV()`, react-native-mmkv 4 on Nitro Modules; same default instance and directory as v3, so saved data carries over), plus `devToolsStorage`, the same instance with `delete` for the devtools sync. Under Jest MMKV swaps in its own in-memory instance; `package.json` maps `react-native-nitro-modules` to `test-utils/nitro-modules.ts` so the import resolves
  - `arnold-chat.ts` — Arnold screen helpers: `getArnoldUrl`, per-turn model context, error → paywall mapping, the saved Conversation (see Key Patterns)
  - `public-api.ts` — `publicApi()`, the one Public API client (`apps/api`): the `lib/api/client.ts` client at `EXPO_PUBLIC_API_URL` with the User's Clerk session token resolved per request (see Key Patterns). `lib/api/client.ts` holds `createPublicApi` (`openapi-fetch`, an injectable `fetch`) and `ApiError`; `lib/api/schema.ts` is generated from `apps/api/openapi.json` (`pnpm mobile api:types`, `openapi-typescript`), committed, never edited by hand
  - `i18n.ts` — the translations (see App language (mobile) in Key Patterns): `i18n`, `@fitme/i18n`'s instance in the App language, bound to `react-i18next` (`setI18n`, so `useTranslation()` needs no provider), `useAppLanguageSync()` (the App language, and the device's region and clock from `useLocales()` / `useCalendars()` through `setDeviceConventions`), and `useAppLanguage()`, the App language the text is in (re-rendering when it changes), which the Library hooks ask in, and `useI18n()`, the instance for `@fitme/i18n`'s formatters (a fresh view of it per `t`, so the React Compiler re-formats when only the region or clock changed). **The one way to format a date, time or number on screen** is `@fitme/i18n`'s `src/format.ts` given `useI18n()` (`i18n` outside React): `formatDate(i18n, date, style)`, `formatTime`, `formatNumber`, and the unit and count helpers; never date-fns `format`, `toLocale*String` or a hand-built `Intl` formatter (date-fns stays for date arithmetic, such as `isThisYear`)
  - `choices.ts` — `useChoiceLabels()` (and `choiceLabels(t)` outside React): every fixed choice the app shows (muscle groups, goals, places, experience levels and their descriptions, genders, measurement systems and their descriptions) by its `@fitme/core` enum id, in the App language from the catalogs' `choices` section; an id the catalogs lack shows as itself. The app never shows core's English labels (`labels.ts`, `muscleGroupToName`), which stay for the servers
  - `tabs.ts` — each tab route's catalog key (`TAB_TITLE_KEYS`), and `getTabTitle`, the focused tab's title in the App language for the back buttons over the tabs
  - `library.ts` — `getLibrary()`, the `@fitme/library-sdk` client, at `EXPO_PUBLIC_LIBRARY_URL` with the User's Clerk session token resolved per request (unset → every call fails unavailable, no request); `library-cache.ts` keeps the Exercises it resolved, and the Covers, in MMKV (see Key Patterns)
  - `arnold-model.ts` — Arnold's model list schema and MMKV cache (`arnold.models`), and the picker's choice (`arnold.model`) resolved against it (see Key Patterns)
  - `utils.ts` — `cn()` class merger (tailwind-merge with the HIG font scale)
  - `segment.ts` — the Segment client, created at import. Segment generates ids through `crypto.getRandomValues`, so `react-native-get-random-values` is a direct dependency even though no app code imports it: only a direct dependency gets its native module (`RNGetRandomValues`) autolinked, and without it the client throws at import and the app never renders. Don't remove it as unused.
  - `constants.ts`
- `test-utils/` — Jest helpers.
  - `setup.ts` (Jest `setupFiles`) binds an English `@fitme/i18n` instance to `react-i18next`, so a screen or component rendered on its own (without the root layout, which loads `~/lib/i18n`) still translates; a test that imports `~/lib/i18n` (for `useAppLanguageSync`, to follow `setDeviceLanguages`) binds that instance instead. It also swaps `~/lib/library` for the in-memory fake in every test file, so no test reaches the network, `~/lib/public-api` for the real client whose `fetch` is the fake Public API (below), and `@sentry/react-native` for a stand-in (`captureException`, `setUser`; the real SDK's import-time `setInterval` keeps Jest alive), which a file checking reports mocks again; `expo-localization` for `device-locales.ts`, an English device (`en-US`), so every screen renders in English: `setDeviceLanguages(["uk-UA"])` sets the device's preferred languages, in order, before rendering or (in `act`) during a test, re-rendering every mounted `useLocales()` (the device region is each tag's), `setDevice24HourClock(true)` switches its 12-hour clock to 24-hour for `useCalendars()`, and `after-each.ts` puts it back to English on a 12-hour clock after each test (a file mocking `expo-localization` itself must not render anything importing `~/lib/i18n`, which reads `getLocales()` and `getCalendars()`); `serveLibrary` (`fake-library.ts`) points the Library fake at a test's Exercises (and `{ covers }`), which `libraryExercise` builds in English, with `translations` (`{ uk: { name, description?, instructions? } }`) for another App language.
  - `stack-screen-stub.tsx` — `StackScreenStub`, expo-router's `Stack.Screen` under Jest (`jest.mock("expo-router", …)` with `jest.requireActual`): the header's title as text and its `headerSearchBarOptions` as a `TextInput` labelled with the placeholder (testID `header-search-bar`), whose typing calls `onChangeText` with the native event's shape, a `Cancel` button clearing it and calling `onCancelButtonPress`, and a `ref` answering `clearText` / `setText`.
  - `fake-public-api.ts` — the fake Public API, over the same in-memory rows as the fake Supabase backend `fake-workout-backend.ts`, as the User `FAKE_USER_ID` with the bearer `FAKE_SESSION_TOKEN`; routes are named as templates (`"POST /v1/workout-sessions/{id}/finish"`, each request keeps its `path` too); `failNext(route, failure)` fails a route with a status, a 429 with `Retry-After`, a network failure or a lost answer, `pause(route)` holds it, `baseUrl = ""` plays an unset `EXPO_PUBLIC_API_URL`; a route it doesn't implement answers 501 and `after-each.ts` fails the test, then resets the fake. It answers like the `/v1` routes, so far these, in path order (a later write adds its route on its own line at its place in the order, not at the end, so parallel additions merge):
    - the public `GET /v1/arnold/models` (`@fitme/core`'s list, whatever the bearer)
    - `POST /v1/plans` (bounds checked like the API's, slugs looked up in the fake Library: `unknown_exercises`, or `library_unavailable` while it `failWith`s)
    - `DELETE /v1/plans/{id}` (a soft delete, 204 again on a repeat)
    - `POST /v1/plans/{id}/activate` (every other Plan inactive; 404 for a missing or deleted one)
    - `PATCH /v1/profile` (bounds checked like the API's, 404 `profile_not_found` without a Profile)
    - `PUT /v1/profile` (every field required, the same bounds; 201 creating the Profile, 200 replacing it, converting to a new system first)
    - `GET /v1/weekly-goals` (the test's seeded `backend.weeklyGoalChanges`; the fake's Plan writes record none)
    - `DELETE /v1/workout-session-exercises/{id}` (204 whether or not it matched, no `order` gap closed; 409 for a finished session)
    - `PUT /v1/workout-session-exercises/{id}` (the slug looked up like `POST /v1/workout-sessions/{id}/exercises` does, then the sets' targets zeroed; 404 for a missing one, 409 for a finished session)
    - `POST /v1/workout-session-exercises/{id}/sets` (appended at the highest `order` + 1, logged at the fake's time, no targets; 404 for a missing Workout Session Exercise, 409 for a finished session)
    - `PATCH /v1/workout-session-sets/{id}` (409 `session_finished` for a finished session)
    - `GET /v1/workout-sessions` (a page of summaries over the fake rows, newest start first, with `completed_rep_count`, `volume`, `personal_records` (`backend.personalRecords`) and the Profile's `weight_unit`; `limit` 1–50, `offset`, `status`)
    - `POST /v1/workout-sessions` (201 started, 200 resuming the Workout's open one, 409 `session_in_progress` while another Workout's is open)
    - `POST /v1/workout-sessions/{id}/exercises` (appended at the highest `order` + 1, the slug looked up in the fake Library: `unknown_exercises`, or `library_unavailable` while it `failWith`s; 404 for a missing session, 409 `session_finished` for a finished one)
    - `POST /v1/workout-sessions/{id}/finish` (`already_finished` on a repeat; awards its Personal records through `@fitme/core`'s `personalRecordFor`; rotates the Workout to the end of its seeded Plan)
    - `GET` and `POST /v1/workout-sessions/{id}/plan-update` (the Plan Update over the seeded Plan, matched by `order` like the service: changes for a finished session until applied, none after; 404 for a missing session)
  - `router-stub.tsx` — expo-router stand-ins for a screen test that follows a push: `stubRouter` (`useRouter()`: `push` / `back` over a stack of pushed routes, a string or `{ pathname, params }`), `<PushedRoutes screens={{ [pathname]: Screen }} />` mounting each pushed route it names over the rendered screen with its params (`useStubParams(base)` as `useLocalSearchParams`), and `StackScreenStub` (`Stack.Screen`: its `title` as a header, its left and right items as buttons, and its `headerSearchBarOptions` as `stack-screen-stub.tsx`'s search bar); call `resetStubRouter()` before each test. The Exercise picker tests (`workout-session-exercises.test.tsx` and others) and the Muscles sheet's (`muscles-sheet.test.tsx`) use it
  - `searched-exercises-view.tsx` — `SearchedExercisesView`, `ExercisesView` with its search held outside the list in a text field labelled `library.search`, as a screen's header search bar holds it, for tests rendering the view on its own
  - Tests build their QueryClient with `createTestQueryClient()` (`query-client.ts`: no retries, no gc timers, which would keep Jest from exiting), cleared after each test by `after-each.ts` (`setupFilesAfterEnv`), and wait for the app with `settle(client)` (real timers only), which advances a macrotask at a time until nothing is fetching, mutating or queued to notify query observers, never on `waitFor`'s 1 s limit
- `plugins/` — local Expo config plugin for Xcode 27 compatibility: `with-ios-min-deployment-target.js` (raises pod targets below iOS 15.1, including resource bundles; still needed on SDK 58, since pods such as `react-native-keyboard-controller`, `react-native-safe-area-context`, `@sentry/react-native` and Segment still declare older minimums). RevenueCat needs no patch: `react-native-purchases` 10 pins purchases-ios 5.95.0, which builds under Xcode 27 / Swift 6.4. It stays on 10 (checked 2026-10-29): 11.0.0 depends on the `PurchasesHybridCommon` 20.1.0 pod (purchases-ios 5.99.0), which isn't on CocoaPods trunk until after its November 1–7 freeze, so `pod install` can't resolve it, and RevenueCat's release notes tell Expo apps to stay on 10.x until then (FIT-373 retries the upgrade). The app itself targets iOS 16.4 (SDK 58's default). UIScene adoption needs no flag on SDK 58: prebuild generates `SceneDelegate.swift`, so there is no `expo-build-properties` plugin.

### apps/web — Next.js app

- `app/` — App Router routes. `(app)/` is the authenticated area (dashboard; account menu is Clerk's `<UserButton>`); `sign-in/[[...sign-in]]` is Clerk's prebuilt `<SignIn>` page. `ClerkProvider` in the root layout sets the sign-in URL and sends signed-out Users to `/`.
- `proxy.ts` — Next 16 request proxy running `clerkMiddleware`: every route except `/` and `/sign-in` calls `auth.protect()`, which redirects signed-out requests to sign-in with a `redirect_url` back. Its matcher skips `/.well-known/` (and static files), so those are served signed out. Route paths live in `lib/routes.ts`.
- `public/.well-known/apple-app-site-association` — the iOS app's associated domains on app.fitmeproject.com (`ios.associatedDomains` in `apps/mobile/app.json`): `webcredentials` (password AutoFill) and `activitycontinuation` (Handoff) for `X75M2KSBQL.com.fitmeproject.ios`. No `applinks` (the app has no universal links) and no `appclips` (no App Clip target, so `app.json` doesn't claim it). `next.config.ts` serves it as `application/json`. `__tests__/apple-app-site-association.test.ts` (vitest, Next's experimental `unstable_doesMiddlewareMatch` / `unstable_getResponseFromNextConfig`) checks the proxy never runs on it, the header and its content.
- `lib/supabase/server.ts` (`createClient()`, Server Components) — a `supabase-js` client typed with `Database` from `@fitme/supabase` whose `accessToken` is the User's Clerk session token, so RLS reads their Clerk id from `sub`. There is no Supabase Auth session in the web app.
- `components/ui/` — shadcn-style primitives (Tailwind v4 + cva). `components.json` is set up for the shadcn CLI.
- Styling: Tailwind v4 via `@tailwindcss/postcss`; `app/globals.css` imports `@fitme/design-tokens` and only maps the font roles to the `next/font` variables (`--next-font-*`). Dark only (`color-scheme: dark`), whatever the OS setting.
- `lib/clerk-appearance.ts` — Clerk's `appearance.variables` as `var(--color-…)` / `var(--radius-…)` / `var(--font-…)` strings, passed once to `ClerkProvider`, so `<SignIn>` and `<UserButton>` follow the tokens.
- Errors and traces: `@sentry/nextjs`, reporting to the `fitme-web` Sentry project (`NEXT_PUBLIC_SENTRY_DSN`, browser and server alike; unset → nothing sent), every option from `lib/observability.ts`'s `sentryOptions()`: the root export's `sdkOptions` for that DSN, the same options `@fitme/observability/node` starts with. `instrumentation.ts` starts it on the server (Node and edge) and exports `onRequestError`, so errors from Server Components, route handlers, server actions and `proxy.ts` are reported; `instrumentation-client.ts` starts it in the browser with `browserTracingIntegration` (page loads, navigations, `fetch` spans; trace headers to the propagation targets only) and no Session Replay or web vitals (an empty integration named `WebVitals` keeps browser tracing from adding the real one; Vercel Speed Insights covers vitals). `app/global-error.tsx` reports root render errors. The Sentry user is the Clerk id only: `components/sentry-user.tsx` (rendered by `Providers`) sets `{ id }` in the browser and clears it on sign-out, and `proxy.ts` and `(app)/layout.tsx` set it for the request's server events. `next.config.ts` exposes `VERCEL_ENV` / `VERCEL_GIT_COMMIT_SHA` as `NEXT_PUBLIC_VERCEL_ENV` / `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` for the browser and wraps the config in `withSentryConfig`: with `SENTRY_AUTH_TOKEN` the build uploads its source maps to `SENTRY_ORG` / `SENTRY_PROJECT` for the release `VERCEL_GIT_COMMIT_SHA` and deletes them from the output; without it the upload is skipped and the build still succeeds. `apps/web/turbo.json` hashes `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` into the build, since both are inlined.

### apps/site — Next.js marketing site

The public marketing site, meant for fitmeproject.com (which doesn't serve it yet: see Hosting below). No auth, no Supabase. Tailwind v4 via `@tailwindcss/postcss` (CSS-first config in `app/globals.css`, typography plugin loaded with `@plugin`) with shadcn-style `components/ui/` primitives. - `blog/*.mdx` — posts with `title`, `summary`, `publishedAt` frontmatter, parsed by `app/blog/utils.ts` and rendered with `next-mdx-remote-client`. Cover image: `public/blog/<publishedAt>.png`.
- `public/.well-known/apple-app-site-association` — universal links for the iOS app (served as JSON via `next.config.ts` headers).
- Analytics: PostHog (proxied through `/ingest` rewrites), Google Tag Manager, Vercel Analytics and Speed Insights. Client init lives in `instrumentation-client.ts`.
- Hosting: the `fitme-site` Vercel project builds it, but it has no domain. fitmeproject.com (DNS on Vercel, checked 2026-10-21) points at superapp (`domains.superapp.now`), which serves a separate Vite-built site from DigitalOcean App Platform, not this app: nothing in this repo deploys there. Until the domain moves to `fitme-site`, this app's Sentry setup only reports from `fitme-site` deployments (previews and its `*.vercel.app` production URL).
- Errors and page loads: `@sentry/nextjs`, browser only, reporting to the `fitme-site` Sentry project. `instrumentation-client.ts` initialises it after PostHog from `@fitme/observability`'s root export (`resolveObservabilityConfig` with `NEXT_PUBLIC_SENTRY_DSN`, so no DSN → no init, nothing sent; `scrubEvent` as `beforeSend` / `beforeSendTransaction`), with `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` inlined by `next.config.ts` as `NEXT_PUBLIC_VERCEL_ENV` / `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` (hashed into the build by `apps/site/turbo.json`). Page loads and navigations are traced at the shared rates (`traceLifecycle: "static"`, so the scrubber sees each transaction); no trace headers on any request (the site calls no backend of ours), no Session Replay, and no web vitals (Speed Insights has them): `browserTracingIntegration` ignores CLS, LCP and INP, and `beforeSendTransaction` drops every transaction's `measurements` (TTFB, FCP and the rest too). `dataCollection` is locked down like the Node setup's: no cookies, headers, bodies, URL query strings or user info. `app/global-error.tsx` reports root render errors, then renders Next's own error page. There is no `instrumentation.ts`: no server SDK, so nothing server-side is reported or traced. `next.config.ts` wraps the config in `withSentryConfig` (from `@sentry/nextjs/config` in SDK 11): with `SENTRY_AUTH_TOKEN` (`SENTRY_ORG` / `SENTRY_PROJECT`) it uploads the browser source maps for the release `VERCEL_GIT_COMMIT_SHA` and deletes them from the output; without it the upload is skipped, and a failed upload is only logged. The site imports `@sentry/nextjs` itself (the Next SDK has to hook the build and the client entry), but takes every rule from `@fitme/observability`.

### apps/api — REST API

The Public API (ADR 0011): Hono app built on `@hono/zod-openapi` (zod 4), like `apps/library`, served with `@hono/node-server`, bundled with tsdown. Reads domain data from `@fitme/core`, and User data through `@fitme/services` inside `asUser` (so `@fitme/db`'s runtime dependencies are in its own `dependencies`; `FITME_DATABASE_URL` carries `application_name=api`). Reports to the `fitme-api` Sentry project through `@fitme/observability`, with the same entry, build setup and `turbo.json` as `apps/webhooks`.

- `src/index.ts` — Node entrypoint, `PORT` env (default 3003).
- `src/app.ts` — the Vercel entry (`dist/app.js`): imports `hono`, calls `initObservability({ service: "api" })` and `reportMissingEnv` with `src/required-env.ts`' list (`CLERK_JWT_KEY`, `FITME_DATABASE_URL`, `LIBRARY_URL`, `LIBRARY_PUBLIC_API_SECRET`), then loads `create-app` with a dynamic `import()` and default-exports `createApp()` (see `apps/webhooks`), which throws in production without Upstash, so such a deployment fails at startup.
- `src/create-app.ts` — `createApp({ clerkJwtKey, createLibrary, createServices, identifyUser, rateLimiter, reportError })` (each one left out = the real one: `CLERK_JWT_KEY`, `createLibraryFromEnv`, `createServicesFromEnv`, `@fitme/observability/node`'s `identifyUser` and `reportError`, `rateLimiterFromEnv(process.env)`): an `OpenAPIHono`, `observeHono(app)` first (request spans), logger, CORS (`origin: "*"`, before auth, so preflights answer without a token and a 401 is readable cross-origin), `/health` and the global `/v1` routes (`publicV1`, no token), then `requireCaller` on every other route (unknown ones included), `identifyUser(userId)` (the Sentry user is the Clerk id only; the same middleware sets `getLibrary`, the client built once on first use, and `reportError` for routes), `rateLimitCallers`, the User-data routes (`userV1`), and JSON `notFound`/`onError` handlers returning `{ error: { code, message } }`; `onError` reports every unhandled error before the 500, an `HTTPException` (and any 4xx a route answers itself) goes out unreported.
- `src/auth.ts` — `requireCaller`: `Authorization: Bearer` must be a Clerk session token (with a `sid`) verified networkless against `CLERK_JWT_KEY` (one Clerk instance per deployment: production's in production, development's everywhere else); anything missing, malformed, expired or from another instance → 401 `unauthorized`, unreported. An unset key throws before the token is even read (a reported 500 for every request past the public routes): never served without auth. It sets the verified caller (`{ userId, kind: "session" }`; `"oauth"` / `"api_key"` join later) and `getServices`, returning the caller's facade, built on first use (an unconfigured database throws: a reported 500). Each User-data route declares the permission it needs through `requires("read" | "write")` in its `createRoute` `middleware`; a session may do both, so nothing is refused yet, and a refusal fails closed (a reported 500) until scoped credentials bring a documented answer for it. Routes declare `security: bearerSecurity` (`bearerAuth` in the OpenAPI document).
- `src/rate-limit.ts` — `rateLimitCallers`, after `requireCaller`: every request with a verified caller (unknown routes included; `/health` and the global routes never) is counted before anything is served, in the caller's bucket (`user:<Clerk id>` for a session; a later OAuth client or API key gets its own key there, nothing else changes). Over the limit → 429 `rate_limited` with `Retry-After` (seconds), documented on every User-data route (`rateLimitedResponse` in `src/schemas.ts`). The limit is `RATE_LIMIT_REQUESTS` per `RATE_LIMIT_WINDOW_SECONDS` (a fixed window, default 300 per 60; a malformed value fails at startup), on `@fitme/rate-limit` with the Upstash prefix `api`. `rateLimiterFromEnv`: Upstash when `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` are set, in memory otherwise outside production (a Vercel preview included: only Production has Upstash), a startup failure in production without them. A limiter that throws or takes over 1 s serves the request uncounted (fail open) and is reported once. Tests use the in-memory limiter on a fake clock (`testApp({ rateLimiter })`; by default one no test reaches).
- `src/services.ts` — `UserServices`, the per-User facade (MCP's pattern): `createServicesFromEnv(userId)` builds it for the verified User id, each method running one `@fitme/services` function inside `asUser` (one transaction per request); `null` without `FITME_DATABASE_URL`. Routes call `c.var.getServices()` and never pass a User id. A read (or write) carrying weights answers `Weighed<T>` (`{ value, weightUnit }`): its transaction first runs `lockProfileUnits`, whose `weight` is the unit (`kg` without a Profile), which the route shows as `weight_unit`. Locking before the read keeps a measurement-system conversion from committing between the two (READ COMMITTED gives each statement its own snapshot). A write (`createPlan`, `replaceWorkouts`, `updatePlan`, `activatePlan`, start, log, finish, adding, removing or replacing an Exercise, adding a set) first takes `ROW EXCLUSIVE` on the User tables in `deleteUserData`'s order, before that Profile row lock: an account deletion holds those tables and then deletes the Profile row, so asking for them after it would deadlock (`integration/account-deletion-locks.test.ts`). Its methods so far, in alphabetical order (a new one goes on its own line at its place in the order, not at the end, so parallel additions merge):
  - `activatePlan` (activates, then reads the Plan in full in the same transaction)
  - `addExerciseToWorkoutSession`
  - `addSetToWorkoutSessionExercise`
  - `applyPlanUpdate` (a straight `asUser` call: the service takes its own table locks and reads the unit, answering `weight_unit` itself)
  - `createPlan`
  - `deletePlan`
  - `deleteWorkoutSession`
  - `finishWorkoutSession`
  - `getActivePlan`
  - `getPlan`
  - `getProfile`
  - `getWorkoutSession`
  - `listPlans`
  - `listWeeklyGoalChanges`
  - `listWorkoutSessions` (`Weighed`: the page's volumes in the User's unit)
  - `logSet`
  - `previewPlanUpdate` (a straight `asUser` call, like `applyPlanUpdate`)
  - `removeExerciseFromWorkoutSession`
  - `replaceExerciseInWorkoutSession`
  - `replaceProfile` (answers whether it created the Profile)
  - `replaceWorkouts` (`updatePlan` with `workouts` only)
  - `startWorkoutSession`
  - `updatePlan` (metadata only, never `workouts`)
  - `updateProfile`
- `src/routes/v1.ts` — versioned router; each resource lives in its own file under `src/routes/` (an `OpenAPIHono` of `createRoute` definitions, each with its request and response schemas) and is mounted here. Every router's `defaultHook` is `invalidRequest` (`src/schemas.ts`): input failing its schema answers 400 `invalid_request` (`{ error: { code, message } }`, the message naming each field), unreported; a route can pass its own hook (`/v1/muscle-groups/{muscleGroup}` answers an unknown muscle group 404 `not_found`). Shared schemas (`ErrorResponse`, `errorResponse`, `Id`, `MuscleGroup`, `WeightUnit`, `WEIGHT_STEP`, `timestamp`, `WorkoutSessionSet`, the public cache header, the documented 400 and 401 responses) live in `src/schemas.ts`.
- `src/routes/client-config.ts` — public, unauthenticated `GET /v1/client-config`: `{ data: { minimumVersion: { ios, android, web } } }`, the oldest supported app version per platform from `MIN_APP_VERSION_IOS` / `MIN_APP_VERSION_ANDROID` / `MIN_APP_VERSION_WEB`, each falling back to `MIN_APP_VERSION` when unset or malformed (`x.y.z`; neither valid → `null`, no minimum), so a typo never lifts the global cutoff. Nothing reads `web` yet (`MIN_APP_VERSION` sets it too). Cached for 5 minutes (`Cache-Control: public, max-age=300, s-maxage=300`).
- `src/routes/profile.ts` — `GET /v1/profile` (`read`): `{ data: Profile }` (`age`, `gender`, `height`, `weight`, `measurement_system`, `units: { height, weight }`, from `getProfile`), or `{ data: null }` before onboarding. `PATCH /v1/profile` (`write`, `updateProfile`): any of `age` (integer 10–120), `gender`, `height` (0–300), `weight` (0–1000; both at most 2 decimals, in the resulting system's units) and `measurement_system`, strict (an empty body or an unknown field is 400 `invalid_request`, a non-JSON body 415); a new system converts every stored height and weight of the User, as the route's OpenAPI description says. Answers `{ data: Profile }`, or 404 `profile_not_found` with nothing written. `PUT /v1/profile` (`write`, `replaceProfile`): the whole Profile, strict, every one of those five fields required with the same bounds (an empty body, a missing or unknown field or an out-of-bounds value is 400 `invalid_request`, nothing written); without a Profile it creates one (201), with one it replaces it exactly as a `PATCH` with every field would (200: a different system converts every stored height and weight first). Both answer `{ data: Profile }`; a repeat is harmless. Every User-data response is parsed through its route's own schema before it goes out, so fields beyond the contract are stripped.
- `src/routes/plans.ts` — `GET /v1/plans` (`{ data: PlanSummary[] }`, live Plans newest first, each with its Workouts in rotation order as `{ id, name, order, exercise_count, cover }`; not paged), `GET /v1/plans/active` (the active Plan in full, or `{ data: null }`) and `GET /v1/plans/{id}` (the Plan in full; a missing, soft-deleted or another User's Plan → 404 `not_found`, a non-uuid id → 400 `invalid_request`), all `read`. A Plan in full has its Workouts, Exercises and sets each in order, every Workout with its `cover` (the id of its Library Cover, ADR 0014, `null` until one is assigned; server-assigned, so a body carrying it is 400 `invalid_request` like any unknown field), Exercises as `exercise_slug` only (no Library call, ADR 0011), plus `weight_unit` (`kg` / `lbs`); weights are as stored, never converted. `/active` is registered before `/{id}`, and its nullable Plan is an inline schema (OpenAPI 3.0 can't mark a `$ref` nullable). `POST /v1/plans` (`write`) creates a Plan in one transaction (`createPlan` with `{ activate }`): its metadata (`note` optional), Workouts in rotation order, Exercises by `exercise_slug` (apps/library' slug format) in order, sets (`reps_recommended` 1–`MAX_REPS`, `rest_recommended` 0–3600, `weight_recommended` 0–`MAX_WEIGHT` with at most 2 decimals, in the User's unit), each list at least one long and every object strict (MCP's bounds), plus `activate` (default `true`; `false` keeps the active Plan). Before the transaction every slug goes through one `lookup` (`checkSlugsAndPickCovers`, `src/library.ts`, `checkExerciseSlugs`' check, ADR 0010): unknown slugs answer 400 `unknown_exercises` naming them, unreported; the Library failing or unconfigured answers a reported 503 `library_unavailable`; nothing is written either way. That same lookup's muscle groups and one `covers()` call then give each Workout its `cover` through `pickCovers` (ADR 0014; `null` for each from a Library without Covers, and `covers()` failing is the same reported 503, nothing written). Answers 201 with the Plan in full, as `GET /v1/plans/{id}` shows it. No idempotency key: a retry can create a second Plan. `PUT /v1/plans/{id}/workouts` (`write`, `replaceWorkouts`) replaces every Workout of a live Plan with `{ workouts }` (strict; the same Workout schema as the create), in one transaction: every Workout gets a new id (documented in the OpenAPI description), past Workout Sessions keep their logged sets but lose the link (`workout: null`), and metadata and `is_active` stay. Its slugs and Covers go through the same `checkSlugsAndPickCovers` first (fresh Covers, none counted as used since every Workout is replaced; 400 `unknown_exercises` / reported 503, nothing changed); a missing, soft-deleted or another User's Plan → 404 `not_found`. Answers 200 with the Plan in full. `PATCH /v1/plans/{id}` (`write`, `updatePlan`): metadata only, any of the create body's fields but `activate` and `workouts` (`note: null` clears it), strict (`workouts`, any other unknown field or an empty body is 400 `invalid_request`), Workouts and their ids untouched; the Plan in full. `POST /v1/plans/{id}/activate` (`write`, `activatePlan`): the Plan becomes active, every other one of the User inactive; the Plan in full. `DELETE /v1/plans/{id}` (`write`, `deletePlan`): soft delete, 204 with no body, also for a Plan of the User's already deleted (a retry never fails); its Workout Sessions stay. On all three a missing or another User's Plan (and, for PATCH and activate, a deleted one) is 404 `not_found` with nothing changed, and a non-uuid id 400 `invalid_request`.
- `src/routes/workout-sessions.ts` — `GET /v1/workout-sessions` (`read`): `{ data: WorkoutSessionSummary[], total, hasMore, weight_unit }`, newest first, each with `exercise_count`, `set_count`, `logged_set_count`, `completed_rep_count` (reps over its logged sets; above 0 once a set has reps, the qualifying rule of `@fitme/core`'s `qualifiesForProgress`), `volume` (weight × reps over its logged sets in `weight_unit`, a set without a weight adding 0) and `personal_records` (`PersonalRecord[]`, the records it earned when it was finished, ADR 0015: `{ exercise_slug, kind, reps, weight }`, `kind` `weight` or `reps`, `weight` in `weight_unit`, 0 for bodyweight; empty for none); `status` (`all`, the default, `in_progress` or `finished`), `limit` (1–50, default 20) and `offset` (default 0; past the end is an empty page). `GET /v1/workout-sessions/{id}` (`read`): `{ data: WorkoutSession }`, its Exercises and sets in order, with `weight_unit` (`kg` / `lbs`, weights as stored); 404 `not_found` when it's missing or another User's, 400 `invalid_request` for an id that isn't a uuid (`Id` in `src/schemas.ts`: any 8-4-4-4-12 hex, as Postgres accepts). Exercises are `exercise_slug` only; every field beyond the contract is stripped by the response schema. The writes (each `write`): `POST /v1/workout-sessions` (`{ workout_id }`, strict; `startWorkoutSession`) answers the Workout Session in full, 201 when started and 200 when the one already open for that Workout is resumed (same body), 409 `session_in_progress` (unreported, nothing written, the message naming the Workout in progress) while another Workout's Workout Session is open (a User has at most one, ADR 0013), or 404 `not_found` for a Workout that's missing, another User's or of a soft-deleted Plan; `POST /v1/workout-sessions/{id}/finish` (`finishWorkoutSession`) answers `{ data: WorkoutSession, already_finished }` (`true` on a repeat, which changes nothing) and is documented as moving its Workout to the end of the Plan's rotation and awarding its Personal records, 404 `not_found`; `DELETE /v1/workout-sessions/{id}` (`deleteWorkoutSession`, a hard delete) answers 204 whether or not anything matched: under RLS a repeat, a missing id and another User's (left untouched) look the same, so all of them answer 204 and no id is revealed; `POST /v1/workout-sessions/{id}/exercises` (`addExerciseToWorkoutSession`, `{ exercise_slug }`, strict, the slug format of `POST /v1/plans` (`ExerciseSlug` in `src/schemas.ts`)) appends the Exercise, with no sets, after the Workout Session's last one and answers 201 `{ data: WorkoutSessionExercise & { weight_unit } }`; its slug goes through `checkExerciseSlugs` first (`slugRefusal` in `src/library.ts`, shared with the Plan writes: 400 `unknown_exercises` unreported / a reported 503 `library_unavailable`, nothing written), then 404 `not_found` for a missing or another User's Workout Session and 409 `session_finished` for a finished one, nothing written. No idempotency key: a retry can add the Exercise twice. `GET /v1/workout-sessions/{id}/plan-update` (`read`, `previewPlanUpdate`) and `POST /v1/workout-sessions/{id}/plan-update` (`write`, `applyPlanUpdate`, one transaction) answer `{ data: { plan, workout, changes, weight_unit } }` (`PlanUpdate`): each change by `kind` (`replace_exercise`, `add_exercise`, `remove_exercise`, `add_sets`) with its `exercise_slug` (and `replaced_exercise_slug`) only, no names (ADR 0011), and the sets it saves as `{ reps, weight }`, weights as stored; `plan` / `workout` inline and nullable, `workout` with its `cover`. A Workout Session without a Plan Update (open, no Workout, a soft-deleted Plan, a repeated `order`, over the caps, already applied) answers 200 with no changes, so a repeated or concurrent apply writes once; a missing or another User's one is 404 `not_found`.
- `src/routes/workout-session-exercises.ts` — the Workout Session Exercise edits, each `write`, each refusing a finished Workout Session with 409 `session_finished` and nothing changed: `DELETE /v1/workout-session-exercises/{id}` (`removeExerciseFromWorkoutSession`) removes the Exercise with its sets and leaves the others' `order` (the Plan Update matches by `order`, so the gap records the removal), answering 204 whether or not anything matched (a repeat, a missing id, another User's left untouched), like `DELETE /v1/workout-sessions/{id}`; `PUT /v1/workout-session-exercises/{id}` (`replaceExerciseInWorkoutSession`, `{ exercise_slug }`, strict) runs the slug through `checkExerciseSlugs` first (`slugRefusal`: 400 `unknown_exercises` / a reported 503, nothing changed), then swaps it in place and zeroes every set's `reps_recommended` and `weight_recommended` in one transaction (the row, its `order` and the logged values stay), answering 200 `{ data: WorkoutSessionExercise & { weight_unit } }`, or 404 `not_found` for a missing or another User's one; `POST /v1/workout-session-exercises/{id}/sets` (`addSetToWorkoutSessionExercise`, `{ reps_completed, weight_completed }`, strict, the bounds of `PATCH /v1/workout-session-sets/{id}`) appends a set after the Workout Session Exercise's last one, logged on creation (`logged_at` the server's) and with no targets, answering 201 `{ data: WorkoutSessionSet & { weight_unit } }`, or 404 `not_found` for a missing or another User's one; there's no route creating an unlogged set, and no idempotency key (a retry adds another set). `WorkoutSessionExercise`, its write response, the `session_finished` answer and the set body and response (`LoggedSet`, `WorkoutSessionSetResponse`, shared with `PATCH /v1/workout-session-sets/{id}`) live in `src/schemas.ts`, shared with `POST /v1/workout-sessions/{id}/exercises`.
- `src/routes/workout-session-sets.ts` — `PATCH /v1/workout-session-sets/{id}` (`write`, `logSet`): `reps_completed` (0–`MAX_REPS`) and `weight_completed` (0–`MAX_WEIGHT`, at most 2 decimals, in the User's unit), strict. Answers `{ data: WorkoutSessionSet & { weight_unit } }`, 409 `session_finished` for a set of a finished Workout Session (nothing written) or 404 `not_found` for a set the User doesn't have, both unreported.
- `src/routes/weekly-goals.ts` — `GET /v1/weekly-goals` (`read`, `getWeeklyGoals`): `{ data: [{ recorded_at, target }], streak }`, every change of the User's Weekly goal (ADR 0015) oldest first, unpaged; `target` the active Plan's frequency, `null` once no Plan is active. The services record them (see `packages/services`' `weekly-goals.ts`); the OpenAPI description says how a client turns them into weeks. Optional `time_zone` is the device IANA timezone (UTC by default); `streak` counts consecutive goal-hit weeks across all retained history, preserves a pending current week and breaks on completed missed/unknown weeks.
- `src/routes/arnold-models.ts` — public, unauthenticated `GET /v1/arnold/models`: `{ data: { models: [{ id, label, description }], defaultId } }`, straight from `arnoldModels` and `defaultArnoldModelId` in `@fitme/core` (list order; no other fields per model), so it always matches what Arnold accepts. No auth: the list isn't secret, Arnold's channel does the gating. Cached for 5 minutes like `client-config`.
- `src/routes/muscle-groups.ts` — public, unauthenticated `GET /v1/muscle-groups` (`{ data: [{ id, name }] }`, every muscle group from `@fitme/core`) and `GET /v1/muscle-groups/{muscleGroup}` (`{ data: { id, name } }`, or 404 `not_found`).
- `src/backfill-covers.ts` (`pnpm api backfill:covers [--dry-run] [--plan <id>]…`, entry `scripts/backfill-covers.ts`) — the one-off Cover backfill (ADR 0014, run once on production after Covers are published): every Workout of a live Plan without a Cover gets one through `withService`, one Plan per transaction, picked by `pickCovers` with the Plan's existing Covers as used, from one `covers()` and one `lookup` (the Public API's `LIBRARY_PUBLIC_API_SECRET`). Refuses to run without Covers; a Workout with a Cover is never changed, so a rerun writes nothing; a dry run counts per Plan, writes nothing and takes no locks; output is Plan ids and counts only. `FITME_DATABASE_URL` carries `application_name=backfill`. How to run it: `apps/api/README.md` (Cover backfill); `integration/backfill-covers.test.ts` scopes every run to its own Plans.
- `src/openapi.ts` (`pnpm openapi`) — writes the committed `openapi.json` from the route definitions (not served). `/v1` is additive only: a breaking change means `/v2`. The Public API workflow (`.github/workflows/public-api.yml`, pull requests touching `apps/api`, `packages/core`, `.github/oasdiff`, `apps/mobile/lib/api` or `apps/mobile/package.json`) fails when `openapi.json` is stale, then when the mobile app's types generated from it (`apps/mobile/lib/api/schema.ts`, `pnpm mobile api:types`) are, runs `.github/oasdiff/check-api-breaking.sh apps/api/openapi.json` (the same check, rules and allowlist as `apps/library`; here the allowed response enum addition is a new muscle group as the `id` of `/v1/muscle-groups`), builds the app and checks `dist/app.js` imports `hono`. A deliberate removal follows `apps/library`' process.
- Tests (`src/__tests__/`, vitest) drive `createApp` through `app.request` (`src/test/harness.ts`: `testApp` with Clerk session tokens signed by a test RSA key (`src/test/clerk.ts`), `fakeServices` where an unfaked method fails the request, the fake Library over `KNOWN_SLUGS` (`library.failWith` for an outage, `library: null` for none), a recording `reportError` and `identifyUser`, and the User id each facade was built for), so they need no Sentry or database. `integration/` (separate vitest config, `test:integration`) runs the same seam with the real facade against the local stack's pooler (URL from `supabase status`, like `apps/mcp`; `FITME_DATABASE_URL` overrides), as made-up Clerk-style `user_…` ids with test-signed tokens; CI runs it in the integration-tests workflow. Its files run in parallel and clean up through `deleteTestUsers` (`@fitme/services/delete-test-users`, see `packages/services`).
- `tsdown.config.ts` — source maps for the Vercel build, uploaded for the release `VERCEL_GIT_COMMIT_SHA` with `SENTRY_AUTH_TOKEN` and skipped without it, exactly as in `apps/webhooks`; `apps/api/turbo.json` hashes `VERCEL_GIT_COMMIT_SHA` into the build.

### apps/webhooks — webhooks app

Hono app served with `@hono/node-server`, bundled with tsdown (same setup as `apps/api`), that receives every third-party webhook. It reaches Postgres only through `withService` from `@fitme/db` and runs business logic from `@fitme/services`.

- `src/app.ts` — the Vercel entry (`dist/app.js`): imports `hono` (Vercel's Hono preset requires it), calls `initObservability({ service: "webhooks" })` and `reportMissingEnv` with `src/required-env.ts`' list (`CLERK_WEBHOOK_SIGNING_SECRET`, `FITME_DATABASE_URL`, `ARNOLD_URL`, `ARNOLD_RESET_SECRET`), then loads `create-app` with a dynamic `import()` so `pg` and the rest load after observability has started and get instrumented (see `packages/observability`), and default-exports `createApp()`.
- `src/create-app.ts` — `createApp({ clerk, reportError })` (no argument = the real dependencies): `observeHono(app)` first (request spans), logger, public `/health`, one route per sender, and the same JSON `notFound`/`onError` handlers as `apps/api` (`{ error: { code, message } }`); `onError` reports every unhandled error before the 500, an `HTTPException` answers its status unreported. `reportError` is `@fitme/observability/node`'s, shared by the routes and `onError`.
- `src/routes/clerk.ts` — `POST /clerk`, `clerkRoutes({ deleteArnoldConversations, deleteUserData, reportError, signingSecret })`: verifies the Svix signature with `verifyWebhook` from `@clerk/backend` on the raw request before anything reads the body (401 otherwise; an unset `CLERK_WEBHOOK_SIGNING_SECRET` answers a reported 500 so Clerk retries). `user.deleted` runs `deleteUserData` through `withService`, then (once that has committed) `deleteArnoldConversations`; a failure of either is reported and answers 500 so Clerk retries. Other events answer 200. No `svix-id` dedupe: both steps are idempotent; a webhook that isn't must dedupe on `svix-id`.
- `src/arnold.ts` — `deleteArnoldConversations({ listSessionIds, resetSession })`: lists the User's recorded Arnold session ids (`listArnoldSessionIds` in `withService`: the id is retired by then) and resets each (five at a time); any failed reset fails the call (an `AggregateError`, first failure as its `cause`). The `arnold_sessions` rows stay as tombstones (see `packages/services`). No recorded sessions → no call to Arnold at all. `arnoldSessionResetter({ arnoldUrl, secret })` posts `ARNOLD_URL/eve/v1/session/:id/reset` with `Bearer ARNOLD_RESET_SECRET`, both read by `arnoldResetConfig(env)`; eve answers `reset`, or `no_active_session` for one already reset, expired or unknown, so a retry is harmless; anything else (or either one unset) throws.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3004).
- Tests (`src/__tests__/`, vitest) drive `createApp` through `app.request` with payloads signed by a test secret (`standardwebhooks`), a fake `reportError` and fake dependencies, so they need no database or Sentry.
- `tsdown.config.ts` — the Vercel build (`dist/app.js`) emits source maps and runs `sentryRollupPlugin` from `@sentry/node/rollup`: with `SENTRY_AUTH_TOKEN` it uploads them to `SENTRY_ORG` / `SENTRY_PROJECT` for the release `VERCEL_GIT_COMMIT_SHA` and deletes the `.map` files; without it (local, CI) it injects debug ids, keeps the maps and skips the upload, and the build still succeeds. A failed upload is logged and never fails the build. `apps/webhooks/turbo.json` hashes `VERCEL_GIT_COMMIT_SHA` into the build, so a commit never replays another commit's `dist/` (and skips its upload).
- Deployed to Vercel as its own Pro project, region `cle1` (`vercel.json`), reporting to the `fitme-webhooks` Sentry project. `FITME_DATABASE_URL` carries `application_name=webhooks`. Its `/clerk` endpoint is registered for `user.deleted` on both Clerk instances, each with its own signing secret in the matching Vercel environment.

### apps/library — Library API

The Library API: a Hono app built on `@hono/zod-openapi` (zod 4), served with `@hono/node-server` and bundled with tsdown (same setup as `apps/webhooks`), that serves the Library (ADR 0007, ADR 0008; the spec is the Linear project "Library API"). The content lives in the private `kprovorov/fitme-exercises` repo, which publishes it as a `library.json` bundle; the build bakes the bundle in, so nothing is read from disk, a database or the network at runtime: the deployment is the data. The monorepo is going public: never commit real Exercise content here, only the made-up fixture.

- `src/app.ts` — the Vercel entry (`dist/app.js`), the `apps/webhooks` pattern: imports `"hono"` (Vercel's Hono preset requires it), calls `initObservability({ service: "library" })`, then loads `create-app`, the generated library and the rate limiter with dynamic `import()`s so they load after observability has started, and default-exports `createApp` with the real env, the generated library and `@fitme/observability/node`'s `identifyUser` and `reportError`.
- `src/create-app.ts` — `createApp({ auth, identifyUser, library, rateLimiter, reportError })`: `observeHono(app)` first (request spans), logger, CORS (`origin: "*"`, before auth, so preflights answer without a token and every response is readable cross-origin; ADR 0007), public `/health`, then `requireCaller` on every other route (unknown ones included), `identifyUser(sub)` for a User (the Sentry user is the Clerk id only; a server caller sets none), `rateLimitUsers`, `deviceCache` on `/exercises/*` and `/covers`, the routes, and the same JSON `notFound`/`onError` handlers as `apps/api` (`{ error: { code, message } }`).
- `src/routes/exercises.ts` — every route takes an optional `language`, one of the App languages from `@fitme/core` (`Language` in `src/schemas.ts`), default `en`; anything else (`de`, an empty value) is 400 `invalid_request` naming the field, and without it the answers are English as before. An Exercise with no translation in that language is answered wholly in English (name, description and instructions together), never field by field. `GET /exercises`: alphabetical by name in that language with its collation (ties by slug), `search` (case-insensitive substring of the name in that language or of the English name, trimmed, `%`/`_` literal, at most 100 characters), `muscle_group` or `muscle_groups` (comma-separated, an Exercise with any of them, a repeat counted once; an unknown group, an empty item or both together is 400), `limit` (1–50, default 20), `offset` (default 0) → `{ data: ExerciseSummary[], total, hasMore }` (an offset past the end is an empty page). With `slugs=a,b,c` (at most 40, repeats answered once; not combined with the list parameters, `language` aside) it's a batch lookup → `{ data, missing }` in asked order, no 404. `GET /exercises/:slug` → one `Exercise`, or 404 `not_found`. Invalid query → 400 `invalid_request`.
- `src/routes/covers.ts` — `GET /covers` → `{ data: Cover[] }` (`id`, `muscle_groups`, `image_url`), every Cover in bundle order, unpaged (`{ data: [] }` for a bundle without Covers); no `language`, since Covers have no text. `src/routes/shared.ts` holds what every content route declares: the 401 and 429 responses, `security` and the `invalid_request` hook.
- `src/schemas.ts` — every response from one field definition (`summaryFields`): `ExerciseSummary` (`slug`, `name`, `muscle_groups`, `thumbnail_url`, `video_url`) and `Exercise` (plus `description`, `instructions`, markdown). Add a field there. `Cover` and `CoverList` are `GET /covers`' answer. `MuscleGroup` is `z.enum(muscleGroups)` from `@fitme/core` (core stays zod-free), the only list in the app.
- `src/auth.ts` — `requireCaller`: `Authorization: Bearer` is first compared (as sha256 digests, constant time) with `LIBRARY_PUBLIC_API_SECRET` (the Public API, `apps/api`), `LIBRARY_ARNOLD_SECRET` (the caller `arnold`) and `LIBRARY_MCP_SECRET` (unset or under 32 characters accepts nothing; `serverSecretsFromEnv` reads only these names, never the pre-rename `EXERCISES_*` ones) → a server caller; otherwise it must be a Clerk session token (with a `sid`) verified networkless against `CLERK_JWT_KEY_PRODUCTION` or `CLERK_JWT_KEY_DEVELOPMENT`, either one → the User (`sub`). Anything else → 401 `unauthorized`. No Pro gate: the Library is free content.
- `src/rate-limit.ts` — `rateLimitUsers`, after `requireCaller` on every route: each User (Clerk `sub`, the bucket key) gets 120 requests per minute (a fixed window), server callers aren't counted. Over the limit → 429 `rate_limited` with `Retry-After` (seconds), before anything is served (a 304 counts too). The limiter itself is `@fitme/rate-limit` (see there): the file only sets the limit, the window and the Upstash prefix `library:user` (`memoryRateLimiter` / `rateLimiterFromEnv` here are the package's with those filled in; `USER_LIMIT` holds them, and tests pass `memoryRateLimiter` a small `limit` so no test sends 120 requests), and maps a refusal to the 429. The `RateLimiter` comes through `createApp`, from `rateLimiterFromEnv` (Upstash in production, in memory outside it without Upstash, a startup failure in production without it); a limiter that throws or takes over 1 s serves the request uncounted (fail open) and is reported. The per-IP backstop is a Vercel Firewall rule, configured by hand.
- Errors and traces go through `@fitme/observability` (no Sentry code of its own): `reportError` is injected through `createApp`, like `apps/webhooks`'; `onError` reports every unhandled error, then answers the JSON 500, and `rateLimitUsers` reports a failing limiter. Reporting to the `fitme-library` Sentry project (`SENTRY_DSN`; unset → logs only, nothing sent).
- `tsdown.config.ts` — the Vercel build (`dist/app.js`) emits source maps and runs `sentryRollupPlugin` from `@sentry/node/rollup`, as `apps/webhooks`' does: with `SENTRY_AUTH_TOKEN` it uploads them for the release `VERCEL_GIT_COMMIT_SHA` and deletes the `.map` files; without it it skips the upload and the build still succeeds; a failed upload is only logged. The `build` is uncached anyway (see `src/generate.ts`), so it needs no `VERCEL_GIT_COMMIT_SHA` in its turbo hash.
- `src/cache.ts` — `deviceCache`: a 200 under `/exercises/*` or at `/covers` gets `Cache-Control: private, max-age=3600` and the library hash as its `ETag`; a matching `If-None-Match` (weak comparison, or `*`) answers 304 with no body. Runs after auth, so a 304 only goes to a caller; errors stay uncacheable.
- `src/bundle.ts` — the zod schema of `library.json` version 1, the contract with `fitme-exercises`: `{ version: 1, exercises: [{ slug, muscle_groups, locales: { en: { name, description, instructions }, uk?: { … } }, thumbnail: { oid, extension }, video: { oid, extension } }], covers?: [{ id, muscle_groups, image: { oid, extension } }] }`. `covers` (ADR 0014) is optional, so a bundle without it stays valid; each Cover is strict, with no locales and no alt text: `id` a lowercase uuid, unique among Covers, at least one known muscle group with no repeats, and an image of `jpg`/`png`/`webp` with a sha256 oid. `locales` is built from the App languages in `@fitme/core`: `en` required, every other one (`uk` so far) optional, each with exactly the same three fields (a non-blank `name`). Strict: an unknown field, a locale that isn't an App language (`de`), a wrong `version`, an invalid or repeated slug, an unknown or repeated muscle group, a bad oid (sha256 hex) or an extension other than `jpg`/`png`/`webp` (thumbnail) or `mp4` (video) fails the build. No URLs: a media object's path is `<slug>/<oid>.<ext>` on both sides, a Cover's image `covers/<id>/<oid>.<ext>`. A new muscle group goes into `muscleGroups` in `@fitme/core` first, then into the content.
- `src/served-library.ts` — `serveLibrary(bundle, supabaseUrl)`: the Library per App language (`languages`), each worked out once here: every Exercise as its response object in that language (wholly English without a translation), sorted by that name with the language's collation (ties by slug), media resolved on the `exercise-media` bucket (`thumbnail_url` through the image transformation `render` endpoint, so clients append `width`/`height`; `video_url` the public object URL), and the search index (each Exercise's lowercased served name and English name); every Cover in bundle order as `{ id, muscle_groups, image_url }` (`image_url` on the render endpoint, like `thumbnail_url`); plus the sha256 of the Covers and every language's answers (the `ETag`, one for every URL, so it stays valid per URL with the language in it).
- `src/generate.ts` (`pnpm generate`) — gets the bundle, validates it (`src/build/library-module.ts`; every problem names the bundle and the field, and exits 1) and writes the git-ignored `src/generated/library.ts`. Which bundle: a production build (`VERCEL_ENV=production`) fetches `library.json` from the private Vercel Blob store (`get("library.json", { access: "private", useCache: false })` from `@vercel/blob`, uncached so it gets the version just published), authenticated through Vercel OIDC (`VERCEL_OIDC_TOKEN` plus `BLOB_STORE_ID`, both set by Vercel once the store is connected; no Blob token on the project). If OIDC isn't available during the build, the fallback is a `BLOB_READ_WRITE_TOKEN` on the project (Production, Sensitive), which the SDK picks up by itself. A missing store, a missing blob, a failed fetch or an invalid bundle fails the build: production never falls back to the fixture. Every other build reads the bundle at `LIBRARY_BUNDLE` (absolute or relative to `apps/library`; default the committed fixture `fixtures/library.json`, made-up Exercises only) and never calls Blob (a preview build would too, but no previews deploy). The build log names the bundle, its Exercise and Cover counts and the library hash (the `ETag`), so a deployment's content can be identified from it. `SUPABASE_URL` must be the project's https origin; it's required on Vercel (`VERCEL` set), and unset anywhere else the media URLs point at a placeholder project. `build`, `dev`, `typecheck` and `test` all run `generate` first (in their scripts, so with or without turbo). Its turbo `build` is never cached and passes the Blob variables through (`apps/library/turbo.json`): turbo would hash the `LIBRARY_BUNDLE` path, not the bundle, and can't see Blob at all, so it would replay a stale library.
- `src/openapi.ts` (`pnpm openapi`) — writes the committed `openapi.json` from the route definitions (not served). No version prefix, so changes are additive only. The Library API workflow (`.github/workflows/library-api.yml`, pull requests touching `apps/library`, `packages/core` or `.github/oasdiff`) fails when `openapi.json` is stale, runs `.github/oasdiff/check-api-breaking.sh apps/library/openapi.json` (oasdiff against the base branch's copy, found at its old path through git's rename detection when the spec moved, shared with `apps/api`: every removal fails, errors and warnings alike, `.github/oasdiff/severity-levels.txt` raising the info-level ones; the one allowed response enum addition is a new muscle group in `muscle_groups`), builds the app and checks `dist/app.js` imports `hono`. **Deliberate removal:** only after the minimum version gate has cut off every build that reads the field; in the removal PR copy each line the check prints (without the `[check id]`) into `.github/oasdiff/allowed-breaking-changes.txt`, say which minimum app version made it safe, and empty the file again once the removal is on `main`. Never loosen the check another way.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3006). `dev` and `generate` load `apps/library/.env` if it exists.
- Tests (`src/app.test.ts`, `src/build/library-module.test.ts`, vitest) drive `createApp` through `app.request` with fixture Exercises, Clerk tokens signed by test RSA keys (`src/test/clerk.ts`), test secrets, a fake reporter and fake limiters (the in-memory one on a fake clock), and the bundle validation on fixture bundles (valid, the committed fixture, unknown muscle group, wrong `version`, invalid slug, …).
- `vercel.json` — region `cle1`, `outputDirectory: dist`, `git.deploymentEnabled` `{ "**": false, "main": true }` (Vercel deploys a branch when any matching rule is true, and `**` also matches branch names with `/`), so only `main` deploys and there are no previews. No `ignoreCommand`: see CI/CD. The Vercel project, domain (`library.fitmeproject.com`) and media bucket are FIT-179.

### apps/arnold — Arnold (EVE)

Arnold as an [EVE](https://www.npmjs.com/package/eve) agent (ADR 0005) whose model calls go through Vercel AI Gateway (ADR 0006), which replaced the `ai-agent` edge function (since removed). EVE is in preview: it is pinned to an exact version; read its changelog on every bump. Its docs ship in the package (`node_modules/eve/docs/`, start at `README.md`; the `eve` agent skill points there). EVE is filesystem-first: every file under `agent/` is discovered by its path, so put helpers in `agent/lib/` and tests in `test/`. Needs Node 24: `engines.node` is `24.x`, so Vercel never moves it to a new major on its own.

- `agent/agent.ts` — `defaultTools: false` (no shell, file or web tools; `eve info --json` lists what the model gets), Conversations end 30 days after they start (`limits.sessionTimeoutMs`; an ended run's data is kept for the plan's default period through `experimental.workflow.retention: "default"`: without it, eve 0.80+ deletes a private or unknown-audience session's run data as soon as its run ends outside development, and account deletion relies on a reset session's stream outliving the reset), and the model is resolved on every `step.started` by `arnoldModelSelection` (`agent/lib/models.ts`): the client sends `clientContext: { model, language }` per turn, eve hands it to the resolver (and the model) as a `context.instruction` user message (`Client context:` + JSON), and the id must be in `arnoldModels` from `@fitme/core`, the only list (none → `defaultArnoldModelId`; anything else, pre-Gateway ids like `gpt-5.5` included, fails the turn). Arnold's model ids are the Gateway's own (`openai/gpt-5.5`, `anthropic/claude-haiku-4.5`), so the selection returns the id and eve routes the call through AI Gateway (credits; Vercel OIDC deployed, `AI_GATEWAY_API_KEY` locally), with `providerOptions.gateway.order` listing the hosts of that same model (OpenAI → Azure → Bedrock, Anthropic → Bedrock → Vertex) so a failed call moves to another host, never another model. No `promptCacheKey` (OpenAI caches automatically); eve sets the Gateway `sessionId` per Conversation itself.
- `agent/instructions.md` — the system prompt, carried over from `ai-agent`. It names Arnold as Fitme's AI and carries the real-person rule of ADR 0012, which `evals/persona.eval.ts` checks, and the language rule: reply in the language of the User's message, and when it doesn't make that clear in the App language (the client context's `language`; missing or not an App language → English, never a failed turn), which `evals/reply-language.eval.ts` checks. The model selection ignores `language`; the tools read it (below).
- `agent/channels/eve.ts` — the eve HTTP channel (`/eve/v1/session…`) behind `accountDeletionReset()` (`agent/lib/reset-auth.ts`) then `clerkSession()` (`agent/lib/clerk-auth.ts`), then `evalRunner()` (`agent/lib/eval-runner.ts`), which admits only on the dev server a local `eve eval` boots (`EVE_EVALUATION` and `EVE_DEV` set, never on Vercel): eve's `local-dev` principal with `allowToolStubs`, never a Clerk User, so tools refuse to act for it, and `admitTurn` lets its turns run without recording the session. `accountDeletionReset` accepts `Bearer ARNOLD_RESET_SECRET` (compared in constant time; unset or under 32 characters accepts nothing) as the `service` principal `account-deletion` on `POST /eve/v1/session/:id/reset` only, and answers 403 for it anywhere else; any other bearer moves on to `clerkSession`: a Clerk session token verified networkless against `CLERK_JWT_KEY`; its `sub` becomes the session principal (`authenticator: "clerk"`). Missing or bad token → 401; missing key → 500, reported once per instance (eve only logs what a channel throws). Then the Pro check (every route, before the session claim): `createProCheck` (`agent/lib/pro-access.ts`) asks RevenueCat's v1 REST API (`GET /v1/subscribers/:id` with `REVENUECAT_SECRET_KEY`) whether the caller's Clerk id (the id `auth-sync` identifies to RevenueCat) has the active `proEntitlement` ("Fitme Pro", from `@fitme/core`) (lifetime or within its billing grace period counts), caching each answer per User for 5 minutes in the instance (a Pro answer no longer than the entitlement lasts; failures aren't cached). Not Pro → 403 `{ ok: false, code: "arnold_pro_required" }` (the app's paywall); RevenueCat failing or taking over 5 s, an unreadable answer or a missing key → reported 503 `arnold_pro_check_unavailable`, never let through (both `arnoldErrorCodes` in `@fitme/core`). EVE's route auth has no session ownership, so any route addressing a session (`/eve/v1/session/:id…`: messages, stream, cancel, clear, compact, reset) claims it through `claimSession` (`agent/lib/claim-session.ts`: `recordArnoldSession` as the caller in `asUser`, a no-op if it's recorded already, then `getArnoldSessionOwner` in `withService`) and answers 403 unless it is recorded for the caller. EVE gives the channel no session id at creation, so the creator's first request addressing it records it; a failed recording fails the request, never lets anyone in. No `localDev()`, so local requests need a token too. Clerk tokens never go past the channel. `/eve/v1/health` is public.
- `agent/lib/owner.ts` — the Conversation owner is the session's `auth.initiator` (the verified caller who started it): the only User id tools act as. Route auth doesn't check session ownership, so `agent/hooks/conversation.ts` cancels a `turn.started` whose caller isn't the owner, and claims the session for the owner (the same `claimSession`, every turn) before the model runs; a session recorded for someone else, or a failed recording, is reported and cancels the turn (account deletion needs every session id to reset it).
- `agent/hooks/turn-limits.ts` — caps per turn (`agent/lib/turn-limits.ts`): 20 model steps and $1.00 of model cost (the `costUsd` AI Gateway reports on each `step.completed`, summed per turn; ADR 0006). The `step.started` past either cap cancels the turn; the last call can overshoot the budget by its own cost, and EVE's retries of a step (up to 4, same `stepIndex`, state restored) aren't counted. A finished step that reports no cost fails closed: it is reported to Sentry and the next `step.started` cancels the turn. eve's own `limits.max*PerSession` (`maxTokenCostUsdPerSession` included) are per session and prompt the user to continue, so they aren't used.
- `agent/hooks/failures.ts` — `step.failed`, `turn.failed` and `session.failed` are reported with their session and turn ids. Every report in Arnold (those, a missing step cost, the owner and session-claim guards, the Pro check) goes through `reportError` from `@fitme/observability/node` to the `fitme-arnold` Sentry project, with `environment` and the commit as `release`; `agent/instrumentation/sentry.ts` starts it once at server startup (eve's provider `setup`) with `tracing: false`, so the Sentry SDK neither traces nor sends trace headers, then runs `reportMissingEnv` with `agent/lib/required-env.ts`' list (`CLERK_JWT_KEY`, `REVENUECAT_SECRET_KEY`, `FITME_DATABASE_URL`, `LIBRARY_URL`, `LIBRARY_ARNOLD_SECRET`, `ARNOLD_RESET_SECRET`). `SENTRY_DSN` unset → logs only.
- Traces (`agent/instrumentation/`): eve's own OpenTelemetry. `otel.ts` sets `deployment.environment` from `VERCEL_ENV` and the process-wide `arnoldTracePolicy` (`agent/lib/trace-export.ts`): no Conversation content (prompts, tool arguments, answers, tool results) in any span outside local development, whatever the audience, so Vercel Agent Runs gets metadata only too. `sentry-traces.ts` is the Sentry destination: `otelIntegration()` with `OTLPHttpProtoTraceExporter` (`@vercel/otel`) to `SENTRY_OTLP_TRACES_URL`, authenticated with the DSN's public key (`x-sentry-auth`); without that URL or `SENTRY_DSN` (local dev, evals, tests) it is `disableInstrumentation()` and nothing is exported. Its `sentryExportPolicy` redacts every span's inputs and outputs, then keeps only an allowlist of metadata attributes (turn and step structure, model ids, `*.usage.*` tokens and cost, tool names, timings, `error.type`): an attribute a later eve or AI SDK adds stays out until it's listed there.
- Source maps: `nitro.config.ts` (`sourcemap: true`, read by the nitro build `eve build` runs) makes the server bundle emit them, and `scripts/upload-source-maps.ts` (run by `build` after `eve build`) injects debug ids and uploads them with `sentry-cli` for the release `VERCEL_GIT_COMMIT_SHA` (`SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT`), then deletes them; without the token it skips, and a failed upload is logged, never fails the build. `sentry-cli` only sees a staged copy (in the temp directory) of the scripts that have a `.map` beside them, with their maps: pointed at the build output it would walk every route function (each a symlink to `__server.func`) and warn for every chunk without a map (FIT-334), and it skips dot directories, so the copy stages `.well-known/workflow/v1/flow.func` (eve's workflow function) as `well-known/…`. The injected scripts are copied back over the output's before the upload. Authored code maps to eve's compiled module map (readable, unminified JS), not to the `.ts` files: eve compiles it without source maps.
- `agent/tools/` — one file per tool, the filename is the tool name, ported 1:1 from `ai-agent` (names, inputs, descriptions). Each is a thin wrapper: `asUser(owner, (tx) => service(tx, owner, …))` with `owner` from `requireConversationOwner(ctx.session.auth)`; tool inputs never carry a User id (their zod schemas strip unknown keys). So far: `get_user_profile` → `getProfile`, `activate_plan` → `activatePlan`, `update_user_profile` → `updateProfile`, `get_active_plan` → `getActivePlan` (`{ error: "No active plan found" }` without one), `get_plans` → `listPlans`, `get_workouts_history` → `listWorkoutHistory` (`limit` 1–20, default 10), `search_exercises` → the Library API's `list` (no database; first 8 matches as `{ exercise_slug, name, muscle_groups }`; `muscle_group` one of `muscleGroups`; in the App language, so it matches the Ukrainian or English name and answers Ukrainian names), the Plan edits `add_exercise_to_workout`, `remove_exercise_from_workout`, `replace_exercise_in_workout`, `add_set_to_exercise`, `remove_set_from_exercise` and `update_set_recommendations` → the matching `@fitme/services/workout-edits` function (row ids are uuids, Exercises are `exercise_slug` / `new_exercise_slug`; set targets and set counts have MCP's plan bounds, reps and weight from `@fitme/core/limits`, the rest in `agent/lib/workout-edits.ts`; an Exercise already at its set limit or a missing row is an `{ error }` result; a remove that finds nothing says it may already have been removed, since a re-run step repeats it; the two appends pass `requestKey(ctx, input)` from `agent/lib/request-key.ts`: a hash of the session, turn, the step's message count, the tool, its input and the call's position among identical calls of the same step execution (told apart by the `ctx.messages` array, which the AI SDK shares across one execution's tool calls and a re-run rebuilds), so a re-run step, which repeats the model call under new `callId`s, finds the rows the first run added, while two identical calls in one step still add two rows), and `display_workout_plan` (returns its input; the app renders every successful result as the plan card, so its schema is the app's contract and a refusal is a thrown tool error, never an `{ error }` result; writes nothing). Exercises (FIT-239; project "Exercises off Postgres", ADR 0010): tools refer to them by Exercise slug only, through the `@fitme/library-sdk` client (`agent/lib/library.ts`: `getLibrary()`, `LIBRARY_URL` with `LIBRARY_ARNOLD_SECRET`; tests swap in the fake). The App language is the turn's client context `language`, which a tool reads from `ctx.messages` (the step's model input, where eve puts the client context as a `context.instruction` message, the same one the model resolver reads) through `agent/lib/client-context.ts` (`appLanguage`; missing or not an App language → English, which is never sent: the Library API's default); searches and names use it, slug checks don't. `agent/lib/exercises.ts` holds the two rules: `checkExerciseSlugs` runs one `lookup` before any `asUser` in every tool taking a slug (`add_exercise_to_workout`, `replace_exercise_in_workout`, `display_workout_plan`): an unknown slug, or a uuid-shaped one from an older Conversation, is an `{ error }` sending the model to `search_exercises`, and a library failure an `{ error }` asking to retry (reported); nothing is written either way. `withExerciseDetails` names the Exercises of `get_active_plan` and `get_workouts_history` (`name`, `muscle_groups` next to `exercise_slug`) through one `lookup` after the transaction, in the App language; a slug the library doesn't know, or every slug when it fails (reported), gets a name made from the slug and no muscle groups, so reads always answer.
- `evals/` — `eve eval` evals (`*.eval.ts`, `evals.config.ts`): the common asks (show my plan, last week's sessions, find a chest exercise, propose a plan, a general question, the persona, the reply language) against a real model, every read tool and `display_workout_plan` stubbed from `evals/fixtures.ts` per session (`t.session({ stubs: readToolStubs })`; Exercises by slug, as the tools show them). Local only: a remote `--url` target has no eval authenticator.
- `agent/sandbox.ts` — just-bash (in-process, nothing to build or pay for): eve prepares a sandbox even though no tool uses one.
- `eve build` bundles the source-only `@fitme/*` packages into `.output/` itself. `FITME_DATABASE_URL` carries `application_name=arnold`.
- Tests (`test/`, vitest) call the pure functions and the tools' `execute` directly: channel auth through `routeAuth` with tokens signed by a test RSA key (Pro check faked), the Pro check with RevenueCat faked through an injected `fetch` and clock (cache window and timeout included), the eval runner's env gate, model selection, turn limits, the trace export policy (metadata kept, content dropped) and the Sentry OTLP config, the owner/turn guard, and each tool with `@fitme/db` and its service mocked (`test/tool-context.ts` fakes a session owned by a Clerk User).

### apps/mcp — MCP server

Stateless [Streamable HTTP](https://modelcontextprotocol.io) MCP server built on Hono + `@modelcontextprotocol/sdk`, served with `@hono/node-server`.

- `src/server.ts` — composition root: `createMcpServer({ context })` (`context` = the request's `ToolContext`, built by the HTTP layer from a verified Clerk User) registers the tool groups from `src/tools/` (`registerTool` with zod input schemas, `title`, and read-only/destructive/idempotent `annotations`).
- `src/tools/` — `catalog.ts` (catalog tools from `@fitme/core`: ping, muscle groups, plan options; they still need a token like every other tool), and user tools in `exercises.ts`, `plans.ts` (+ `plan-schemas.ts`), `sessions.ts`, `profile.ts`; page bounds in `limits.ts` (set bounds from `@fitme/core/limits`). `helpers.ts` holds `asJson`, `requireFound`, `withToolErrors` and `withServices` (`withToolErrors` plus the caller's services; a failure becomes an `isError` result: a `ToolError` (not found, not configured) shows its message unreported, anything else (a Postgres error, an unknown exception) goes to the context's `reportError` first (as is: `@fitme/observability/node`'s `reportError` strips a query failure's SQL, parameters and Postgres message) and shows the Postgres message, never the SQL, or a generic one). Invalid input is rejected by the SDK before the handler runs, so it's never reported either. Every write reads its result back in its own transaction, so no tool returns a `warning`. `library.ts` is how tools reach the Library (ADR 0010): `fromLibrary` (searches, `get_exercise`, write checks: a library failure is reported, then the `ToolError` "Library unavailable, try again."), `requireKnownSlugs` (one `lookup` before the services' transaction; unknown slugs are a `ToolError` naming them, unreported, and nothing is written) and `lookupForRead` / `namedPlan` / `namedSession` (after the transaction, the slug's `name` and `muscle_groups` added next to it; an unknown slug, or the library failing (reported) or unconfigured, gets `exerciseNameFromSlug`'s name and no muscle groups, and the read still answers).
- `src/context.ts` — `createToolContext({ user, reportError, createServices?, createLibrary? })`: per-request `ToolContext` for a verified Clerk User, carrying the app's `reportError` for `withServices` and `getLibrary()`, the `@fitme/library-sdk` client (`src/library.ts`: `LIBRARY_URL` with `LIBRARY_MCP_SECRET` as the bearer; either unset is the "not configured" tool error, unreported). `getServices()` returns the `UserServices` (`src/services.ts`) built for `user.userId`, each method running one `@fitme/services` function inside `asUser(user.userId, …)`; every user tool runs on them via `withServices` and never passes a User id, and a missing `FITME_DATABASE_URL` is the "not configured" tool error.
- `src/auth.ts` — MCP authorization (OAuth 2.1) with Clerk as the authorization server: protected-resource metadata naming the Clerk instance (`protectedResourceHandlerClerk` from `@clerk/mcp-tools/hono`) and the middleware chain for `/`: `requireConfig` (500 when `CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY` or `FITME_DATABASE_URL` is missing; never serve without auth), `requireBearerToken` (`401` + `WWW-Authenticate: Bearer resource_metadata=…`), `@clerk/hono`'s `clerkMiddleware`, then `requireClerkUser` (`getAuth(c, { acceptsToken: "oauth_token" })`; a rejected token gets `401` `error="invalid_token"`). No audience check (Clerk OAuth tokens have no `aud`), no custom scopes, no dynamic client registration.
- `src/app.ts` — the Vercel entry (`dist/app.js`), as in `apps/webhooks`: imports `hono`, calls `initObservability({ service: "mcp" })` and `reportMissingEnv` with `src/required-env.ts`' list (`CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY`, `FITME_DATABASE_URL`, `LIBRARY_URL`, `LIBRARY_MCP_SECRET`), then loads `create-app` with a dynamic `import()` (so `pg` gets instrumented) and default-exports `createDefaultApp()` (`createApp` with `@fitme/observability/node`'s `reportError`). `tsdown.config.ts` and `turbo.json` upload source maps the same way too (only with `SENTRY_AUTH_TOKEN`; a failed upload never fails the build).
- `src/create-app.ts` — `createApp({ reportError, createServices?, createLibrary?, identifyUser? })` builds the Hono app: `observeHono(app)` first (request spans); the MCP endpoint is the root `/` (all methods, initialize and `tools/list` included), behind the `auth.ts` chain, creating a fresh server per request through `streamableHttpHandler` (`@clerk/mcp-tools/hono`); only `/.well-known/oauth-protected-resource` (OAuth discovery) and `/health` (liveness) are public. After `requireClerkUser`, `identifyUser` (default: `@fitme/observability/node`'s) sets the request's Sentry user to the verified Clerk id only. A JSON `onError` (`{ error: { code, message } }`) reports every unhandled error before the 500; an `HTTPException` and the auth chain's 401s and config 500 answer unreported. Deployed at https://mcp.fitmeproject.com.
- `src/index.ts` — Node entrypoint, `PORT` env (default 3002).
- Tests (`src/__tests__/`, vitest) drive `createMcpServer` through the SDK's `InMemoryTransport` + `Client` (`harness.ts`, `contextFor(services, reportError?, library?)` builds the `ToolContext`, the library defaulting to the in-memory fake over `BENCH` and `SQUAT`; `recordingReporter()` records what a tool reports), and the Hono app via `app.request` (`app.test.ts`, with `@clerk/hono` mocked so `getAuth` answers per test, and a recording `reportError` and `identifyUser`). Tools run on fake services (`connectWithServices` / `fakeServices`: an unfaked method fails the call) and the fake Library (`fakeLibrary`, `failWith` for an outage), never the network. `integration/` (separate vitest config, `test:integration`) runs the same tools against a real local stack as made-up Clerk-style `user_…` ids through `asUser` on the stack's pooler (the config reads its URL from `supabase status`, like `packages/services`; `FITME_DATABASE_URL` overrides), including a cross-user isolation suite that also runs table writes directly as the intruder, with the fake Library over `INTEGRATION_EXERCISES` (no Exercise is seeded: Postgres doesn't check slugs). `integration/clerk-oauth.test.ts` (helpers in `integration/clerk.ts`) runs the real OAuth flow headlessly against the Clerk development instance (Backend API test Users and a public OAuth application, sign-in token on a dev browser, consent POSTed to the Frontend API, PKCE through the MCP SDK's OAuth client, then user tools over HTTP) and is skipped without `CLERK_DEV_SECRET_KEY`. CI runs both in `.github/workflows/integration-tests.yml`.
- Exercises are Exercise slugs everywhere, in tool inputs (`exercise_slug` in the plan schemas, `exerciseSlug` for `get_exercise` / `get_exercise_history`) and outputs; no tool takes or shows an `exercise_id` (MCP clients fetch tool schemas every session, so it switched in one step). `list_exercises` and `get_exercise` read the Library API (`list`, `get`); a `list_exercises` page over the API's 50 is read in two requests.
- Plan writes go through `createPlan` / `updatePlan` from `@fitme/services/plans`, each one transaction. `update_plan` with `workouts` recreates every workout (new ids); a metadata-only update keeps them. Unknown Exercise slugs are rejected (`requireKnownSlugs`) before anything is written. Every Workout in the plan outputs (`list_plans`, `get_plan`, `create_plan`, `update_plan`, `activate_plan`) shows its `cover` (its Library Cover's id, ADR 0014, or `null`; an id only, no image URL); the input schemas have no `cover`, so one sent in is stripped. `create_plan` and `update_plan` with `workouts` pick each new Workout's Cover themselves (`withCovers` in `tools/library.ts`): after `requireKnownSlugs`, one `covers()` call, then `pickCovers` from `@fitme/core` over the muscle groups that lookup answered, so the Covers stay distinct within the Plan while there are enough; a failing `covers()` is the Library tool error (reported, nothing written), no Covers stores `null`, and a metadata-only `update_plan` leaves the Workouts and their Covers alone. `start_workout_session` and `finish_workout_session` run `startWorkoutSession` / `finishWorkoutSession` from `@fitme/services` (see there), each returning the session read in the same transaction; a start while another Workout's session is open is an unreported `ToolError` naming that Workout (one open Workout Session per User).

### packages/i18n — `@fitme/i18n`

Fitme's translations (project "Mobile app in Ukrainian"), in their own package so the web app and site can share them later. Source-only, like the other `@fitme/*` packages, with no React Native, Expo or React import (the `react-i18next` binding belongs to the app). The mobile app uses it (`apps/mobile/lib/i18n.ts`).

- `src/catalogs/<language>.json` — one catalog per App language from `@fitme/core` (`en.json`, `uk.json`), i18next JSON v4: nested keys, plurals as `<key>_one` / `_few` / `_many` / `_other` with `{{count}}`. English is the source and the fallback. One namespace, `translation`. `choices` holds the fixed choices keyed by their `@fitme/core` enum ids, one section per list; `src/__tests__/choices.test.ts` fails when a section's ids differ from core's list, so a new enum value can't ship untranslated.
- `src/index.ts` — `catalogs`, and `createI18n(language)`: a new i18next instance for an App language, initialised synchronously (`initAsync: false`) with every catalog bundled (no backend, nothing loaded later), `fallbackLng` English, so a key missing from `uk` shows its English text, never the raw key; `escapeValue: false` (React escapes). It also augments i18next's `CustomTypeOptions` with the English catalog's keys, so `t("unknown.key")` is a type error wherever the package is imported.
- `src/format.ts` (exported from the root) — dates, times, numbers, units and counts in the App language, each taking an i18next instance (`Translator`: its `t` and `language`). The locale is the App language plus the device region (`formatLocale`: `uk-UA`, `en-GB`; the language alone without a region), set per instance with `setDeviceConventions(i18n, { region, uses24hourClock })` (kept in a `WeakMap`, found through react-i18next's copy of the instance and any view inheriting from it; an instance without them gets the language's own conventions, as in this package's tests). `formatDate(i18n, date, style)` (`Intl.DateTimeFormat`; styles `dayMonth`, `dayMonthYear`, `dayOfMonth` and `weekday` (History's date tile), `shortDayMonth` (`Oct 21`, a chart column), `monthYear`, `weekdayDayMonth`, `weekdayDayMonthYear`, each in the locale's own order and words: `October 21` / `21 October` / `21 жовтня`), `formatTime` (hour and minute on the device's clock: `hour12` from `uses24hourClock`, the locale's own when `null`), `formatNumber` (`Intl.NumberFormat` in that locale: `62.5` / `62,5`; English on a German device writes `62,5`). Hermes has no `Intl.RelativeTimeFormat`: a relative text ("2 days ago") is a catalog plural, never `Intl`. Number formatters are cached per locale and options; date formatters never are, since one keeps the time zone it was built in and the device can move. `formatCount(i18n, kind, count)` (`counts.<kind>` plurals: `sets`, `reps`, `exercises`, `workouts`, `workoutSessions`, `minutes`, `entries`), `unitName` / `formatUnit` / `spokenUnit` (`unitNames.<unit>`, `units.<unit>`, the `spokenUnits.<unit>` plurals for VoiceOver; units are the Profile's codes `cm`, `in`, `kg`, `lbs`, never `Intl`'s `style: "unit"`, unchecked on Hermes), `formatWeight` / `formatHeight` / `formatWorkoutDuration` (moved from `@fitme/core`), `formatDuration(i18n, ms)` (hours and minutes, `formatWorkoutDuration`'s words), and `formatCompactVolume` / `spokenCompactVolume` (a total volume: whole kg or lbs below a thousand, then tonnes (`compactUnits.t`) or thousands of pounds (`compactUnits.thousandLbs`) to one decimal, `spokenCompactUnits.*` plurals for VoiceOver). The unit follows the User's measurement system, never the language. The catalogs write every number through `{{…, number}}` (`createI18n` replaces i18next's `number` format with the same locale as `formatNumber`, passing only `useGrouping` and the fraction digits on to `Intl`), so a count or value placeholder reads as the language writes it. The one exception is a bound a form field quotes back (`sets.form.*TooHigh`'s `{{max}}`): it stays ungrouped, since the field reads `10,000` as 10.
- `src/check.ts` — `checkCatalogs(catalogs)`, the translation check behind AI-written translations, which answers one line per problem: a key (a plural by its key without the suffix) missing from a catalog, a key that's a string in one catalog and a plural in another (or both in one), a plural without exactly its language's forms (`pluralForms`: `en` `one` / `other`, `uk` `one` / `few` / `many` / `other`, checked against Node's `Intl.PluralRules`; `_zero` optional everywhere, as i18next allows), a key whose `{{placeholders}}` (across its forms) differ from English's, an empty or non-string value, an empty section, and a name with a `.` (i18next splits on it). A plain key never ends in a plural suffix (`_one`, `_other`, …): the check would read it as a plural. `src/__tests__/catalogs.test.ts` runs it over the real catalogs, so CI's unit tests fail on a missing translation; `check.test.ts` proves each failure over inline catalogs.
- **The rule:** a pull request adding or changing an English string adds or changes its Ukrainian translation in the same pull request (written by the agent, reviewed by a human: say so in the PR description), with every plural form Ukrainian needs. A new App language gets its catalog, its `pluralForms` entry, its line in `catalogs`, its `@formatjs/intl-pluralrules` locale data in `apps/mobile/lib/i18n.ts` and its entry in `apps/mobile/app.json`'s `supportedLocales` (see App language (mobile)).
- `src/text-check.ts` (`pnpm text-check`, run by Node's own type stripping) — the text check (FIT-409): reads every `.ts` / `.tsx` under `apps/mobile` (not `__tests__/`, `*.test.ts(x)`, `test-utils/`, `e2e/`, `.d.ts`, native projects or build output), parses it with TypeScript and fails on text with a letter in JSX text, in a string literal (or a template's static part) shown as a JSX child, as a text prop's value, an object property or a destructured default of the same name (`isTextProp`: `TEXT_PROPS` (`title`, `label`, `placeholder`, `accessibilityLabel`, an alert button's `text`, …) and any name ending in `Label`, `Title`, `Text`, `Message`, `Hint` or `Placeholder`), or as `Alert.alert` / `Alert.prompt`'s title or message, printing `file:line:column  text`. A catalog key, a condition, a comparison, another function's argument, comments, whitespace, text without a letter (HTML entities included) and every other prop (`testID`, `href`, `className`, analytics event names) never count. `ALLOWLIST` (a path and a reason each; empty so far) exempts a file, and an entry whose file has no hardcoded text left fails the check. CI runs it in the `checks` job of `.github/workflows/unit-tests.yml`. The rule and the allowlist policy are in `docs/agents/ui.md` (The text check).
- Tests (`src/__tests__/`, vitest): the check over inline catalogs, the real catalogs passing it, and `createI18n` (English and Ukrainian text and plural forms, the English fallback, and the typed keys through `@ts-expect-error`, which the typecheck holds); and the text check on inline `.tsx` / `.ts` fixtures (`text-check.test.ts`).

### packages/observability — `@fitme/observability`

Errors and traces for every app (Sentry today; the vendor-neutral name leaves room for Axiom). Source-only, like `@fitme/db`. An app on it never imports `@sentry/*` for errors or traces: it goes through this package, which keeps the rules in one place. The one exception is a platform SDK that has to hook the app's build and entry points (`@sentry/react-native` in `apps/mobile`, `@sentry/nextjs` in `apps/site` and `apps/web`): the app calls it directly, with every rule it can take from the root export. So far `apps/webhooks`, `apps/api`, `apps/library`, `apps/mcp` and `apps/arnold` (errors only: `initObservability({ service, tracing: false })` for an app tracing through its own OpenTelemetry pipeline) are on it, and `apps/mobile`, `apps/site` and `apps/web` read its root export (`apps/mobile` the scrubber and propagation targets; `apps/site` the config and scrubber; `apps/web` `sdkOptions`, every shared option).

- `.` (`src/index.ts`) — pure, no SDK import, safe for Node, React Native and Next: `scrubEvent` (`beforeSend` / `beforeSendTransaction`: drops `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers, cookies and request bodies, and reduces the user to `{ id }`, the Clerk id; a user without an id is dropped; a backstop for errors captured around `reportError`, such as Sentry's own handlers or console breadcrumbs: an event with an exception value mentioning `Failed query:` has every exception value replaced (the rest are its cause chain), and such a breadcrumb loses its message and data), `sanitizeError(error)` (a Drizzle `DrizzleQueryError` anywhere in the cause chain → a fresh `DatabaseQueryError`: only the SQLSTATE, also as the `sqlstate` tag, the original stack frames and no cause, so no SQL, parameter or Postgres message, which can echo input; anything else as is) with `isQueryError` (recognised by shape, `query` and `params` own properties, since the package can't depend on drizzle-orm), `tracePropagationTargets` (regexes: our services `api`, `app`, `arnold`, `library`, `mcp`, `webhooks` on `fitmeproject.com`, localhost / 127.0.0.1, and same-origin relative paths; never a wildcard over `*.fitmeproject.com`, since Clerk answers on `clerk.fitmeproject.com`), `resolveObservabilityConfig({ dsn, env })` (`environment` = `VERCEL_ENV`, `development` without it; `release` = `VERCEL_GIT_COMMIT_SHA`; traces at 0.2 in production and 1.0 otherwise; no DSN → `enabled: false`, nothing sent). Each platform passes its own DSN variable. `sdkOptions(config)` turns the resolved config into the SDK options every platform starts with: the scrubber as `beforeSend` / `beforeSendTransaction`, the propagation targets, `traceLifecycle: "static"` (SDK 11 streams spans by default, which skips `beforeSendTransaction`) and `dataCollection` locked down (SDK 11's replacement for `sendDefaultPii: false`: no user info, cookies, bodies, credential headers, response headers, DB query data, gen-AI inputs/outputs or stack-frame variables).
- `./node` (`src/node.ts`) — `initObservability({ service, tracing? })`: called once at process startup, before the app is built; without `SENTRY_DSN` it does nothing (local runs, tests, CI). Otherwise it starts `@sentry/node` with `sdkOptions` and a `service` tag; `tracing: false` drops its spans and trace headers (for an app tracing through its own OpenTelemetry pipeline, Arnold). `reportError(error, tags?)` runs `sanitizeError` first, then logs, captures (tags merged with the `sqlstate` one) and flushes (2 s) before the response, since a serverless instance may freeze afterwards; before init it only logs. `identifyUser(userId)` sets the request's Sentry user to `{ id }` (a Clerk id from a verified token only; each request has its own scope). `reportMissingEnv(required, { env?, report? })`: on Vercel production only (`VERCEL_ENV=production`), reports a `MissingEnvError` (tagged `env_var`) for each required variable missing or empty, an entry like `["NEW_NAME", "OLD_NAME"]` (a renamed variable) met by any of its names, and answers the missing names; it never throws. `apps/api`, `apps/arnold`, `apps/mcp` and `apps/webhooks` call it at startup, after `initObservability`, each with its own `required-env.ts` list (`apps/library` has none yet). `observeHono(app)` (Sentry's `honoMiddleware`, registered first with `app.use`) gives a Hono app its request spans whatever order Hono was loaded in. On Vercel the SDK also keeps the function alive until each request's spans are flushed.
- `@sentry/node` is a runtime dependency here and must also be in each consuming app's own `dependencies` (the tsdown apps keep it external).
- **Bundling finding (FIT-217):** the SDK instruments libraries through module hooks it registers at `initObservability`, so it only sees modules loaded after that. A tsdown bundle hoists every external `import` to the top of the entry, so a statically imported `pg` loads before init and gets no spans (`[instrumentation:pg, pg-pool] not injected yet`). The Vercel entry (`src/app.ts`) therefore imports `hono`, calls `initObservability`, and only then `await import("./create-app.js")`; with that, `pg` / `pg-pool` spans appear under the request span. Request spans don't depend on load order (`observeHono`), and outgoing `fetch` spans (`http.client`, with trace headers to the propagation targets) come from Node's own diagnostics channels, so bundling doesn't affect them. A tsdown app moving onto the package copies the `apps/webhooks` entry, build setup and `turbo.json`.
- Tests (`src/__tests__/`, vitest) cover the root export: the scrubber (its `Failed query:` backstop included), `sanitizeError` on Drizzle-shaped errors, the SDK options, the propagation list (our services and localhost match; Clerk, RevenueCat, Supabase and look-alike hosts don't) and the config resolution (production, preview, no DSN, outside Vercel); `required-env.test.ts` checks `reportMissingEnv` with a recording reporter; `report-error.test.ts` checks what `reportError` hands a mocked `@sentry/node` and the console for a query failure.

### packages/library-sdk — `@fitme/library-sdk`

The one client for the Library API (`apps/library`), shared by Arnold, MCP and the mobile app (project "Exercises off Postgres"), plus an in-memory fake for their tests. Source-only, like the other `@fitme/*` packages, and `fetch`-only: nothing Node-specific, so it runs in Node and React Native (the query string is built by hand, since React Native's `URLSearchParams` is partial). No zod; its only dependency is `@fitme/core` (muscle groups), so a tsdown app needs nothing extra in its `dependencies`.

- `src/client.ts` — `createLibrary({ url, token, fetch?, timeoutMs? })`. `token` is an async getter asked once per request: a server secret (`LIBRARY_ARNOLD_SECRET`, `LIBRARY_MCP_SECRET`) for Arnold and MCP, the User's Clerk session token for mobile; `null` / empty fails unauthorized without a request. `get(slug)` → one `Exercise` in full (`GET /exercises/:slug`), or `null` for a 404 or an empty slug (no request). `lookup(slugs)` → `{ data, missing }`: drops repeated slugs, splits the rest into requests of at most 40 (`MAX_LOOKUP_SLUGS`, the API's `?slugs=` limit), sent in parallel, and answers in asked order with every slug no Exercise has in `missing` (an empty slug or one with a comma is never sent, only answered missing); one failed chunk fails the lookup. `list({ search, muscleGroup, muscleGroups, limit, offset })` → `{ data, total, hasMore }`, sending only the parameters given so the API's defaults apply (`muscleGroups`, Exercises with any of them, goes out comma-separated as `muscle_groups`, never when empty; `muscleGroup` stays `muscle_group`, which Arnold and MCP use). Each method takes an optional `language`, an App language from `@fitme/core` (`get(slug, { language })`, `lookup(slugs, { language })`, `list({ language, … })`), sent only when given (without it the API answers English) and on every request a lookup is split into; the types don't change, since a translated Exercise has the same fields. MCP and the Public API call without one. `covers()` → every Cover (`GET /covers`, `{ id, muscle_groups, image_url }`, in the Library's order; an empty list for none), no `language` (Covers have no text).
- `src/errors.ts` — every failure is a `LibraryError` with a `code` (match on it or the subclass): `LibraryUnauthorizedError` (401, or no token), `LibraryRateLimitedError` (429, `retryAfterSeconds` from `Retry-After`, 60 when unreadable), `LibraryUnavailableError` (network failure, a throwing token getter, the 10 s timeout (`timeoutMs`), any other status, an unreadable or malformed answer (each answer is checked field by field, muscle groups only as strings so a new one never breaks an old client); `cause` kept) and `LibraryInvalidRequestError` (400, the API's message).
- `src/types.ts` — `ExerciseSummary`, `Exercise`, `ExercisePage`, `ExerciseBatch`, `Cover` mirror `apps/library`' `src/schemas.ts` by hand (muscle groups typed from `@fitme/core`): a field added there is added here too. `Library` is the interface both the client and the fake implement.
- `src/name.ts` — `exerciseNameFromSlug(slug)`: the readable name (`barbell-back-squat` → `Barbell back squat`) a consumer shows for an Exercise it can't resolve.
- `src/fake.ts` (export `@fitme/library-sdk/fake`) — `createFakeLibrary(exercises)`: the API's answers over those Exercises in memory (alphabetical by name, ties by slug; trimmed case-insensitive substring search, `%`/`_` literal; muscle group filter; `muscleGroups` read as the API reads `muscle_groups` (any of them, a repeat counted once; an unknown group, an empty item or `muscleGroup` as well failing invalid request); paging with its defaults and bounds, an out-of-bounds parameter failing invalid request; lookup with `missing`, summaries only; `get` answers the Exercise in full, empty description and instructions for one given as a summary), each in the `language` asked for exactly as the API answers it: an Exercise may carry `translations` (`{ uk: { name, description?, instructions? } }`), one without a translation in that language answers wholly in English, search matches the name in that language or the English one, and lists sort by that language's name with its collation; `createFakeLibrary(exercises, { covers })` answers `covers()` with those Covers (none by default); and `failWith(error)` fails every call until `failWith(null)`. Consumers' tests use it, never the network.
- Tests (`src/__tests__/`, vitest) drive the client through a stubbed `fetch` answering like `apps/library` (`stub-api.ts`): chunking at 40, order, dedupe and `missing`, the bearer on every request, the error mapping; `language` sent on `get`, `list` and every chunk of a `lookup`, never when not given; `covers()`'s shape and error mapping; `fake.test.ts` checks the fake answers exactly what the client does over the same translated Exercises and Covers, with no language, `en` and `uk`, and fails on demand.

### packages/rate-limit — `@fitme/rate-limit`

The per-caller rate limiter, shared by the backend apps (`apps/library` and `apps/api`). Source-only, like the other `@fitme/*` packages, with no app-specific code: the limit, the window, the Upstash key prefix and each request's bucket key are the caller's (a User id today; a per-credential bucket, per OAuth client or API key, is a new key, nothing else). Its runtime dependencies (`@upstash/ratelimit`, `@upstash/redis`, `@vercel/functions`) must also be in each tsdown app's `dependencies`.

- `src/index.ts` — `RateLimiter` (`limit(key)` → `{ allowed: true }` or `{ allowed: false, retryAfterSeconds }`, whole seconds, at least 1). `memoryRateLimiter({ limit, windowMs, now? })`: a fixed window per key in the instance's memory (local development, tests; `now` for a fake clock). `upstashRateLimiter({ limit, windowMs, prefix, timeoutMs?, url, token })`: a fixed window per key in Upstash Redis, no client retries, each call aborted after `timeoutMs` (default 1 s; give `checkRateLimit` the same, so a request served uncounted stays uncounted), Upstash's Rate Limit Analytics on with its write left to `waitUntil`. `rateLimiterFromEnv(env, { limit, windowMs, prefix, timeoutMs? })`: Upstash with `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`, otherwise in memory outside production and a throw in production (`NODE_ENV=production`, except a Vercel preview, `VERCEL_ENV=preview`, which runs with it but has no Upstash), so a production deployment without Upstash fails at startup. `checkRateLimit({ key, limiter, reportError, timeoutMs? })` counts one request: a limiter that throws or takes over `timeoutMs` (default 1 s, `LIMITER_TIMEOUT_MS`) answers allowed (fail open) and reports `Rate limiter failed, serving uncounted` with the failure as its `cause`. The HTTP answer (429, `Retry-After`, the error body) and who isn't counted are the app's middleware.
- Tests (`src/__tests__/`, vitest): the in-memory limiter on a fake clock (limit, window, `Retry-After` rounding, separate buckets), the environment choice (production without Upstash throws) and `checkRateLimit`'s fail-open on a throwing or hanging limiter (fake timers).

### packages/db — `@fitme/db`

The only way backend apps reach Postgres (ADR 0003): Drizzle on node-postgres (`pg`, not postgres.js) through the Supavisor transaction pooler, as the shared `fitme` login. Source-only, like the other workspace packages.

- `src/schema.ts` + `src/relations.ts` — generated Drizzle schema (the `public` tables plus `private.retired_user_ids` as `retiredUserIdsInPrivate`); `src/index.ts` re-exports the tables, and the relations only feed the client so `tx.query` works. `schema:generate` runs `drizzle-kit pull` (`drizzle.config.ts`, direct superuser URL from `supabase status`) against the running local stack, renames the `private` schema object to `privateSchema`, sorts declarations by name and formats with Biome, so reruns against the same migrations are byte-identical. Never edit them by hand, and never run `drizzle-kit generate`/`migrate`/`push`: the Supabase SQL migrations own the schema (ADR 0004). After a migration, regenerate and commit both files with `database.types.ts`.
- `src/index.ts` — the two doors and the `Transaction` type (typed with the generated schema, so `tx.select().from(plans)` and `tx.query.plans.findMany(…)` are checked). `asUser(userId, fn)` opens a transaction, runs `SET LOCAL ROLE authenticated` and `set_config('request.jwt.claims', {sub, role: authenticated}, true)`, then `fn(tx)`, so RLS and `current_user_id()` apply; `userId` only ever comes from a verified token. `withService(fn)` does the same as `service_role` (bypasses RLS; only where that is the point, such as webhooks). Both also set `application_name` locally.
- `src/client.ts` — internal: the lazily created `pg.Pool` (small `max`, registered with `@vercel/functions`' `attachDatabasePool`) and Drizzle client, from `FITME_DATABASE_URL`, which must carry `?application_name=<app>`. Never export the raw client or pool, and never import this module from outside the package.
- A new runtime dependency here (or in `@fitme/services`) must also go in the `dependencies` of `apps/mcp` and `apps/webhooks`, or their tsdown build fails (see "Workspace packages are source-only").
- Never use a session-level `SET ROLE` or `set_config(…, false)` anywhere: the transaction pooler doesn't reset connections, so session state leaks to other requests.
- A transaction is one connection: await its queries one at a time, never `Promise.all` over the same `tx` (pg deprecates queueing on a busy client and pg@9 rejects it). The db, services and MCP integration suites run with `--throw-deprecation`, so such a query fails them.
- Every integration suite (db, services, MCP, `apps/api`) runs `@fitme/db/wait-for-pooler` as its vitest `globalSetup`: one `select 1` through the suite's `FITME_DATABASE_URL`, retried for up to 90 s, before any test file starts, since test files connecting to a cold pooler at once (the first run after `pnpm db start`) time out their 30 s hooks. Nothing listening on the port fails it within 5 s ("local Supabase pooler not reachable at …; run `pnpm db start`"); a stopped stack already fails at config load, when `supabase status` has no pooler. A new integration suite adds it too.
- `fitme` (migration `20261014130000_fitme_login.sql`) is `LOGIN NOINHERIT` with no grants of its own, a member of `authenticated` and `service_role` only, so a query outside both doors fails with "permission denied". Its credential is service-role strength: server environments only. Local stacks set its development password in `supabase/roles.sql` (run by the CLI before the migrations, never pushed); hosted projects set theirs by hand. The pooler user is `fitme.pooler-dev` locally and `fitme.<project-ref>` on hosted projects.
- `integration/` (`test:integration`) runs the doors against the local stack's pooler (its port comes from `supabase status --output-format json`; `FITME_DATABASE_URL` overrides): identity and RLS, concurrent transactions with rollbacks never seeing another User's id, clean reused connections, and the login denied outside the doors. CI runs it in the integration-tests workflow.

### packages/services — `@fitme/services`

Business logic shared by the backend apps (ADR 0004), which replaced the Postgres RPCs (the last ones dropped by migration `20261027120000_drop_legacy_rpcs.sql`, FIT-339). Source-only; each service is its own export (`@fitme/services/<name>`), no barrel.

- The rule: a service takes the `Transaction` from `asUser` or `withService` as its first argument and never opens its own connection. Any User id it acts on comes from a verified source (a verified token, or a signed webhook), never from request or tool input.
- Exercises are Exercise slugs only (ADR 0007, FIT-244; project "Exercises off Postgres"): every Workout Exercise in `getPlan` / `getActivePlan` / `createPlan` / `updatePlan` and every Workout Session Exercise in `getWorkoutSession` / `listWorkoutHistory` / start and finish carries `exercise_slug` and no Exercise details (consumers name them through the Library API, after the transaction). Writes take an Exercise as `exercise_slug` (`createPlan` / `updatePlan`), `exerciseSlug` (`addExerciseToWorkout`) or `newExerciseSlug` (`replaceExerciseInWorkout`), never checked (ADR 0010: the tool layer checks it), so any string is stored. `startWorkoutSession` copies the slugs. A replacement already in place is compared by slug.
- `profile.ts` — `getProfile(tx, userId)`, run inside `asUser`: the User's Profile (gender, age, height, weight as numbers, `measurement_system`) plus its `units` (metric = cm/kg, us/uk = in/lbs; an unknown system counts as metric), or `null` without a Profile. Used by MCP's `get_profile` and Arnold's `get_user_profile`. `updateProfile(tx, userId, changes)` (Arnold's `update_user_profile`): changes only the given fields and returns `getProfile`'s result, or `null` with nothing changed without a Profile. A new `measurement_system` first converts every stored height and weight of the User, the weights of their Personal records included, which are never added or removed by it (weights times 2.20462, heights times 0.393701, or divided by them, rounded to 2 decimals; us <-> uk changes nothing); it finds Workout Sessions by their own `user_id`, so a session whose Workout is gone is converted too (FIT-267; sessions skewed before that keep their values, since their original unit isn't recorded); the given height and weight are then written in the new system's units. It row-locks the Profile with a no-op UPDATE first, so a repeat or concurrent run sees the new system and never converts twice. `replaceProfile(tx, userId, profile)` (the Public API's `PUT /v1/profile`) takes every field: it inserts the Profile `on conflict (user_id) do nothing` first (so concurrent first calls never both create one) and answers `{ created: true, profile }`, or else runs `updateProfile` with every field (converting first) and answers `created: false`. `lockProfileUnits(tx, userId)` (the Public API's Plan reads) answers the Profile's `units` (or `null`) and share-locks the Profile row until the transaction ends, so no conversion (which row-locks it first) commits while the caller reads weights after it.
- `arnold-sessions.ts` — `recordArnoldSession(tx, userId, sessionId)` / `listArnoldSessionIds(tx, userId)`, run inside `asUser`: Arnold's EVE session ids per User in `arnold_sessions` (migration `20261014160000_coach_sessions.sql`, renamed from `coach_sessions` with its policies, index and primary key by `20261024140000_arnold_sessions.sql`; RLS: a User reads and inserts only their own rows, `service_role` may delete). Recording is idempotent (`on conflict do nothing`), and an id already recorded for another User stays theirs. `getArnoldSessionOwner(tx, sessionId)` runs in `withService` (the channel's ownership check). `deleteUserData` locks this table but keeps the rows, and so does the Clerk webhook after resetting the sessions: each is the ACL for an EVE session whose stream outlives the reset (a missing row lets the first caller claim it), and the id in it is already retired, so it fails closed. The webhook lists them with `listArnoldSessionIds` in `withService`, since the retired id no longer matches RLS.
- `exercises.ts` — run inside `asUser`: `getExerciseHistory(tx, userId, { exerciseSlug, limit })` (the User's Workout Session entries for the Exercise, newest first, only sets with a logged weight), MCP's `get_exercise_history`. Timestamps go through `jsonTimestamp` (`json-timestamp.ts`, `to_json`) so they keep PostgREST's ISO format. Searching and reading Exercises is the Library API's, never a service's.
- `plans.ts` — run inside `asUser`, each filtering on the User id as well as RLS: `listPlans(tx, userId)` (live Plans newest first, each with Workout summaries in rotation order and Exercise counts; no pagination), `getPlan(tx, userId, planId)` (a live Plan with Workouts, Exercises and sets, each in `order`; `null` when missing, soft-deleted or foreign), `getActivePlan(tx, userId)` (the same for the User's active Plan, or `null` with none), `deletePlan(tx, userId, planId)` (soft delete: sets `deleted_at`, and the `deactivate_deleted_plan` trigger clears `is_active`; an already deleted Plan answers `alreadyDeleted: true`, a missing one `null`) and `activatePlan(tx, userId, planId)` (the live Plan becomes active and every other Plan of the User inactive, so at most one is active; its summary, or `null` with nothing changed for a missing, soft-deleted or foreign Plan. Concurrent activations serialize on row locks and the last one wins), `createPlan(tx, userId, plan, { activate }?)` (a Plan with its Workouts (each with an optional `cover`, its Cover id from the caller, stored as given: services never choose one, ADR 0014), Exercises and sets, each `order` from its array position, made the active Plan through `activatePlan` unless `activate: false`, which creates it inactive and leaves the active Plan alone; the Plan in full) and `updatePlan(tx, userId, planId, changes)` (only the given metadata fields change; with `workouts` every Workout is deleted and recreated, new ids, otherwise they and their ids stay; the Plan in full, or `null` with nothing changed for a missing, soft-deleted or foreign Plan; it locks the Plan row by its UPDATE before touching Workouts). Each read is one relational query (one statement, so one snapshot under READ COMMITTED: a concurrent `updatePlan` never mixes old metadata with new Workouts). Output matches what PostgREST returned: snake_case keys, timestamps through `jsonTimestamp`, numeric weights as numbers. Used by MCP's `list_plans`, `get_plan`, `create_plan`, `update_plan`, `delete_plan` and `activate_plan`, by Arnold's `activate_plan` (`activatePlan`), `get_plans` (`listPlans`) and `get_active_plan` (`getActivePlan`), and by the Public API's Plan routes.
- `workout-edits.ts` — Arnold's Plan edits, run inside `asUser`, each filtering on the User id as well as RLS (another User's row is `null` / `false`, never edited): `addExerciseToWorkout(tx, userId, { workoutId, exerciseSlug, sets, requestKey? })` and `addSetToExercise(tx, userId, { workoutExerciseId, set, requestKey? })` append after the last row; `removeExerciseFromWorkout(tx, userId, workoutExerciseId)` and `removeSetFromExercise(tx, userId, setId)` renumber the remaining siblings from 1; `replaceExerciseInWorkout(tx, userId, { workoutExerciseId, newExerciseSlug, sets })` keeps the row and its place and replaces its sets (when that Exercise with exactly those sets is already in place, it rewrites nothing, so set ids stay valid); `updateSetRecommendations(tx, userId, setId, changes)` changes only the given targets. `addSetToExercise` throws `TooManySetsError` for a Workout Exercise already at `MAX_SETS_PER_EXERCISE` (20) sets. A replacement already in place is detected by comparing weights as Postgres rounds them to numeric(8,2). Each append, remove or replace first takes ROW EXCLUSIVE on `workouts`, `workout_exercises`, `workout_exercise_sets` (`deleteUserData`'s order, so it queues behind an account deletion instead of deadlocking with its cascade), then row-locks (`FOR NO KEY UPDATE`) the parent it appends to or renumbers (the Workout, or the Workout Exercise) and nothing above it, so concurrent edits keep `order` contiguous and can't deadlock with `updatePlan` / `finishWorkoutSession`. A Workout of a soft-deleted Plan is still edited, as `ai-agent` did. Retries: removing, replacing and updating are safe to repeat (a repeated remove answers not found); an append stores its `requestKey` in the row's `request_key` column (migration `20261015120000_plan_edit_request_keys.sql`, partial unique index), and a repeated call with the same key returns that row.
- `personal-records.ts` — `initializePersonalRecords(tx, userId)` explicitly initializes a User's complete finished History, atomically with durable completion, reusing the finish award rules with a chronological boundary. The Profile unit lock and per-User transaction advisory lock serialize replay with conversion and new finishes. Retries preserve existing awards and never replay completed History. No startup, client or production backfill caller is installed; see `docs/agents/personal-record-initialization.md`.
- `workout-sessions.ts` — run inside `asUser` (RLS scopes every query to the User; the session edits also filter on the User id): `listWorkoutSessions(tx, { limit, offset, status })` (newest first, with exercise/set/logged-set counts, `personal_records` and `total`, counted in the page's own statement; an offset past the end is an empty page), `getWorkoutSession(tx, id)` (exercises and sets in order, or `null`; one statement, so a concurrent delete never yields a half-read session), `listWorkoutHistory(tx, { limit })` (the last `limit` finished sessions, last finished first, each in full like `getWorkoutSession`, in one statement; Arnold's `get_workouts_history`), `logSet(tx, { setId, repsCompleted, weightCompleted })` (`logged` / `not_found` / `session_finished`; table locks in deletion order followed by the session row lock, so a finish includes the log or rejects it after finishing; queues behind `deleteUserData`) `deleteWorkoutSession(tx, id)` (false when nothing matched), `startWorkoutSession(tx, workoutId)` and `finishWorkoutSession(tx, id)` (`started` / `finished` with the session, `session_in_progress` for a start, or `not_found`), `addExerciseToWorkoutSession(tx, userId, { sessionId, exerciseSlug })` (`added` with the Workout Session Exercise and no sets / `session_finished` / `not_found`; the slug is stored unchecked, ADR 0010), `removeExerciseFromWorkoutSession(tx, userId, sessionExerciseId)` (`removed` / `session_finished` with its session id / `not_found`; its sets go by cascade, the others keep their `order`) and `replaceExerciseInWorkoutSession(tx, userId, { sessionExerciseId, exerciseSlug })` (`replaced` with the Workout Session Exercise and its sets / `session_finished` / `not_found`: the slug swapped in place, unchecked, and every set's `reps_recommended` and `weight_recommended` set to 0, never `null`, which the Plan Update reads as a set added during the session) and `addSetToWorkoutSessionExercise(tx, userId, { sessionExerciseId, repsCompleted, weightCompleted })` (`added` with the set / `session_finished` / `not_found`: a set logged `now()`, with no targets). Session edits filter on the User id as well as RLS, take ROW EXCLUSIVE on `workout_sessions`, `workout_session_exercises`, `workout_session_exercise_sets` (`deleteUserData`'s order), then row-lock the Workout Session (`FOR NO KEY UPDATE`) and check it's open in the same transaction, so a concurrent finish either waits or is seen; an add appends at the highest `order` + 1 (a remove's gap stays), so concurrent adds never share an `order` (adding a set also row-locks its Workout Session Exercise before reading it). Timestamps are rendered as PostgREST did (`to_json`), numerics as numbers, weights in the User's unit. Used by every MCP Workout Session tool (adding, removing and replacing an Exercise and adding a set only by the Public API).
- `startWorkoutSession`: a User has at most one open Workout Session (ADR 0013; partial unique index `workout_sessions_one_open_per_user_idx`, migration `20261029120000_one_open_session_per_user.sql`, whose cleanup is `private.close_extra_open_workout_sessions()`, kept for pgTAP and callable by its owner only). It returns that session when it's the Workout's (`resumed`), refuses with nothing written when it's another Workout's or one whose Workout is gone (`session_in_progress` with its `sessionId` and `workoutName`, `null` for a gone Workout), or inserts one `ON CONFLICT DO NOTHING` against the per-User index and copies the Workout's exercises and sets; a lost race reads the winner back and resumes (same Workout) or refuses (another Workout), and a Workout of a soft-deleted Plan or another User's is `not_found`. `finishWorkoutSession` takes its locks in a fixed order (`workout_sessions` `ROW EXCLUSIVE`, then the Profile row (share, `lockProfileUnits`, so no conversion commits while it copies weights), then the per-User Personal record advisory lock shared with initialization, then the Plan row, then the session), claims only an open session, awards the Personal records it earned (`awardPersonalRecords`, `personal-records.ts`, only by the finish that claimed it, so a repeated or concurrent finish awards nothing more), and moves its Workout to the end of the Plan, renumbering from 1 (`rotated`); a session whose Workout is gone is only finished (`rotated: false`), an already finished one is left alone (`alreadyFinished`).
- `plan-update.ts` — the Plan Update, run inside `asUser`: `previewPlanUpdate(tx, userId, sessionId)` and `applyPlanUpdate(tx, userId, sessionId)`, each filtering on the User id as well as RLS. For a finished Workout Session it works out the structural changes to its Workout, matching session Exercises to Workout Exercises by `order`: `replace_exercise`, `add_exercise`, `remove_exercise` and `add_sets` (sets created during the session: no `reps_recommended`, or past the Plan's set count, since replacing an Exercise in the app zeroes every set's targets), targets from the logged sets, nothing that was never logged, at most 20 sets per Workout Exercise. It answers `{ plan, workout, changes, weight_unit }`: each change's Exercise(s) as `exercise_slug` / `replaced_exercise_slug` only (no names), its sets as `{ reps, weight }` with weights as stored, and the User's unit (`kg` without a Profile). Applying writes them in one transaction (replacements and added sets, then removals renumbering from 1, then added Exercises appended) and stamps `workout_sessions.plan_changes_applied_at` (migration `20261021120000_workout_session_plan_changes.sql`, which also indexes `workout_exercises.workout_id`, `workout_exercise_sets.workout_exercise_id` and `workout_session_exercise_sets.workout_session_exercise_id`; pgTAP `plan_update_schema.test.sql`), after which both modes answer no changes, so a repeated or concurrent apply writes once. An open session, a NULL `workout_id`, a soft-deleted Plan, a repeated `order` on either side (the app never writes one, but RLS allows it, and the slot join would grow with the product of the duplicates) or more than 50 Exercises (or an Exercise with more than 100 sets) on either side has none; `plan` and `workout` are `null` when the Workout is gone or its Plan soft-deleted, and another User's or a missing Workout Session is `null`. Locks, in preview too: ROW EXCLUSIVE on `workout_sessions`, `workouts`, `workout_exercises`, `workout_exercise_sets` (`deleteUserData`'s order), then the Profile row (share-locked by `lockProfileUnits`), the Plan row, the Workout row, its Workout Exercise rows (Arnold's set edits lock only those) and the session row (`finishWorkoutSession`'s order), so concurrent applies serialize and the second is a no-op. The Public API's Plan Update routes call it (`GET` / `POST /v1/workout-sessions/{id}/plan-update`), and the mobile finish flow goes through them.
- `weekly-goals.ts` — the Weekly goal log (ADR 0015; migration `20261031120000_weekly_goal_changes.sql`, `weekly_goal_changes`: append-only, RLS, a User reads and inserts only their own rows, no update, `service_role` deletes): `recordWeeklyGoal(tx, userId)` appends the active Plan's frequency (`null` once none is active) when it differs from the last one recorded, in one statement and with no lock of its own; `null` before tracking started adds nothing. `activatePlan` (so `createPlan` with `activate`), `updatePlan` with `frequency`, `deletePlan` and the first `finishWorkoutSession` of a session call it last in their transaction, so every writer keeps it; the migration started tracking for every User with an active Plan. Weeks are the device's (its timezone), so it stores instants and `@fitme/core`'s `weeklyGoalOverview` derives the weeks. `listWeeklyGoalChanges(tx, userId)`: every change, oldest first. `getWeeklyGoals(tx, userId, timeZone, now?)` returns those `changes` and the lifetime `streak`, computed from all qualifying finished Workout Sessions across Plans with local Monday boundaries; `now` is a test seam. The SQL walks backward from the current week and stops at the first completed miss or unknown goal; each week reads at most its target's qualifying sessions from `workout_session_progress`, through a partial `(user_id, started_at, finished_at)` index that excludes unfinished and zero-rep Sessions. It never reads source Sessions or their children during qualification. UTC week bounds are materialized before the RLS-protected range predicates so the index is usable. IANA zones retain DST; Expo's GMT/UTC fixed-offset calendar IDs use numeric intervals to preserve their ISO offset sign. The server-owned Weekly goal tracking release (2026-10-31, migration `20261031120000`) bounds total recursion; forged gap-free histories cannot move it earlier, and no legitimate tracked week is truncated. `trackingStartedAt` is a historical-fixture seam alongside `now`, never API input. Caller-writable goal timestamps never expand a calendar series. Weekly goal targets are constrained to 1-7 by `20261101110000_weekly_goal_target_bounds.sql`; old out-of-range evidence is read as unknown, and the Session query independently caps its LIMIT at `MAX_FREQUENCY`. The constraint is NOT VALID to preserve old append-only rows while rejecting every new invalid insert. No persisted streak counter. Migration `20261101100000_workout_session_progress.sql` backfills a read-only Session qualification aggregate and private per-Exercise positive-Set counts under source-table write locks. Owner-run, non-callable triggers with an empty search path propagate atomic Set deltas, Exercise moves/deletes, Session metadata and FK cascades; clients cannot forge either cache. Counter-row locks serialize concurrent writes and moves without rescanning rejected Sets. The aggregate has only own-User SELECT under RLS (service_role also SELECT); its private Exercise cache has no client grants.
- `delete-user-data.ts` — `deleteUserData(tx, userId)`, run inside `withService` (it replaced the dropped `delete_user_data` SQL function): rejects an empty id, locks the User-owned tables and their children `IN SHARE ROW EXCLUSIVE MODE` (roots, children, `arnold_sessions`, then `weekly_goal_changes`, which its writers write last), throws `UserRekeyedError` (`code` `55000`) for an id the Clerk migration rekeyed away (a `private.retired_user_ids` row with `rekeyed_to`), retires the id in `private.retired_user_ids` (on conflict do nothing) and deletes the root rows (Workout Sessions, Plans, Profile) and the Weekly goal changes, the roots' children cascading; Arnold session ids stay (the webhook resets those sessions and keeps the rows as their ACL). A second run is a no-op. Its table list must track the schema. `service_role`'s grants for it come from migration `20261014140000_service_role_deletes_user_data.sql`.
- `integration/` (`test:integration`) runs the services against the local stack's pooler like `packages/db` (the URL helper is `@fitme/db/local-database-url`), as made-up Clerk-style `user_…` ids; CI runs it in the integration-tests workflow. Its files run in parallel, so they (and `apps/api`'s, through the `./delete-test-users` export) clean up through `deleteTestUsers` (`integration/delete-test-users.ts`), which first takes every User table (`USER_DATA_TABLES`, exported by `delete-user-data.ts`) `NOWAIT` and retries in a new transaction until it gets them all, then runs `deleteUserData`: a transaction waiting for those locks one table at a time would deadlock with another file's fixture writing them out of `deleteUserData`'s order. A test running `deleteUserData` or holding its locks itself goes through the same `withUserTablesLocked`.

### packages/supabase — `@fitme/supabase`

- `supabase/` — Supabase CLI project: `config.toml`, `migrations/`, `tests/`. No seed: Postgres holds no Library, and every other row belongs to a User. There are no Edge Functions: backend code lives in the Node apps (`apps/api`, `apps/arnold`, `apps/mcp`, `apps/webhooks`).
- Account deletion: the app deletes the User in Clerk (`user.delete()`, needs Clerk's "allow users to delete their accounts") and signs out; Clerk then sends `user.deleted` to `apps/webhooks`' `POST /clerk` (registered on both Clerk instances), the only cleanup path, which runs `deleteUserData` from `@fitme/services` inside `withService`, then wipes the User's Arnold Conversations: it resets every EVE session recorded for them through Arnold's reset route (`apps/webhooks/src/arnold.ts`), so none can be resumed (a send answers `session_not_active`). EVE still keeps a reset session's stream for its retention period, so the `arnold_sessions` rows stay as tombstones: owned by the retired id, they keep the channel answering 403 to everyone. A session whose first recording failed has no row, so deletion can't find it; the first Clerk caller who addresses it claims it (nobody but its creator has the id). A failed cleanup answers 500 so Clerk retries (about a day) and is reported to Sentry.
- Personal records (ADR 0015, migration `20261031130000_personal_records.sql`, FIT-465): `personal_records` holds the records a finished Workout Session earned, one row per Exercise at most (unique `(workout_session_id, exercise_slug)`): `user_id`, `exercise_slug`, `kind` (`weight` / `reps`), `weight` (numeric(8,2), the User's unit, 0 for bodyweight) and `reps`. Cascades with its Workout Session; RLS own rows only (an insert only for the caller's own Workout Session); authenticated CRUD grants (no anon grants); RLS allows own reads and writes only through the backend's fitme login for a finished own session; the reject_retired_user_id trigger. finishWorkoutSession creates new awards; initializePersonalRecords explicitly replays historical ones; the conversion rescales their weights. The per-User completion in personal_record_initializations (FIT-466) prevents reinterpretation after conversion or session deletion; see docs/agents/personal-record-initialization.md. No automatic backfill runs on deployment.
- Exercise slugs (ADR 0007; expand migration `20261022120000_exercise_slugs_expand.sql`, FIT-235, then contract migration `20261024130000_exercise_slugs_contract.sql`, FIT-244; project "Exercises off Postgres"): Postgres holds no Library. There is no `exercises` table and no foreign key to an Exercise: `workout_exercises` and `workout_session_exercises` refer to one by `exercise_slug` only (NOT NULL, no default, no format check, ADR 0010), any string. The Library's content lives in the private `fitme-exercises` repo and is served by the Library API (`apps/library`, ADR 0008). `@fitme/services` writes, copies and matches slugs (a Workout Exercise without one fails on NOT NULL).
- `src/database.types.ts` — generated Supabase types; `src/index.ts` exports `Database`, `Tables<>`, `TablesInsert<>`, `TablesUpdate<>`, `Enums<>`
- Run the Supabase CLI from this directory (or via `pnpm db <script>`).
- Auth: Supabase Auth itself is unused: no users, every sign-up off in `config.toml` (its `[auth]` section only keeps the signing keys and the Clerk trust), no email templates, local mail server off. Supabase trusts Clerk session tokens through third-party auth (`[auth.third_party.clerk]` in `config.toml` points local stacks at the Clerk development instance; the E2E workflow adds it to its preview branch through the Management API; production trusts the production instance via the dashboard, and `config.toml` has no `[remotes]` block so it is never deployed there). `scripts/check-clerk-trust.ts` (`clerk:check`) verifies it; CI runs it against the local stack (integration-tests workflow) when the `CLERK_DEV_SECRET_KEY` secret is set, and against the E2E preview branch (e2e workflow), where the secret is required and `API_URL` also checks the E2E Public API.
- Local signing keys: `config.toml` sets `[auth] signing_keys_path` to `supabase/local-only-signing-keys.json` (committed, development only), holding the local stack's own ES256 signer. Never trust it on a hosted project.
- Identity (ADR 0001): every `user_id` column is `text` with no foreign key to `auth.users`. RLS policies read the caller through `public.current_user_id()` (the JWT `sub` claim, only when the token's `role` claim is `authenticated`; NULL for role-less tokens such as Clerk OAuth access tokens, `anon` and any other role, and for ids in `private.retired_user_ids`); never use `auth.uid()`. Nothing cascades from Supabase Auth, so account deletion runs `deleteUserData` (`packages/services`), which retires the id so a still-valid token can't write it back (`current_user_id()` is NULL for it, and `reject_retired_user_id` triggers stop writes that bypass RLS). The one-shot Clerk migration (FIT-73) rekeyed every legacy UUID to its Clerk id and retired the UUID with a pointer (`rekeyed_to`); those rows stay, and `deleteUserData` refuses such an id (`UserRekeyedError`, SQLSTATE 55000). The migration script and its `rekey_user` function were removed after the 30-day rollback window (FIT-77, migration `20261018120000_drop_rekey_user.sql`).
- `supabase/tests/` — pgTAP suite (`pnpm db test:db`). `fitme_login.test.sql` checks the `fitme` login's attributes and memberships and fails when any `public` table has RLS disabled; every new table needs RLS. Table grants on `public` are explicit in the migrations (`20261016120000_explicit_table_grants.sql`, matching the hosted project), never left to Supabase's default privileges: `supabase/roles.sql` drops the default table grants on local stacks and CI, so a new table grants `anon` / `authenticated` / `service_role` what it needs in its own migration (or fails with "permission denied"), and `table_grants.test.sql`, which lists every `public` table, gets a line for it. Functions and sequences keep the defaults (a new function is executable by `PUBLIC`, `anon`, `authenticated` and `service_role`), so a SECURITY DEFINER function in `public` revokes EXECUTE `FROM PUBLIC, anon` in its own migration and grants the roles that call it (`20261026120000_revoke_anon_rpc_execute.sql`, FIT-326), and `function_grants.test.sql`, which lists every one, gets a line for it (`current_user_id()` is the only one since the legacy RPCs were dropped, FIT-339); `current_user_id()` is the exception, since the policy of every app table but `arnold_sessions` targets `PUBLIC` and calls it, so anon keeps EXECUTE on it. Impersonate a User with `set local role authenticated` plus `request.jwt.claims` carrying a Clerk-style text `sub` and `"role": "authenticated"`; don't insert into `auth.users`.

## Key Patterns

History summaries also carry retained Personal records. A row with any shows the PR badge (`history.personalRecord`, `trophy.fill`); VoiceOver reads each record's Exercise (named through `useExercises`) and result after the rest of the row. The row still opens Workout Summary.

**Data fetching (mobile)**: All queries/mutations use `react-query-kit` wrappers (`createQuery`, `createMutation`). Import from `~/hooks/queries/<entity>` or `~/hooks/mutations/<entity>`. Reads go to Supabase, except History's: `useWorkoutSessionHistoryQuery` reads every finished Workout Session through `GET /v1/workout-sessions` (`fetchWorkoutSessionHistory`, pages of 50 until none follow, so no page size cuts the month counts or this month's totals short; a read whose `total` or `weight_unit` changed between pages, a session finished or deleted or the measurement system changed meanwhile, is read again, up to three times), since the summaries carry each session's volume and completed reps in one unit, and `useWeeklyGoalsQuery` (`hooks/queries/weekly-goals.ts`, `["weekly-goals"]`) reads `GET /v1/weekly-goals?time_zone=…` for retained goals and the service-calculated Weekly streak badge (hidden at zero), refreshing every minute for week rollover; it supplies the Weekly goal chart under this month's totals (`components/views/history-weekly-goal.tsx`, through `weeklyGoalOverview`; hidden without an active Plan or when the read fails, the list still shown; re-read after saving, activating or deleting a Plan and after a finish). Writes the Public API covers go through `publicApi()` (`lib/public-api.ts`; project "Mobile writes through the Public API", ADR 0011), typed from the committed OpenAPI document, so a body of the wrong shape fails to compile. So far these, in path order (a new write goes on its own line at its place in the order, not at the end, so parallel additions merge):

- `POST /v1/plans` — saving an Arnold plan card (`useCreatePlanMutation`: saved and made active in one transaction, then `Plan Saved` and `Plan Activated`; `lib/plan-card.ts` fits the card into `@fitme/core`'s Plan bounds, see Arnold screen)
- `DELETE /v1/plans/{id}` — deleting a Plan (`useDeletePlanMutation`; a repeat answers 204 again): `Plan Deleted` fires only after the API succeeds, and the Plan screen shows a failure as an alert (a 404 as the Plan being gone, never claiming nothing changed) and re-reads the Plans either way
- `POST /v1/plans/{id}/activate` — activating a Plan (`useActivatePlanMutation`): `Plan Activated` fires only after the API succeeds, and the Plan screen shows a failure as an alert (a 404 as the Plan being gone, never claiming nothing changed) and re-reads the Plans either way
- `PATCH /v1/profile` with only the fields edit-profile changed — editing the Profile (`useUpdateProfileMutation`: nothing changed sends no request, so a value saved before today's bounds never fails an unrelated edit; without a saved Profile it creates one through `PUT /v1/profile`, below; the name still saves to Clerk; the Profile form takes `@fitme/core`'s Profile bounds, on onboarding and edit alike, a saved value passing as long as it's unchanged)
- `PATCH /v1/profile` with `{ measurement_system }` — switching the measurement system (`useUpdateMeasurementSystemMutation`; the API converts every stored height and weight)
- `PUT /v1/profile` with the whole Profile — creating the Profile (`useStoreProfileMutation` on onboarding and `useUpdateProfileMutation` on edit-profile, both through `saveProfile`: without a saved Profile the whole one goes through PUT, with one only the changed fields through PATCH, so a re-run onboarding never makes a second Profile and an unchanged value saved before today's bounds never fails it; onboarding re-reads the Profile before moving on, and both screens show a 429 as the wait)
- `DELETE /v1/workout-session-exercises/{id}` — removing an Exercise from an open Workout Session (`useDeleteWorkoutSessionExerciseMutation`; `Exercise Deleted` only after it succeeds, a failure the same alert as adding one; the session is re-read either way)
- `PUT /v1/workout-session-exercises/{id}` — replacing one (`useReplaceWorkoutSessionExerciseMutation`: the slug and the zeroed set targets in one transaction; `Exercise Replaced` only after it succeeds, a failure keeps the picker open behind the same alert as adding one; the session is re-read either way)
- `POST /v1/workout-session-exercises/{id}/sets` — adding a set (`useCreateWorkoutSessionExerciseSetMutation`: logged on creation, `logged_at` and `order` the server's; a failure, a 409 included, is the row's usual error, a 429 its wait)
- `PATCH /v1/workout-session-sets/{id}` — logging a set (`useUpdateWorkoutSessionExerciseSetMutation`; `logged_at` is the server's, and a finished session's 409 `session_finished` is the row's usual error)
- `POST /v1/workout-sessions` — starting a Workout (`useCreateWorkoutSessionMutation`: 201 started and 200 resumed alike, then the Workout Session is read through Supabase by the answer's id; `useStartWorkout` (`hooks/start-workout.ts`) shares it between every card of the Workout tab's carousel, which pushes the Workout Session screen (the card of a Workout whose session is open comes first and reads Continue, opening it), the Workout screen, whose pinned Start replaces itself with it (Continue Workout instead when the Workout's own session is open), and the empty History's card (`components/history/empty-history-card.tsx`, shown only with no finished Workout Session and only once History, the open Workout Session and the Plans have all answered: Resume the open Workout Session, else Start the active Plan's next Workout, else Create a Plan; a 409 turns it into Resume); each shows the "Couldn't start workout" alert on a failure, the wait on a 429). Start follows the one open Workout Session per User (ADR 0013): `useOpenWorkoutSessionQuery` (`["open-workout-session"]`, a Supabase read of the User's open Workout Session: id, Plan and Workout ids, Workout name), read by the Workout screen, the Home route and History alongside their own reads, gives `useStartWorkout`'s `blockedBy`, another Workout's open session; then the Workout screen's Start is disabled with "Finish <Workout> first" and Continue <Workout> opening it (`components/workout-sessions/blocked-start.tsx`; a session whose Workout is gone opens on `/workout-sessions/{id}`), and a carousel card's Start (`onContinueBlocking`) still asks the API. A 409 `session_in_progress` re-reads it instead of the alert (still the alert when the re-read shows nothing to continue; on a carousel card, the "Couldn't start workout" alert saying "Finish <Workout> first", with a Continue button opening it); starting and finishing invalidate it, and it's re-read every 30 s while a session is open, so one finished elsewhere unblocks Start
- `POST /v1/workout-sessions/{id}/exercises` — adding an Exercise to an open Workout Session (`useCreateWorkoutSessionExerciseMutation`; `Exercise Added` fires only after it succeeds, and a failure keeps the picker open behind an alert: `library_unavailable` asks to try again, `rate_limited` gives the wait, `session_finished` says the Workout is already finished, anything else, `unknown_exercises` included, is the generic error; the session is re-read either way, since a lost answer may have saved it)
- `POST /v1/workout-sessions/{id}/finish` — finishing a Workout Session (`useFinishWorkoutSessionMutation`; `already_finished` is a success)
- `GET` / `POST /v1/workout-sessions/{id}/plan-update` — the Plan Update after finishing (`fetchPlanUpdate` and `useApplyPlanUpdateMutation`; see Finishing a Workout Session)

A write takes only what it needs from the API's answer and refetches or invalidates its Supabase queries, so no API response goes into the query cache. Every non-2xx answer, network failure or unset `EXPO_PUBLIC_API_URL` rejects with an `ApiError` (`lib/api/client.ts`: `status`, the API's `code`, `message`, `retryAfterSeconds` for a 429; `status` and `code` `null` without an answer); a screen shows `rate_limited` as "try again in N s" (`rateLimitedFor`) and anything else as its usual error state, a 401 isn't special-cased, and a write never falls back to Supabase. No mobile write is left on Supabase. The fake Supabase backend has no RPCs and refuses the moved writes (inserting or updating a Workout Session set, inserting, updating or deleting a Workout Session Exercise, updating a Plan, and inserting, upserting or updating a Profile), so a test whose screen falls back to Supabase fails. The Public API workflow regenerates `lib/api/schema.ts` from `apps/api/openapi.json` and fails when it's stale, so a contract change regenerates the app's types in the same pull request (`pnpm mobile api:types`).

**Exercises (mobile)**: Plans, Workouts and Workout Sessions refer to Exercises by Exercise slug (`exercise_slug`; ADR 0007, project "Exercises off Postgres"): the Supabase reads select it and join no Exercise, and the writes go through the Public API, which checks the slug of a Plan or of an Exercise added to or replaced in a Workout Session. Details come from the Library API through `hooks/queries/library.ts`, in the App language (`useAppLanguage()` from `lib/i18n.ts`, passed to the SDK as `language`; an Exercise without a translation comes wholly in English): `useExercises(slugs)` (and `useExercise(slug)`) answer every slug as a `ShownExercise` at once, one react-query query per slug (`["exercise-summary", language, slug]`, stale after an hour, the API's `Cache-Control`), the slugs asked for in the same tick and language sharing one `lookup` (the client splits it into requests of 40); `useExerciseDetailQuery(slug)` reads one in full (`get`, `["exercise-detail", language, slug]`) for the detail screen and the guide. Every key carries the language, so a new App language refetches and never mixes languages. Each resolved Exercise is kept in MMKV per language (`library.<language>.exercise-summary.<slug>`, `library.<language>.exercise.<slug>`, the same for every User, with when it was saved; `lib/library-cache.ts`) and read as the query's `initialData`, so each language shows offline and right after a restart and is refetched once stale; one the library no longer has is forgotten in every language. The English-only keys of earlier builds (`library.exercise-summary.*`, `library.exercise.*`) are swept once per install (`library.untranslated-exercises-swept`). A slug never resolved (offline first run, a failing library, or unknown to it) shows `exerciseNameFromSlug`'s name, no muscle groups and no thumbnail, and isn't a link to a detail screen or guide; screens never wait on the library. Thumbnails are the render endpoint's `thumbnail_url` with the shown size appended (`sizedThumbnailUrl` in `lib/exercise-media.ts`, device pixels). Exercise history queries `workout_session_exercises` by `exercise_slug`. Arnold's plan card links and saves by each Exercise's `exercise_slug` (a card from before slugs can't be saved). It saves through `POST /v1/plans` (see Data fetching), its body built by `planCardBody` (`lib/plan-card.ts`): the card is a suggestion, so set counts, reps, rest, frequency and Workout duration are clamped into `@fitme/core`'s bounds and rounded, Workouts without Exercises left out, lists and text cut to their maximum; with nothing left Save is disabled. `unknown_exercises` and `library_unavailable` show their own message on the card, a 429 its wait, anything else the card's generic error; nothing is saved and Save stays available. The Library tab and the Workout Session's Exercise picker (both `components/views/exercises-view.tsx`; the picker is its own route, `app/workout-sessions/[workoutSessionId]/exercise-picker.tsx`, a page sheet with a native header titled Add Exercise, or Replace Exercise given `replaceExerciseId`, a Workout Session Exercise's id, starting on `muscleGroup` chosen, plus a close button; it adds or replaces through the Public API and closes once saved, a failure keeping it open behind its alert) search the library through `useExerciseSearch({ search, muscleGroups })`: an infinite query over `list` in the App language (`language` sent unless it's English, the API's default; the query key carries it, so a new App language starts a fresh search at once and never shows another language's results, not even while rate limited), so a search matches the name in the App language or the English one and results come in that language's order; pages of 20, `offset` paging while `hasMore` (the next page loads as the User scrolls near the end of the list, no button; a request in flight is never repeated, and a failed one asks again only when a drag ends near the end), a changed search sent 300 ms after the last keystroke (each User gets 120 requests a minute) and a changed Muscle group choice at once. The Muscle group choice (Exercises working any of the chosen groups, `muscleGroups` on `list`) comes from the Muscles pill, which always reads "Muscles" and opens the Muscles sheet (`app/muscles.tsx`, a root-stack form sheet, medium → large, with Reset, the title and a ✓ in its native header): every choosable Muscle group (core's `muscleGroups` but full-body and cardio) in core's order with a check circle, ticked as a draft from the opener's choice; ✓ hands the draft back and closes, Reset clears it without applying, swiping away discards it. Each chosen group also shows as a chip under the pill (`components/exercises/muscle-group-chips.tsx`): one lime `Badge` with a trailing `xmark` per group, in that same order, wrapping onto further lines; tapping × removes that group at once (VoiceOver reads "Remove <group>" from `library.removeMuscleGroup`), and with nothing chosen there is no chip row. Each screen's choice lives in memory only (`hooks/muscle-choice.ts`, keyed per screen, passed to the sheet as `choice`, kept in core's order so the same choice reuses its query): the Library tab's (`library`) lasts while the app runs, the picker gets a fresh key per opening (`newMuscleChoiceKey` with `useMuscleChoiceOpening`, the replaced Exercise's first Muscle group or none) and forgets it once closed, so the two never share a choice. "Show All Exercises" clears the search and every chosen Muscle group. A 429 keeps the last results on screen with no error and holds every next request (a search, the next page, a refresh, from either screen: the deadline is kept in the query client) back until `Retry-After` has passed; any other failure, a failed refresh included, is the view's error state (a failed next page keeps the results, with a message at the bottom of the list). Both search from the native header search bar (`headerSearchBarOptions` on the screen's Stack screen, `placement: "stacked"`, through `useHeaderSearch` in `hooks/header-search.ts`; on the Library tab hidden until pull-down on iOS, in the picker's page sheet always shown and keeping its header, title and Close, while searching, since pulling a sheet's list down dismisses it), whose text the screen hands the view as `search` / `onSearchChange` ("Show All Exercises" clears the bar through its `ref`); the view has no search field of its own, and the picker's search starts empty on every open. The view is the screen's scroll container, a virtualised `FlatList` (the Muscles pill and its chips are its header; the picker's page sheet has no `ScrollView` around it, and the Library tab gets pull to refresh through `refreshable`), keeping taps (`keyboardShouldPersistTaps="handled"`), so a result is tapped with the keyboard up. Every listed Exercise is seeded into its row query and MMKV copy in the language it was listed in, so its detail screen has its name at once and it shows offline; picking one writes its `slug`. The "Update your plan?" sheet names the Plan Update's slugs through `useExercises`, so an unresolved one shows its slug's name. Each slug's query retries once (never on a 429, 401 or 400), and the detail query writes what it read into the slug's row query, so an Exercise that left the library stops linking at once. The Workout tab's cards show their Workout's Cover (`workouts.cover`, ADR 0014) at 80% opacity under the card's scrim, from `useCovers()`: one query over `covers()` (`["covers"]`, stale after an hour, retried once like the slugs), kept in MMKV as one list for every User and language (`library.covers`) and read as its `initialData`, so Covers show offline and right after a restart; a failed refresh, a 429 included, keeps the last list. The image is the render endpoint's `image_url` at the card's size (`sizedThumbnailUrl`); a Workout without a Cover, an id the list doesn't have, no list at all or an image that fails to load leaves the card black, and the tab never waits on Covers.

**Minimum version gate (mobile)**: `components/minimum-version-gate.tsx` wraps the root `Stack` in `app/_layout.tsx`. The global `fetch` is `expo/fetch`, installed by Expo's runtime (since SDK 57), so eve's NDJSON stream streams; don't set `EXPO_PUBLIC_USE_RN_FETCH`. The custom chat components (`components/chat/`) read the runtime's state (`useAuiState`) as assistant-ui `ThreadMessage`s; the plan card renders from a `display_workout_plan` tool call's result. `lib/arnold-chat.ts` holds the pure parts (unit-tested): each send carries `runConfig: { custom: { model, language } }` (`arnoldRunConfig`), which eve sends as the turn's client context, with the model-picker's choice and the App language (`i18n.language`, English when it isn't an App language) read at send time (no model → only `language`, so Arnold uses its default model); `arnoldErrorAction` maps the channel's Pro refusal (`arnold_pro_required`) to the paywall, an ended session (`session_not_active`, `session_expired`, `session_stranded`) to a new Conversation, and anything else to the existing error state, whose text comes from the catalogs by `arnoldErrorKind` (the Pro check unavailable, a send that never reached Arnold, or generic), never the server's message; a refused or failed send's text goes back into the composer and its failed bubble is hidden (`isRefusedSend`); and the User's current Conversation (eve session cursor plus the event log from the last finished turn) is saved in MMKV per Clerk User id (`arnold.conversation.<userId>.session`, rewritten on every streamed event, and `….events`, once per finished turn), so reopening the screen resumes it, an answer still streaming included. "+" in the header resets the eve session and forgets the saved one. The model picker (`app/(tabs)/arnold/model-picker.tsx`) lists the models served by `apps/api`'s `GET /v1/arnold/models` through `publicApi()` (`useArnoldModelsQuery`, ADR 0006), never a bundled list: the last successful response is kept in the global MMKV key `arnold.models` (not per User), read as the query's `initialData` (offline too) and rewritten on every successful fetch; an unreadable or malformed value counts as no list. `lib/arnold-model.ts` resolves the saved pick (`arnold.model`) against the list: kept while it's in it, otherwise (removed, or an old pre-Gateway id; never migrated) the list's `defaultId`. With no list at all (nothing cached and the fetch failed, or `EXPO_PUBLIC_API_URL` unset) the picker shows a loading or unavailable state and sends carry no `model`; chat never waits on the list.

**Finishing a Workout Session (mobile)**: every way of finishing (the session header's Finish button, the finish suggestion) goes through `useFinishWorkoutSession` (`hooks/finish-workout-session.ts`): the "Finish workout?" confirmation when planned sets are unlogged (not for the suggestion), the finish call (`POST /v1/workout-sessions/{id}/finish`), then the plan update step: `GET /v1/workout-sessions/{id}/plan-update` (`fetchPlanUpdate` in `hooks/queries/workout-sessions.ts`). With changes (and a live Plan and Workout) it asks "Update your plan?" (`components/workout-sessions/plan-update-sheet.tsx`, one line per change from the pure formatter in `lib/plan-changes.ts`, which also holds the `PlanUpdate` types taken from the generated API schema; each Exercise by its Library name through `useExercises`, and weights in the answer's `weight_unit`, so no Profile is read) and opens the Summary once the User answers; without changes it opens the Summary at once, and a failed preview is reported to Sentry and opens the Summary too, so finishing never fails because of it. The sheet is a native `Dialog` that can't be swiped away, shown by `PlanUpdateSheetHost` in the root layout (`app/_layout.tsx`) through the small store in `hooks/plan-update-prompt.ts`, not by the screen that finished: the session screen that finished it is replaced by the Summary. "Update plan" applies (`useApplyPlanUpdateMutation`, `POST /v1/workout-sessions/{id}/plan-update`, idempotent server-side, so a Retry never applies twice), invalidates the Plan queries and opens the Summary; a failed apply shows an inline error with Retry (a 429 its wait, unreported), and "Keep plan as is" always opens the Summary unapplied. Segment gets `Plan Update Suggested` (a count per change kind) once the preview has answered, `Plan Update Accepted` once the apply has, and `Plan Update Declined`. Free: no Pro check.

**Subscriptions**: RevenueCat manages IAP. `useIsProQuery` (queryKey `["rc-is-pro"]`) checks the "Fitme Pro" entitlement. Customer info updates are listened to in `_layout.tsx`.

**Module aliases**: Inside each app, `~/` and `@/` resolve to that app's root. Cross-workspace imports always go through the package name (`@fitme/core`, `@fitme/supabase`).

**Workspace packages are source-only**: no build step. Metro resolves them through the hoisted `node_modules`; Next compiles them via `transpilePackages`. CSS (`@fitme/design-tokens/tokens.css`) is `@import`ed by package name and resolved by Tailwind's compiler (uniwind's, under Metro). The tsdown apps (`apps/api`, `apps/library`, `apps/mcp`, `apps/webhooks`) inline `@fitme/*` and no package from `node_modules` (`deps.onlyBundle: []`): a workspace package's runtime dependency (`pg`, `drizzle-orm`, `@vercel/functions` for `@fitme/db`) must also be in the app's `dependencies`, or its build fails; it stays external and Vercel traces it into the function. Their build emits the Vercel entry as `dist/app.js` and the standalone Node server (`pnpm start`) as `dist/node/index.js`, out of Vercel's entrypoint lookup. pnpm uses `nodeLinker: hoisted` (see `pnpm-workspace.yaml`) because React Native autolinking needs a flat `node_modules`. Its `overrides` pin `react` / `react-dom` to the version Expo's React Native expects, so the workspace has one copy (`expo-doctor` flags a second); move it with the Expo SDK, together with each app's own pin. Its `patchedDependencies` patch uniwind (`patches/`): uniwind's Metro resolver swaps `react-native` for its own export list, which lacks RN 0.88's `AssetRegistry`, so expo-asset can't load assets, `useFonts` fails without a LogBox error and the splash never hides. Drop the patch once a uniwind release exports it (FIT-170).

## Shell

- Never `cd` inside a `&&` chain. The working directory carries over between commands, so `cd apps/mobile && <edit>` run from inside `apps/mobile` fails at the `cd` and silently skips the edit. Use absolute paths, `git -C <path>` and `pnpm --filter <package>` instead.
- macOS has neither `timeout` nor `gtimeout`: bound a long command with your tool's own timeout, not a wrapper.
- `scripts/setup.sh` (and the other `scripts/*.sh`) runs under macOS `/bin/bash` 3.2: test changes with `/bin/bash -n`. Bash 5 accepts things 3.2 rejects (a quote inside a heredoc in `$(...)` once made setup a syntax error), so keep Node out of heredocs, in its own file (`scripts/rewrite-env.mjs`, `scripts/stale-stacks.mjs`, tested with `pnpm test:scripts`). Setup appends timestamped step lines to `scripts/setup.log` (git-ignored).
- Wait in the background: a foreground `sleep` (`sleep 60; gh pr view …`) is blocked by the harness. Run the command in the background or use Monitor; for a pull request, `watch_pull_request`.
- `pgrep -f` / `pkill -f` match the shell running them, since the pattern is in its own command line: the wait never ends, or the kill takes your shell with it. Use a bracket pattern (`pgrep -f '[u]ltracite'`) or the PID you saved when starting the process.
- The shell is zsh: an unquoted `?` or `*` is a glob, and one matching nothing fails the command with "no matches found". Quote URLs and arguments carrying them: `gh api 'repos/…/git/trees/HEAD?recursive=1'`, `--filter='...[origin/main]'`.
- zsh doesn't word-split an unquoted `$var`: a list in a variable stays one argument (`files=$(grep -rl …); perl -pi -e '…' $files` hands perl one long name). Use an array (`files=(a b)`; `"${files[@]}"`), `${=var}`, or pipe NUL-separated names into `xargs -0` (`git ls-files -z`, `grep -rlZ`).
- Supabase CLI output: `--output-format json`, never `-o` / `--output` (the CLI refuses the legacy flag).
- Secrets: never print an env file's values, and never let a `prod` value into your shell, a file or a command line. How to look at an env file, and how to smoke-test a deployment without a prod credential: `docs/agents/secrets.md` (Handling values).
- zsh ties the lowercase array `path` to `PATH`: `path=…`, `local path=…`, `for path in …` or `while read path` replaces the command search path, and every later command in that shell fails with "command not found". Never name a variable `path`; use `file`, `dir` or `p`.
- Run EAS (the global `eas` CLI, no workspace dependency) in `apps/mobile`, through `pnpm --filter @fitme/mobile exec eas …`, never from the repo root, where it writes a stray `app.json` (`{"expo": {}}`).
- A Claude Code `PreToolUse` hook (`.claude/hooks/check-shell-command.mjs`, wired in `.claude/settings.json`) refuses a Bash call that breaks these rules, with the rule's reason: `timeout` / `gtimeout` as a command, `cd <relative path>` followed by `&&`, `;` or another line, `pkill -f` / `pgrep -f` without the bracket trick (`'[u]ltracite'`), a foreground `sleep` of 5 s or more, `for x in $var` (one bare variable as the whole list), a `path` variable set (`path=…`, `local` / `typeset` / `declare` / `export` / `readonly` / `read path`, `for path in`; function bodies included, `path+=(dir)` allowed), `supabase … -o` / `--output`, `infisical secrets [get|set]` / `export` / `run` with `--env=prod`, and `cat` / `head` / `tail` / `less` / `more` / `bat` / `grep` / `rg` / `sed` / `awk` / `cut` printing a `.env*` file (`.env.example` aside) unless it or a later command in its pipeline strips the values (`cut -d= -f1`, `awk -F= '{print $1}'`, `sed 's/=.*/…/'`; `grep -q` / `-l` / `-c` and `sed -i` print none). It only reads command words, never quoted text, heredocs or comments, and checks the commands inside a substitution (`$(…)`, `` `…` ``, `<(…)`) as commands too; its matcher (`.claude/hooks/shell-rules.mjs`) is tested with `pnpm test:hooks` (Node's `node:test`).

## Git

The default branch is `main` (there is no `master`); branch from it and open pull requests against it. A clone whose `origin/HEAD` still points at `origin/master` is stale; repair it with `git remote set-head origin --auto && git remote prune origin`.

Compare against `origin/main`, never the local `main`: worktrees branch from a local `main` that is often several commits behind, so `git diff main...HEAD` shows other pull requests' changes. `git fetch origin` first, then diff, rebase and compare against `origin/main` (`git diff origin/main...HEAD`, `git rebase origin/main`).

Before pushing, check only what changed and leave the full matrix to CI, which still runs every suite (see CI/CD): repo-wide `pnpm check`, `pnpm typecheck` and `pnpm turbo run test` overrun the 600 s tool timeout on the shared 2-core agent box and flake under load. Run `pnpm turbo run test typecheck --filter='...[origin/main]'` (the changed workspaces and their dependents, so a change to `packages/core` or `packages/design-tokens` reaches every app that uses it) and `pnpm exec ultracite check <changed files>`, plus `pnpm literal-check` when a `.tsx` in `apps/mobile`, `apps/web` or `apps/site` changed, and `pnpm text-check` when a `.ts` or `.tsx` in `apps/mobile` did. A root config change (`biome.jsonc`, `turbo.json`, root `package.json`, `pnpm-workspace.yaml`) touches every workspace: the filter then selects them all, and the lint rules may have moved, so run the full `pnpm check` too, as a background command.

Resolving a rebase or merge conflict: edit each hunk by hand, never with a regex or script that concatenates both sides (one dropped a `/**` from `apps/api/src/services.ts` and failed every `@fitme/api` test file). Before `git rebase --continue`, run `git diff --check` and the changed workspaces' `pnpm turbo run test typecheck --filter='...[origin/main]'`. In `AGENTS.md`, the long lists keep one item per line in a stated order, so a new item goes in at its place and parallel additions merge on their own; keep both sides when they still conflict.

Put a `FIT-<n>` key in a pull request's title, branch or commits only when that pull request finishes the issue: Linear links the PR on sight, moves the issue to In Progress and closes it on merge.

A contract step (dropping legacy routes, RPCs, env names or code once the minimum version gate has cut off their readers) is `refactor:` / `chore:` (or `feat:` / `fix:` when it changes behaviour), never `!` or `BREAKING CHANGE`. Those are for a deliberate major app release only, since `release.yml` cuts a major version from them (see CI/CD). Its check greps every commit's subject and body for `BREAKING CHANGE` anywhere, so never write that phrase in a commit message, a squash message or a pull request title, even to mention it (say "breaking-change marker").

`main`'s ruleset requires every review conversation resolved before merging: with CI green and the review approved, `gh pr merge` is still refused while a thread is open. After pushing the fix for a review comment, reply with the commit and resolve the thread (`gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "…"}) { thread { isResolved } } }'`; list the ids with `reviewThreads { nodes { id isResolved } }` on the PR's `pullRequest` query). Resolve only the threads you actually fixed.

A Codex review can hang on "Running" and never post, and `watch_pull_request` only wakes on checks, comments or conflicts, so a hung review never wakes the agent. If there's no Codex summary comment at all, or it still says "Running", about 30 minutes after CI went green, comment `@codex review` once. If it still hasn't answered about 30 minutes after that, unwatch the PR (`unwatch_pull_request`) and hand it back to the user, naming the stuck review. Never merge without the review unless the user says so. Wait on `watch_pull_request` notifications only, never a shell loop polling `gh pr view` (see **Shell**).

A "stopped watching" notification means the watch dropped, not that the PR is done: re-read the PR (checks, reviews, unresolved threads), act on anything new, then call `watch_pull_request` again. If it stops a second time, hand the PR back to the user.

Before merging, read every check with `gh pr checks <n> --json name,state,bucket`, which lists check runs and status contexts (the Vercel deployments) alike, and merge only when no entry is in the `pending` or `fail` bucket. In `statusCheckRollup` a status context keeps its values in `.context` / `.state`, not `.name` / `.conclusion`, so a query on the latter prints `null` for it and can't see a pending or failed Vercel build.

Merge with `gh pr merge <n> --squash`, without `--delete-branch`: the repo deletes the remote branch on merge (`delete_branch_on_merge`), and settle removes the worktree's local branch. With `--delete-branch` gh prints `! Branch … is checked out in the current worktree; skipping local delete`, which is harmless; don't report it.

The pre-commit hook (`.husky/pre-commit`) scans the staged changes for secrets with gitleaks (`.gitleaks.toml`: the default rules, a `password-literal` rule, and the allowlisted false positives, by path or value, never by commit) and fails the commit on a finding; install it with `brew install gitleaks`, or the hook only warns. It also fails a commit whose staged lines add a conflict marker (`<<<<<<<`, `|||||||`, `>>>>>>>`). A worktree runs no hook until `pnpm exec husky` has created its `.husky/_` (`scripts/setup.sh` runs it). CI's `secrets` job (`.github/workflows/unit-tests.yml`) scans every pull request's commits the same way.

## Code Review Rules

Before reviewing a pull request's diff, gather its intent:

1. Read the PR description in full. It states what the change does, why, and what was deliberately left out.
2. Read the linked Linear issue. The issue key (`FIT-<n>`) is in the PR title, branch name or description. Read its description and comments, including acceptance criteria and blocking relations.
3. If the issue belongs to a Linear project, also read the project description. The project description is the spec, and it holds the decisions and constraints that apply across all of the project's issues.

Then review the diff against that intent: flag code that misses an acceptance criterion, goes beyond the issue's scope, or contradicts a decision in the spec, the ADRs (`docs/adr/`) or this file. Don't flag things the description or spec explicitly defers to a later issue. If a PR names no issue, or you can't read Linear, say so in the review and review against the PR description alone; never guess what an issue says.

### Issue tracker

New issues always go to `Backlog`, never `Todo`, and carry an area label (`mobile`, `web`, `site`, `mcp`, `api`, `arnold`, `webhooks`, `library-api`, `database`, `ci`, `docs`) for every area they're expected to change; `exercises` is only for work in the private `fitme-exercises` repo. # Ultracite Code Standards

This project uses **Ultracite**, a zero-config preset that enforces strict code quality standards through automated formatting and linting.

## Quick Reference

- **Format code**: `npm exec -- ultracite fix`
- **Check for issues**: `npm exec -- ultracite check`
- **Diagnose setup**: `npm exec -- ultracite doctor`

Biome (the underlying engine) provides robust linting and formatting. Most issues are automatically fixable.

---

## Core Principles

Write code that is **accessible, performant, type-safe, and maintainable**. Focus on clarity and explicit intent over brevity.

### Type Safety & Explicitness

- Use explicit types for function parameters and return values when they enhance clarity
- Prefer `unknown` over `any` when the type is genuinely unknown
- Use const assertions (`as const`) for immutable values and literal types
- Leverage TypeScript's type narrowing instead of type assertions
- Use meaningful variable names instead of magic numbers - extract constants with descriptive names

### Modern JavaScript/TypeScript

- Use arrow functions for callbacks and short functions
- Prefer `for...of` loops over `.forEach()` and indexed `for` loops
- Use optional chaining (`?.`) and nullish coalescing (`??`) for safer property access
- Prefer template literals over string concatenation
- Use destructuring for object and array assignments
- Use `const` by default, `let` only when reassignment is needed, never `var`

### Async & Promises

- Always `await` promises in async functions - don't forget to use the return value
- Use `async/await` syntax instead of promise chains for better readability
- Handle errors appropriately in async code with try-catch blocks
- Don't use async functions as Promise executors

### React & JSX

- Use function components over class components
- Call hooks at the top level only, never conditionally
- Specify all dependencies in hook dependency arrays correctly
- Use the `key` prop for elements in iterables (prefer unique IDs over array indices)
- Nest children between opening and closing tags instead of passing as props
- Don't define components inside other components
- Use semantic HTML and ARIA attributes for accessibility:
  - Provide meaningful alt text for images
  - Use proper heading hierarchy
  - Add labels for form inputs
  - Include keyboard event handlers alongside mouse events
  - Use semantic elements (`<button>`, `<nav>`, etc.) instead of divs with roles

### Error Handling & Debugging

- Remove `console.log`, `debugger`, and `alert` statements from production code
- Throw `Error` objects with descriptive messages, not strings or other values
- Use `try-catch` blocks meaningfully - don't catch errors just to rethrow them
- Prefer early returns over nested conditionals for error cases

### Code Organization

- Keep functions focused and under reasonable cognitive complexity limits
- Extract complex conditions into well-named boolean variables
- Use early returns to reduce nesting
- Prefer simple conditionals over nested ternary operators
- Group related code together and separate concerns

### Security

- Add `rel="noopener"` when using `target="_blank"` on links
- Avoid `dangerouslySetInnerHTML` unless absolutely necessary
- Don't use `eval()` or assign directly to `document.cookie`
- Validate and sanitize user input

### Performance

- Avoid spread syntax in accumulators within loops
- Use top-level regex literals instead of creating them in loops
- Prefer specific imports over namespace imports
- Avoid barrel files (index files that re-export everything)
- Use proper image components (e.g., Next.js `<Image>`) over `<img>` tags

### Framework-Specific Guidance

**Next.js:**
- Use Next.js `<Image>` component for images
- Use `next/head` or App Router metadata API for head elements
- Use Server Components for async data fetching instead of async Client Components

**React 19+:**
- Use ref as a prop instead of `React.forwardRef`

**Solid/Svelte/Vue/Qwik:**
- Use `class` and `for` attributes (not `className` or `htmlFor`)

## Testing

- Write assertions inside `it()` or `test()` blocks
- Avoid done callbacks in async tests - use async/await instead
- Don't use `.only` or `.skip` in committed code
- Keep test suites reasonably flat - avoid excessive `describe` nesting

## When Biome Can't Help

Biome's linter will catch most issues automatically. Focus your attention on:

1. **Business logic correctness** - Biome can't validate your algorithms
2. **Meaningful naming** - Use descriptive names for functions, variables, and types
3. **Architecture decisions** - Component structure, data flow, and API design
4. **Edge cases** - Handle boundary conditions and error states
5. **User experience** - Accessibility, performance, and usability considerations
6. **Documentation** - Add comments for complex logic, but prefer self-documenting code
